# GCP emulator — wire contract

This document states what the emulator's fidelity matrix promises. It is a **wire
contract** — a declaration of which operation/transport cells are supported and
wire-conformant — **not** a claim of feature-parity with Google Cloud. Read it with
[`docs/fidelity/fidelity-matrix.md`](../fidelity/fidelity-matrix.md) open.

For the local-testability view — per-service tiers, behavioural depth, the AWS→GCP
mapping, and what must be tested against real GCP — see
[`docs/gcp/testability.md`](testability.md). For the guide, quick start and the
per-service caveats, see [`README-GCP.md`](../../README-GCP.md).

---

## 1. What `ga` means in the matrix

`ga` is a claim about the **wire contract**, not about reproducing every GCP subsystem:

- An official Google client — a REST service client or a native gRPC client — pointed at
  `jaiscloud-gcp` sees the same request/response shapes, status codes, error envelopes, field
  names, and long-running-operation envelopes the real API returns, within the surface declared
  in the fidelity matrix.
- Every operation/transport pair is classified `ga` / `limited` / `preview` / `unsupported` in
  the derived fidelity matrix. That matrix *is* the published contract.
- `ga` means **supported and wire-conformant**. It does **not** mean the emulator implements the
  same backend. Where a service is metadata-only or has no data plane, the matrix says `limited`
  and the reason names the missing plane.
- A `ga` service can still be metadata-only by design where the real behaviour *is* the metadata
  API (Eventarc trigger/channel CRUD, Managed Kafka cluster/topic metadata). The matrix measures
  the API contract; the functional caveats live in
  [README-GCP "Known Limitations"](../../README-GCP.md#known-limitations).
- Unsupported surfaces fail loud — HTTP `501 UNIMPLEMENTED` on REST, `codes.Unimplemented` on
  gRPC — rather than silently succeeding or fabricating data.
- The matrix also reports **coverage**, per service and transport: the published method list
  (the vendored Discovery document for REST, the proto service descriptors for gRPC) against the
  routes the emulator actually registers and the methods the cells grade. `served` is a
  registration statement — a served method may answer the documented `UNIMPLEMENTED` and be graded
  `unsupported`; it is not missing. `not served` means no route exists at all, so no cell could
  grade it. A missing cell is therefore **not** a `ga` claim, and where the published list cannot
  be derived from what is vendored (no Discovery document, or a REST-only service with no gRPC
  surface) the row says `unavailable` with the reason instead of guessing.

In short: a client written against the official SDKs will interoperate; a workload that needs a real
backend the emulator does not model (a VM, event delivery, a full analytics engine) will not get
one, and the matrix says so up front.

## 2. Supported surface

The canonical sources are
[`docs/fidelity/fidelity-matrix.json`](../fidelity/fidelity-matrix.json) (machine-readable),
[`fidelity-matrix.md`](../fidelity/fidelity-matrix.md) (human-readable) and
[`fidelity-matrix.csv`](../fidelity/fidelity-matrix.csv) (flat). They are generated by
`make gen-gcp-fidelity-matrix` from the emulator's operation registry, the vendored Discovery
schemas, the wire-conformance harness, and the curated
[`docs/fidelity-overrides.yaml`](../fidelity-overrides.yaml); `make check-gcp-fidelity-matrix`
fails CI if the committed matrix drifts. The current service/cell rollup, by state and by
transport, is in the generated matrix — `make gcp-status` prints the same rollup.

### Field coverage

The matrix grades **operations**; a field can be present in the published API,
absent from the emulator's mapping, and still pass every operation-level gate.
That is the defect class behind TGM1-3, TGM6, TGM11-1 and TGM14, so fields have
their own derived inventory:
[`docs/fidelity/field-coverage.csv`](../fidelity/field-coverage.csv). It lists one
row per field and transport for the resources in
[`tools/fieldgen/scope.yaml`](../../tools/fieldgen/scope.yaml) — derived from the
compiled proto descriptors (`google.api.field_behavior`,
`google.api.resource_reference`) and the vendored Discovery schemas
(`readOnly`) — and classifies each row `roundtrip`, `derived`, `immutable`,
`output-only` or `unsupported`. `roundtrip`/`immutable` rows must point at an
existing test function (`path#TestName`, resolved by the gate) that exercises
the field, `derived` rows
name the formula, `output-only` rows carry a test or a reason the emulator never
populates them, and `unsupported` rows carry a written reason and a future review
date (an expired date fails). A `roundtrip` row whose definition declares the
field `OUTPUT_ONLY`/`IMMUTABLE`/`readOnly` must carry a reason: it is a
deliberate deviation, not an accident. `make gen-gcp-field-coverage`
scaffolds new definition fields (they arrive unclassified) and drops the
classification of a row whose definition behavior changed, so a semantics change
forces re-review; `make check-gcp-field-coverage` fails CI when a definition field
has no row, a row is stale, recorded behavior drifts from the definition, or a
classification's evidence contract is unmet. The pilot scope is Storage `Bucket`, Firestore
`Database`/`BackupSchedule`, Functions v2 `Function`, KMS `CryptoKey`, Cloud DNS
`ManagedZone` and Monitoring `AlertPolicy`; later waves widen it. A Terraform
provider-schema join (sent-but-unsupported attributes) is the documented FC6 hook
in `tools/fieldgen/terraform.go`.

### States

| state | meaning |
| --- | --- |
| **ga** | supported and wire-conformant |
| **limited** | implemented with a declared caveat (each cell carries its reason) |
| **preview** | not covered by the stability promise |
| **unsupported** | not implemented — explicit `Unimplemented` stub |

gRPC-only wire services (no REST descriptor of their own): **Firestore Admin,
Operations (long-running)**. Firestore Admin's REST control plane (databases,
collection-group fields, backup schedules, backups, user creds, change streams)
is served under the `firestore` service descriptor on
`firestore.googleapis.com/v1/…`; the distinct
`google.firestore.admin.v1.FirestoreAdmin` gRPC wire service has no REST
descriptor because REST clients address it through the `firestore` document
service. Change streams are **REST-only by upstream design**: the admin v1
Discovery document declares `projects.databases.changeStreams.{create,get,list,delete}`
while the `FirestoreAdmin` proto service declares no ChangeStream RPC, so the
emulator serves those four methods on the `firestore` REST descriptor only (no
gRPC cell exists to grade). The resource is stored and echoed as configuration;
no change records are produced, because no read method exists on which a feed
could be observed.

### Recorded evidence (`verified`)

Each cell carries a **`verified`** signal distinct from its state: a cell is verified when
real recorded evidence backs it — a schema-validated response in the committed conformance
transcript (REST) or a passing check from the official-client gRPC conformance suite. A `ga`
cell that is not `verified` is a *registration claim* (implemented, Discovery-mapped, no
finding, persists), not a response guarantee. `make gcp-status` prints the verified rollup, and
`make gcp-status-evidence` lists every Discovery-mapped REST operation without a validated
response. This is **enforced**: `tests/gcpconformance` derives a probe for every registry
operation that maps to a Discovery method (see `probe.go`) and `TestMappedOpCoverage` fails the
build (via `make test-gcp-wire-conformance` and `make ga-check`) on any mapped operation that has
neither a recorded 2xx response matched to its Discovery method nor an entry in
`tests/gcpconformance/testdata/coverage-exemptions.json` with a written reason. A response
whose body is a single JSON document is additionally schema-validated against the Discovery
schema by `TestTranscriptsConform`.

### Release policy

The emulator ships as one release carrying every cloud binary, so this section is the release
contract a tag has to satisfy (it is what `README-GCP.md` install instructions point at):

| decision | policy |
| --- | --- |
| **Tag target** | **`main`** — releases are tagged on `main` (the former long-lived `gcp` branch was merged there via #610 and `v0.1.1` was cut from it). One tag publishes `jaiscloud-aws` **and** `jaiscloud-gcp` artifacts, images and packages from the same commit. |
| **Version** | Semver (**`v0.1.1`**; `v0.1.0` is the prior published tag). `release.yml` fires on any `v*` tag. |
| **Prerelease** | `prerelease: auto` in `.goreleaser.yaml`: a bare `vX.Y.Z` tag is a full GitHub release, a `vX.Y.Z-rc.N` tag is flagged prerelease. |
| **Image tags** | Docker Hub `jaisraj/jaiscloud-gcp` and `jaisraj/jaiscloud-aws` each get `{{ .Version }}` and `latest`; GHCR (`ghcr.io/<owner>/jaiscloud-gcp`) is pushed from `main` by `docker-publish.yml`. `latest` follows the newest **full** release; a prerelease should be tagged by version only (`.goreleaser.yaml` currently tags `latest` unconditionally with a TODO to gate it — flip that before cutting a prerelease). |
| **Artifacts** | `jaiscloud-gcp_<version>_<os>_<arch>.tar.gz` (`.zip` on Windows), `.deb`/`.rpm` for linux amd64/arm64, Homebrew cask `jaiscloud-gcp`, Scoop `jaiscloud-gcp`, `checksums.txt`; every binary is built with `-tags ui` so the console is embedded. |

Both binaries must report the tag via `<binary> version`, and the release is only cut once
`ci.yml`'s `release-config` and the artifact suite (`make test-release`) are green on the merged
commit.

## 5. Explicitly non-`ga` surfaces

- **BigQuery** — 40 cells: 1 `ga` (the Discovery document), 36 `limited` + 3 `unsupported`.
  `jobs.query`/`jobs.insert` (query
  configuration) evaluate a documented Standard SQL subset — `SELECT` plus DDL/DML — on an
  in-process pure-Go SQLite engine in both memory and `--dsn` modes
  (`docs/gcp/bigquery-sql-engine.md`); `jobs.insert` also runs `configuration.load` jobs from
  one or more `gs://` NDJSON/CSV/Parquet/Avro sources (a single-`*` wildcard URI is expanded)
  or an uploaded file (multipart/resumable media session, `load_table_from_file`), with the
  schema supplied, embedded in the file, or autodetected; `tabledata.*` reads and writes the
  stored rows;
  `routines.*` and `rowAccessPolicies.*` are stored CRUD resources (memory and `--dsn`; a
  routine body is never executed and a row access policy predicate is never enforced);
  table-level IAM (`tables.getIamPolicy`/`setIamPolicy`/`testIamPermissions`) is a stored
  policy over the shared `ResourceStore` with etag OCC and the AIP-149 version rules, while
  dataset-level IAM is the legacy dataset `access` ACL (real BigQuery publishes no
  `datasets.getIamPolicy`); the
  `models.*` resource and the routines/rowAccessPolicies IAM methods are explicit `501`
  stubs. Simplifications
  (synchronous DDL/DML jobs, serialized DML spans, atomic CTAS, immutable
  `getQueryResults` snapshots, documented divergences) are the cell reasons.
- **Metadata-only services** — `limited` REST cells: **Cloud SQL** (27 + 1 `unsupported` stub),
  **Compute Engine** (35 + 1), **Cloud DNS** (20 + 1), **Memorystore** (13). No control plane,
  VM/disk/network data plane, authoritative DNS server, or Redis data plane.
- **BigLake Iceberg REST catalog** — 14 cells `preview` (no official Discovery document).
- **Cloud Functions** — **v1 and v2 surfaces**. gcloud 586 (and current client SDKs) speak the
  v2 API, so `/v2/projects/{p}/locations/{loc}/functions` (and `operations`) route to the
  `functions` service and serialize the v2 shape (`state`, `buildConfig`, `serviceConfig`);
  `gcloud functions list` and `gcloud functions describe` pass. v2 runtime resolution works
  (`GET /v2/.../runtimes` + gRPC `ListRuntimes`), and v2 `generateUploadUrl` provisions a
  GCS-backed upload target (`gcf-v2-sources-*`, with a `storageSource` in the response) whose
  `uploadUrl` points at the emulator, so `gcloud functions deploy --gen2` runs end-to-end
  (upload → create → poll). Source referenced by a GCS object (v1 `sourceArchiveUrl` or v2
  `buildConfig.source.storageSource`) is fetched, persisted with a revision hash, and executed in
  Docker/K8s mode; each deploy bumps a persisted revision counter, so a deployed function renders
  the backing Cloud Run revision (`serviceConfig.revision`) with `allTrafficOnLatestRevision`. The
  v2 1st→2nd gen upgrade/traffic control plane (`setupFunctionUpgradeConfig`,
  `redirect`/`rollbackFunctionUpgradeTraffic`, `commitFunctionUpgrade`/`commitFunctionUpgradeAsGen2`,
  `abortFunctionUpgrade`, `detachFunction`) is served over REST with a persisted `upgradeInfo`
  state machine — REST-only in practice: the RPCs are documented in the Cloud Functions RPC
  reference, but the public `googleapis` proto and every generated client omit them.
  `Function.GetLocation` is served as the shared `google.cloud.location` common API (the service
  Discovery document does not enumerate it). The gRPC surface
  registers both `google.cloud.functions.v1.CloudFunctionsService` and
  `google.cloud.functions.v2.FunctionService` over one shared core/store; create/update/delete
  return inline `done:true` operations with typed `Any` metadata/response. v1 `CallFunction`
  (runtime invocation) is served over the shared cloud-neutral container executor on both
  transports: by default it runs the **GCP Functions Framework** contract (`POST /` on `$PORT`,
  source mounted at `/workspace`, `FUNCTION_TARGET`/`FUNCTION_SIGNATURE_TYPE`/`LOG_EXECUTION_ID`
  injected), and `JAISCLOUD_FUNCTIONS_EXECUTOR=lambda` selects the legacy Lambda-RIE contract.
- **gRPC** — a single cell (Logging `TailLogEntries`) remains `limited`, verified against the
  proto descriptors only. The explicit `Unimplemented` stubs are `unsupported` (see the
  `Unimplemented` list below); the rest of the gRPC surface is `ga` and verified with the
  official `cloud.google.com/go` clients against a live emulator. The conformance harness
  exercises **513** checks over those `ga` proto methods (Cloud Run 15,
  Container 34, Dataproc 35,
  Datastore 15, Eventarc 39, Firestore 18, Firestore Admin 27, Functions 20, IAM 16, IAM Credentials 4,
  KMS 35, Logging 42,
  Managed Kafka 21, Metastore 18, Monitoring 39, Operations 10, Pub/Sub 25, Resource Manager 11,
  Scheduler 8, Secret Manager 21, Service Usage 6, Storage 24, Tasks 20, Workflow Executions 4,
  Workflows 6, the rest one per method). The remaining `limited` cell is Logging `TailLogEntries` (a bounded store-poll with
  no deterministic conformance assertion); Secret Manager's Cloud SQL managed rotation
  (`RotateSecret`/`EnableManagedRotation`) is `ga` — the emulator records the managed-rotation
  config/status and stores the generated password as a version, but has no Cloud SQL data plane to
  apply it to (see README-GCP "Known Limitations"). Managed Kafka consumer groups are `ga`: with the opt-in broker mode the list/get/
  update/delete surface reads the live broker's group coordinator, so the hermetic harness asserts
  the no-broker shape (`NOT_FOUND` for an absent group) and the real-Kafka data plane is covered by
  the k3d gate (`tests/persistent_mode/gcp/managedkafka-broker`). Logging's gRPC `ConfigServiceV2` serves sinks, exclusions, buckets, views, links, log scopes and the CMEK/settings records, and
  `MetricsServiceV2` serves logs-based metrics (create/get/list/update/delete, with the descriptor
  `name`/`type`/`description` synthesized from the metric id/description and `metric_kind`/`value_type`
  immutable across updates); only `CopyLogEntries` remains an explicit `unsupported`
  `Unimplemented` stub (a cross-project log copy needs a per-bucket entry data plane the emulator
  does not model).
- **Other documented caveats** (functional, not cell states — see
  [README-GCP Known Limitations](../../README-GCP.md#known-limitations)): Firestore `ExecutePipeline` implements the read-only
  relational subset (`collection`/`collection_group`/`database`/`documents`/`literals` sources
  plus `where`, `sort`, `select`, `distinct`, `limit`/`offset`) and rejects other pipeline
  stages and unsupported expressions with `Unimplemented`; Firestore's `UpdateTime` and
  Datastore's entity `update_time` optimistic-concurrency tokens are kept strictly monotonic
  (per document / per entity) even under a frozen clock; Datastore transactions are single
  entity-group with read-set
  approximations, and its query engine models only kind/filter/offset/limit, so GQL projection,
  `ORDER BY`, and cursor bindings are parsed/ignored and `HAS ANCESTOR`/`CONTAINS`/`NOT` are
  rejected (the same limits the structured query surface has); **KMS destruction timing** — `DestroyCryptoKeyVersion` moves the version to
  `DESTROY_SCHEDULED` with a `destroyTime` (the documented 30-day default), and a lazy on-read
  promotion flips it to the terminal `DESTROYED` (recording `destroyEventTime`) once the window
  elapses; `Encrypt`/asymmetric/MAC on a scheduled version fail with `FAILED_PRECONDITION` and
  `DestroyCryptoKeyVersion` is idempotent on an already-scheduled/destroyed version. The
  CryptoKey response carries the 30-day `destroyScheduledDuration`; the per-key
  `destroy_scheduled_duration` override (and the org-policy minimum) is not modelled —
  the documented 30-day default applies. As with
  rotation, promotion runs on access (no background scheduler); KMS rotation schedules
  execute lazily on read (a due key rotates on its next `GetCryptoKey`/`ListCryptoKeys`/`Encrypt`,
  creating a new primary and advancing the schedule — there is no background scheduler); KMS
  `keyRings.delete` is **REST-only** — the Discovery declares `DELETE v1/{+name}` (an LRO) but
  the `google.cloud.kms.v1.KeyManagementService` proto declares no `DeleteKeyRing` RPC, so the
  gRPC surface has no such method — and it deletes only an **empty** ring (a ring that still holds
  a `CryptoKey` is `400 FAILED_PRECONDITION`), leaving the ring's name reusable because
  `RetiredResource` models deleted `CryptoKeys` only; Logging
  `TailLogEntries` is a bounded, at-most-once poll;
  Eventarc delivers Pub/Sub- and Cloud Storage-sourced events to `cloudFunction`, `cloudRun` and
  `httpEndpoint` destinations (fire-and-forget binary-mode CloudEvents POST, no retries; a `cloudRun`
  destination is forwarded through the Cloud Run runtime to the service's latest ready revision,
  honoring `path`, so it needs a ready revision and works without DNS; a Pub/Sub publish carries the
  push-delivery JSON, a GCS object finalize/delete the object-metadata body with source
  `//storage.googleapis.com/projects/_/buckets/{bucket}`; GKE/Workflows destinations are not
  delivered; delivery is exercised end-to-end on k3d by `make test-e2e-eventarc-k8s`, which asserts
  a published Pub/Sub message and a GCS object finalize reach a real HTTP sink with the right
  `ce-*` headers and body, and that `cloudRun` delivery lands through the run runtime); Managed
  Kafka is metadata-only by default
  (an opt-in docker/k8s/native broker mode stands up a real Redpanda endpoint behind `bootstrapAddress`,
  over which topic create/update/delete and ACL mutations are mirrored and consumer groups are read
  from its group coordinator — with no broker the list is empty and get/update/delete return
  `NOT_FOUND`; ACLs are installed on the broker but only enforced when its own
  `kafka_enable_authorization` is enabled, which is off by default; in k8s mode each cluster's
  broker Pod/Service live in a per-cluster namespace provisioned and torn down with the cluster
  through the shared `internal/k8shelpers` namespace seam, and the emulator falls back to the
  process-wide `JAISCLOUD_K8S_NAMESPACE` when namespace RBAC is unavailable; the
  shared `locations/{location}/operations` LRO path is disambiguated by host — a
  request whose first DNS label is `managedkafka` (as in `managedkafka.googleapis.com`)
  serves the service's own `GetOperation`/`ListOperations`, while the default host
  keeps that path on Cloud Workflows);
  Cloud Resource Manager serves the legacy v1 REST and v3 gRPC project surfaces over one core:
  a lightweight project registry persists created projects (create/get/list/delete/undelete,
  the metadata/search admin surface `update`/`move`/`search`, project IAM as metadata) while any
  uncreated id still synthesizes as ACTIVE, and project numbers stay deterministic — the
  org/folder *hierarchy* is not modelled (only the project's parent reference is stored and
  reparentable via `MoveProject`), and a project etag rotates on update/move with a stale etag
  rejected `ABORTED`; billing/quota, real project-number allocation, and IAM enforcement are not
  modelled;
  Dataproc `Reset` does not drain in-flight Spark job goroutines, and a Dataproc gRPC
  `SubmitJobAsOperation` completes inline in the default mock executor but cannot be `Wait`-polled
  while a k8s-executor job is still in flight (the generic `google.longrunning.Operations` stub
  does not read the Dataproc store; the REST `operations.get` path does); Metastore's Hive Thrift
  serving plane implements databases/tables/partitions/locks with one catalog per Service: each
  Service gets its own port (a request's `port` is honored — the API field is Optional and real
  Metastore echoes it; otherwise `--hms-port`+1 and upward), and its `port`/`endpointUri` name the
  listener that serves only its catalog, so two Services (same project or different
  projects/locations) do not collide on a database name, each owns its `default`, and Iceberg
  commit locks are per catalog. The Thrift protocol carries no service identity, so the port is
  the catalog selector: a requested port must be free and must not be the base `--hms-port`
  (duplicate `ALREADY_EXISTS`, reserved base `INVALID_ARGUMENT`), and an update with
  `updateMask=port` moves the listener with it.
  The base `--hms-port` (:9083) keeps serving the legacy shared catalog for clients that name no
  Service (the AWS Glue Data Catalog analogue: one catalog per account+region), and a pre-NF32

- **Cloud Monitoring alert evaluation** — the background worker evaluates
  `condition_threshold` and `condition_absent`. `condition_matched_log`, MQL, PromQL, and SQL
  conditions are stored but never evaluated (they never fire). For `condition_absent`, a metric
  that has never produced a measurement does not fire (matching real Cloud Monitoring), the absent

- **Cloud Scheduler** — job CRUD plus a real cron engine that fires `httpTarget` and
  `pubsubTarget` jobs on the emulator clock (advance `/_jaiscloud/clock`, or use
  `POST /_jaiscloud/scheduler-tick`, to fire deterministically). `httpTarget` delivery performs the
  documented HTTP request (method/headers/body, `X-CloudScheduler*` headers) and `pubsubTarget`
  reuses the Pub/Sub publish path (fan-out to subscriptions). `appEngineHttpTarget` is stored and
  echoed but never delivered (no App Engine router) — its attempts are recorded as `Unimplemented`
  and are terminal: the job is attempted once, the status is recorded, no retries are consumed and
  the job waits for its next cron slot.
  English-like schedules ("every 5 minutes") are not parsed (unix-cron plus `@` descriptors only);
  `oauthToken`/`oidcToken` attach a synthetic emulator-local bearer token, not a real Google token.
- **Cloud Tasks** — the v2 control plane plus a dispatch engine: queue CRUD plus
  `pause`/`resume`/`purge`, queue IAM (`getIamPolicy`/`setIamPolicy`/`testIamPermissions` over the
  shared policy store — metadata only, authorization is not enforced), and task CRUD plus the
  `tasks:buffer` (REST-only) and `tasks:batchCreate`/`tasks:batchDelete` (both surfaces). `httpRequest`
  (url/method/headers/body/oauth|oidcToken) and `appEngineHttpRequest` are accepted and echoed. The
  engine delivers due `httpRequest` tasks on the emulator clock (advance `/_jaiscloud/clock`, or use
  `POST /_jaiscloud/tasks-tick`, to fire deterministically) with per-queue rate limits and
  exponential-backoff retries, attaching the documented `X-CloudTasks-*` headers; a 2xx target
  response deletes the task, a failure retries until the attempt's effective
  `retryConfig.maxAttempts`/`maxRetryDuration` is exhausted — a task-level `retryConfig` overrides
  the queue's wholesale (never a field merge), and a zero `maxAttempts` means "unspecified" (the
  documented default of 100), not "inherit the queue". A task is deleted once it has been retained
  for 31 days past its `scheduleTime` (the maximum task retention), on the dispatch tick and before
  the due check; reads never delete. `RunTask` / REST `:run` forces a synchronous attempt that
  bypasses pause and rate limits. `appEngineHttpRequest` is never delivered (no App Engine router) —
  the task is attempted once, that attempt is recorded as `Unimplemented`, and the task is deleted
  immediately instead of retried, so the failure is terminal and never a silent drop after a retry
  storm. **`tasks:buffer` is REST-only**: the REST Discovery
  document declares it, but the `google.cloud.tasks.v2.CloudTasks` proto declares no `BufferTask`
  RPC (the generated clients have no such method), so the gRPC server does not expose one. Because
  the emulator models no queue-level `httpTarget` (the field real Cloud Tasks resolves a buffered
  task's URL from), a `BufferTaskRequest` must carry the full task to create; a body-only request is
  `INVALID_ARGUMENT`, which is the error real Cloud Tasks returns for a queue without an HTTP
  target. `locations.getCmekConfig`/`updateCmekConfig` are served over both REST and gRPC and are
  **metadata only**: the KMS key name is shape-validated
  (`projects/*/locations/*/keyRings/*/cryptoKeys/*`), stored per project+location, echoed back and
  cleared by an empty `kmsKey`, but task payloads are stored in plaintext — there is no at-rest
  encryption. Real `oauthToken`/`oidcToken` token minting is not modelled (a synthetic
  emulator-local bearer token is attached instead). The engine polls once per second, so sustained
  throughput is bounded by `maxBurstSize` per second rather than `maxDispatchesPerSecond`.
- **Google Kubernetes Engine (GKE)** — a metadata-only mock of the v1 control plane
  (`container.googleapis.com`), REST + gRPC: cluster `create`/`get`/`list`/`delete` plus the GKE
  `Operation` records they return (`get`/`list`), node-pool `create`/`get`/`list`/`delete`/`update`
  and the node-pool setters (`setAutoscaling`/`setManagement`/`setSize`/`rollback`), and the cluster
  update/setter/rotation RPCs (`update`/`updateMaster`/`setAddons`/`setLegacyAbac`/`setLocations`/
  `setLogging`/`setMonitoring`/`setNetworkPolicy`/`setMaintenancePolicy`/`setMasterAuth`/
  `setResourceLabels`/`startIpRotation`/`completeIpRotation`), served over both the REST surface and
  the native gRPC `google.container.v1.ClusterManager` transport. Every mutating call returns a GKE
  `Operation` (correct `operationType`, and `DONE` by default) and the recorded fields are echoed on
  read-back. The three list methods (`clusters`, `nodePools`, `operations`) return the complete
  collection: the Discovery document declares no `pageSize`/`pageToken` on them and their response
  schemas carry no `nextPageToken`, so a stray paging parameter is accepted and ignored, as real GKE
  ignores it, and REST and gRPC return the same shape. GKE's concurrent-operation rules sit behind an opt-in simulated in-flight window
  (`JAISCLOUD_GKE_OPERATION_WINDOW`; unset keeps every operation instant-`DONE`): while a window is
  open the returned operation is `RUNNING` with no `endTime` and settles to `DONE` one window after
  it started, a mutating call that overlaps an operation still running on its target is the 400
  `FAILED_PRECONDITION` real GKE answers — "Cluster is running incompatible operation
  <operation-id>" — and because the granularity is one operation per node pool, different pools of
  a cluster still mutate in parallel while a cluster-level change waits for all of them.
  `JAISCLOUD_GKE_CONCURRENT_OPERATIONS` caps the operations in flight per project/location and
  rejects the next mutation with 429 `RESOURCE_EXHAUSTED`. With no window open nothing is ever in
  flight, so both rules are inert. A
  cluster is an instantly-`RUNNING` stored record (default master version, `network`/`subnetwork`);
  a create that carries inline `nodePools` materializes those pools in the same call (each with its
  canonical `selfLink`, `RUNNING` status, the cluster's node version and its `initialNodeCount`
  node count) through the same materialiser `nodePools.create` uses, so the two paths cannot assign
  different fields; a name repeated inside one create request is `400` (`duplicate node pool name:
  <name>`, nothing stored), while `nodePools.create` with a name already taken on the cluster is the
  `409` conflict that call answers — a request-scope distinction stated in one place in the core;
  a create that carries none gets the generated `default-pool` built from the legacy
  `initialNodeCount`/`nodeConfig` pair (Discovery: the config "will be used to create a NodePool
  object with an auto-generated name"), so that pool gets the same `selfLink`/`RUNNING`
  status/version/node count and the caller's `nodeConfig` as its `config`. Combining `nodePools`
  with either legacy default-pool field is the 400 real GKE returns — `initialNodeCount > 0` gets
  "It's invalid to specify both cluster.initial_node_count and a node pool. Please only provide a
  node pool.", a `nodeConfig` gets the same sentence with cluster.node_config (it wins when both are
  set), and a zero `initialNodeCount` means "no default node pool" and is accepted, all captured
  against real GKE in [`gke-create-pool-conflict.md`](gke-create-pool-conflict.md). A negative
  cluster-level `initialNodeCount` on a request with no `nodePools` is the 400
  "Cluster.initial_node_count must be zero or higher."; with pools it is accepted and ignored, as
  on real GKE. On read, a
  cluster-level `nodeConfig` is rendered from the first node pool's `config` (Discovery: "this field
  will be populated with the node configuration of the first node pool"), so the legacy create shape
  round-trips, and every node pool's own `config` is fully populated even when the create named none
  — `e2-medium`, `COS_CONTAINERD`, a 100 GB `pd-balanced` boot disk, the `default` service account
  and the six default OAuth scopes, captured in

  caller used — a short name, a project-relative partial resource name or a Compute self-link, which

  while `masterAuth.clusterCaCertificate` stays empty because the mock mints no CA.

  `projects/{p}/locations/{l}/keyRings/{r}/cryptoKeys/{k}` form, or an accelerator entry with no
  type or a non-positive count, is `400` (the form is the only thing enforced: the emulator has no
  GPU catalog to validate an accelerator type against, and no GPU or disk behind the fields).

  container API documents no `projects.locations.get`/`list` method (neither Discovery nor the

  location-scoped), so neither is synthesized. The served version surface is `v1` **and**

  the real Spark SQL CLI, with `queryFileUri`/`queryList.queries`/`jarFileUris`/`properties`/`scriptVariables`
  mapped to `-f`/`-e`/`--jars`/`--conf`/`--hivevar`), and every other job type
  (`hadoopJob`, `hiveJob`, `pigJob`, `prestoJob`, `trinoJob`, `flinkJob`) is fail-loud —
  the job is created and immediately set to `ERROR` with a "not supported by the emulator" detail
  (`hiveJob` in particular is not approximated over Spark, since HiveQL is a superset of Spark SQL;
  a user who needs Hive attaches their own HiveServer2/Spark to the Hive Metastore Thrift plane `:9083`,
  which serves the catalog while the emulator remains metadata-not-engine);
  and `driverOutputResourceUri`/`driverControlFilesUri` resolve to real GCS objects captured from
  the client-mode driver (stdout/stderr, byte-capped — staged only at termination, so a long-running
  job's URI resolves to nothing until it is cancelled or the driver exits);
  a long-running/streaming job (detected from `spark.sql.streaming.*`/`spark.streaming.*` `properties`
  — an emulator approximation, since real GCP has no streaming marker) stays `RUNNING` in mock mode
  until cancelled, and `Job.scheduling` (`maxFailuresPerHour`/`maxFailuresTotal`, docker/k8s executor mode)
  restarts a failed driver while within both limits and not thrashing, with success strictly driver
  exit `0` (restart counters are per-process and the per-hour window is a fixed-window approximation);
  the Docker Spark executor (`JAISCLOUD_SPARK_EXECUTOR_MODE=docker`) runs each job as a one-shot
  `spark-submit --master local[*]` container on the local Docker daemon with the same GCS-connector
  wiring and driver-output staging as k8s, reaping the container on cancel/cluster-delete/reset;
  the Kafka-source Structured Streaming path is verified against the live opt-in Managed Kafka broker
  by `make test-dataproc-streaming-kafka` (the `spark-sql-kafka` connector is supplied through
  `jarFileUris`, since it is not bundled in the deployed Spark image; checkpoint and
  checkpoint-log consumer offsets are asserted to advance before cancel reaps the driver);
  Dataproc `ListClusters` ignores
  `filter`/`clusterName`, while `ListJobs` honors `clusterName`,
  `jobStateMatcher` and a bounded `filter` subset (`status.state`, `labels.<key>`, `insertTime`),
  and
  `ListOperations` is not exposed (pollable `operations.get` is served);
  Eventarc delivers a Pub/Sub- or Cloud Storage-sourced event to a trigger's `cloudFunction`,
  `cloudRun` or `httpEndpoint` destination with a fire-and-forget binary-mode CloudEvents POST (no
  retries; a `cloudRun` destination is resolved to the service's latest ready revision through the
  run runtime and honors `path`; a GCS object finalize/delete is matched by its `type`/`bucket`
  eventFilters and carries the object-metadata body; GKE/Workflows destinations are not delivered). The
  advanced surface — message buses, enrollments, pipelines, Google API sources, channel connections
  and the per-location Google channel config — is served as control-plane metadata CRUD on both
  transports (a message bus / enrollment / pipeline records the event-routing graph but the emulator
  runs no bus/pipeline delivery engine; see Known Limitations). The
  Eventarc gRPC proto defines no IAM RPCs, so Trigger/Channel/advanced-resource IAM is served through the shared
  `google.iam.v1.IAMPolicy` router. The REST Channel render carries an emulator-internal `etag`
  used for optimistic concurrency; real Eventarc's `Channel` has no `etag` field, so the gRPC
  surface never exposes it. Managed Kafka `UpdateCluster`/`UpdateTopic`/`UpdateAcl`
  merge the supplied `update_mask` fields but ignore the mask itself. Functions gRPC
  create/update/delete return inline `done:true` operations that are never persisted (so they
  cannot be polled across a process); the REST `operations.get` path synthesizes a done operation;
  v2 `ListFunctions` ignores `filter`/`orderBy` and `GenerateUploadUrl` ignores
  `kmsKeyName`/`environment`.

## 6. CI gates

The real jobs in [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) and what each gates:

| job | what it proves |
| --- | --- |
| `test-gcp-unit` | race-tested unit tests for `internal/gcp/...` plus the shared Spark/K8s/platform/executor packages, the `tools/gcpstatus` dev-tool tests, the **behavioural-coverage gate** (`make gcp-status-behavioral-gate` — every `ga` service has an official-client suite or a reasoned exemption), the **behavioural-depth gate** (`make gcp-status-depth-gate` — every `ga` service records each of `p2`–`p5` as present or dated-exempt), and the **statement-coverage ratchet** (`make test-gcp-coverage` — no `internal/gcp` package drops below its committed per-package floor) (no services required) |
| `test-gcp-integration` | builds and boots the binary (REST `:8080`, gRPC `:8081`), then runs the raw-HTTP integration suite and **18** official-SDK test modules |
| `test-gcp-conformance` | records a fresh wire transcript, validates every response (and the error envelope) against the Discovery schemas — failing on any high-severity divergence — runs the gRPC message-level suite, the REST↔gRPC cross-transport parity suite, and the gcloud CLI suite, fails if the fidelity matrix is stale, and fails if the **field-coverage inventory** (`make check-gcp-field-coverage`) has an unclassified or stale field or a `roundtrip` row whose evidence pointer no longer resolves |
| `test-gcp-persistence` | with a Postgres service container, runs the `gcp_persistence` suite proving state survives process restarts |
| `test-aws` | AWS + shared unit/integration tests (`internal/gcp/...` excluded — the GCP package must never import `internal/aws/`) |
| `docker-build` | the shared `Dockerfile` builds for `linux/amd64` (no push) **for both clouds** (`CLOUD=aws` on 4566 and `CLOUD=gcp` on 8080), then runs each image: the `VERSION` build arg reaches `version`, `/_jaiscloud/health` answers on the cloud's REST port, and `/ui/` answers 200 on 4567 with `--ui` (proves the UI build stage + `-tags ui`) |
| `release-config` | `goreleaser check` plus a `goreleaser release --snapshot` (no docker, no publish) and `make test-release`: the six `jaiscloud-gcp` archives, the deb/rpm packages, one version across `dist/`, `jaiscloud-gcp version` reporting the archive version, and the archive binary serving REST + the embedded console |

The conformance job is the wire-contract gate; integration and persistence prove the client
surface and durability. The behavioural-coverage gate (in `test-gcp-unit`) is the
**behavioural-depth** gate: it derives `service → suite → transport` from the registry +
fidelity matrix + `tests/integration/gcp` tree and fails if any `ga` service has no
official-client suite and no reasoned exemption (`docs/gcpstatus-coverage-exemptions.yaml`).
The committed per-service map lives in
[`docs/gcp/testability.md` §9](testability.md#9-behavioural-suite-contract--the-ga-definition-of-done-gated).
`test-gcp-unit` also runs the `p2`–`p5` depth gate (§10) and the statement-coverage ratchet
(§11): `make test-gcp-coverage` profiles `internal/gcp/...` and fails if a measured package
drops below its committed floor in `docs/gcp-coverage-floor.yaml`.
`make test-all-gcp` aggregates it with unit + integration + conformance (`ga-check`) + persistence.

Outside PR CI, `make test-gcp-load` is the **load / concurrency gate**: it boots an ephemeral
emulator with `--metrics` and drives GCS object PUT/GET, Pub/Sub publish + fan-out and Firestore
commits at `-c 100`, failing on any 5xx or on goroutine/memory growth past a threshold. It runs
locally and on the weekly/manual [`gcp-load.yml`](../../.github/workflows/gcp-load.yml) workflow
(§12 of [`docs/gcp/testability.md`](testability.md#12-load--concurrency-gate--the-hot-path-soak-local--nightly)).

Also outside PR CI, `make test-gcp-mutation PKG=…` is the **assertion-strength** measurement: it
runs the pinned `go-mutesting` over one target (a package, or a single file within one — `PKG=
./internal/gcp/adapter/jsoncodec.go`), replays the target package's own tests against each
mutant, and writes a mutation score + surviving-mutant report to `bin/gcp-mutation-report.json`.
`make test-gcp-mutation-ratchet PKG=…` runs the same spike and then gates the score against the
committed per-target floor in `docs/gcp-mutation-floor.yaml` (`make test-gcp-mutation-update`
ratchets a floor up, refusing to lower one without `ALLOW_LOWER=1`). It is a local ratchet, not a
per-PR gate (a full package run is minutes)
(§13 of [`docs/gcp/testability.md`](testability.md#13-mutation-testing--assertion-strength-the-local-spike)).

The Terraform suite has its own boundary statement:
[`terraform-compatibility.md`](terraform-compatibility.md) records what a green
Terraform/OpenTofu gate proves and what it does not (authz, quotas, org
hierarchy, data planes). The static coverage inventory is a PR check; the apply
matrix, the lifecycle/pattern gates and the TF6 differential replay run in
`terraform-nightly.yml`, and the differential is recorded from real GCP by a
credentialed operator step (`make record-gcp-terraform-differential`).

## 7. How to verify

One aggregate gate — deterministic, offline plus client-conformance:

```bash
make ga-check
```

It runs `check-gcp-fidelity-matrix`, `test-gcp-wire-conformance`, `test-gcp-grpc-conformance`,
`test-gcp-rest-grpc-parity` and `test-gcp-gcloud-conformance` (the client suites build and self-start
an ephemeral emulator; `gcloud` self-skips if it is not on `PATH`), then prints what the
infrastructure-backed gates need.

The following are also required before a release (they need real clients, Docker,
Postgres, or k3d, so they are not part of `ga-check`):

```bash
GCP_DIFFERENTIAL_STRICT=1 make test-gcp-differential   # 0 open divergences vs real-GCP goldens
make test-gcp-python-conformance                       # Python google-cloud-* clients
make test-e2e-gcp-persistence                          # Postgres mode survives restarts
make test-e2e-lakehouse-k3d                            # real Medallion Spark ELT on k3d
make test-e2e-iceberg-gcp                              # Iceberg-on-Hive (Docker Spark + HMS Thrift)
```

The `ga-check` gates and the Postgres persistence job run on every PR as the `test-gcp-*` CI jobs in §6. The fidelity check
consumes the generated conformance report under `tests/gcpconformance/testdata/report/`
(gitignored); `check-gcp-fidelity-matrix` regenerates it from the committed transcript via
`test-gcp-wire-conformance`, so `make ga-check` works on a fresh clone with no setup. (CI, by
contrast, records the transcript against a live emulator first — see §6.) The gRPC report,
`tests/gcpconformance/grpc/testdata/report/report.json`, is committed as the evidence for the
`ga` gRPC cells; the gRPC suite overwrites it with a fresh run on CI before the matrix is
generated.

Client-level detail — SDK modules, gRPC check counts and the gcloud command set — is in §4.

## 8. Accepted risks

Identity authorization is not enforced; a cryptoKey's IAM policy gates its crypto operations
default-permissively; long-running operations complete synchronously by default; the
metadata-only tier has no data plane; and any Yellow/Red service or permission-sensitive path
still needs a real-GCP smoke run. The reasoning behind each:

| Decision | Resolution |
| --- | --- |
| **Release posture** | Ship as a **tiered supported surface**. `ga` is a wire-contract claim; the fidelity matrix is the published contract. Yellow/Red services are not claimed as behaviourally complete. |
| **Authz enforcement** | **Identity authz documented, not enforced — accepted risk.** No optional enforcement mode is shipped (it would be new service behaviour). Identity IAM policies are metadata and are not checked at request time; this matches the AWS implementation, which likewise never enforces identity policies. The one resource-policy hook is Cloud KMS: a cryptoKey's IAM policy gates its crypto operations (`encrypt`/`decrypt`/`asymmetricSign`/`asymmetricDecrypt`/`macSign`/`macVerify`/`getPublicKey`), **default-permissive** — a key with no policy allows every operation, and only a policy scoped to roles that omit the required permission returns `403 PERMISSION_DENIED` — mirroring the AWS KMS emulator's key-policy check. `iam`/`resourcemanager`/`serviceusage` remain "Shape only"; permission-sensitive paths **must** be smoke-tested against real GCP before being relied on. |
| **LRO realism** | **Documented synchronous completion — accepted risk, narrowed by an opt-in mode.** By default the emulator completes LROs inline (`done: true`) and the create/update/delete response is unchanged; both shapes stay covered (the gRPC conformance suite asserts the inline envelope, and the real-GCP differential goldens capture the real, eventually-consistent envelopes). With `JAISCLOUD_LRO_MODE=async` (in-flight window via `JAISCLOUD_LRO_DELAY`, default `250ms`) `workflows`, `functions`, `metastore`, `managedkafka`, `dataproc` and `serviceusage` return operations in flight and settle them lazily when a client polls `operations.get`. In that mode the generic `google.longrunning.Operations` service is registry-backed for the services that persist operations: `cancel`/`delete` act on Service Usage's persisted operations (`cancel` is a validate-and-no-op, since the emulator does not model cancellation), Cloud Functions v2 serves a location-scoped `list` that honors the AIP-160 `done`/`name` `filter`, Cloud Workflows' operations list evaluates `done`/`name`/`state`/metadata filters with the shared operations compiler (AND/OR/NOT, implicit AND and parentheses; an unsupported filter is `INVALID_ARGUMENT`), and an operation name no service owns is `NOT_FOUND` (real GCP semantics) rather than the lenient terminal stub. The default (sync) keeps the terminal stub and the no-op delete/cancel that synchronous SDK init paths rely on. The opt-in mode is a local-testing affordance, not a fidelity claim (see [`testability.md`](testability.md)); code that assumes async readiness must still be tested on real GCP. Independently of the mode, `google.longrunning.Operations` is endpoint-scoped: a request addressed at a service's own endpoint (the HTTP/2 `:authority` first label, e.g. `metastore.localhost` / `metastore.googleapis.com`) is served only by that service, so `ListOperations(parent=…)` returns its operations exactly as real GCP serves Operations per service host — for every LRO-owning service (Managed Kafka, Metastore, Run, Cloud Functions, Dataproc, Workflows; Service Usage and Resource Manager in async mode); a request to an unregistered endpoint keeps the shared name-based `Get`/`Wait` and an empty list (never another service's operations). |
| **Throttle/quota injection** | **Opt-in, emulator-only failure injector — accepted gap.** No real quota plane is modelled and the project quota/account-settings API is absent (FD11); by default no path is throttled. An opt-in injector (`JAISCLOUD_GCP_THROTTLE`, default `off`) refuses matching REST + gRPC requests before dispatch with a retryable `429 RESOURCE_EXHAUSTED`/`503 UNAVAILABLE`, a `Retry-After` header and a `google.rpc.RetryInfo` detail, so client backoff/retry/idempotency code runs locally. The policy can be armed/retuned/disarmed mid-run via `POST /_jaiscloud/throttle` (no restart). It injects synthetic failures, not real quota values; real quota behaviour must still be tested on real GCP (see [`testability.md`](testability.md)). |
| **Metadata-only tier** | **Declared control-plane-only.** `compute`, `cloudsql`, `memorystore` and `clouddns` are `limited`/metadata-only — resource records + `get`/`list`, no data plane. Their data planes are explicitly out of scope. |
| **Yellow/Red real-GCP smoke** | **Defined and required for trust.** A local green run is not evidence for a Yellow/Red service or an authz-sensitive path; those must be validated against real GCP. The repo's mechanism is the differential recorder (`make record-gcp-differential`, ADC + a real project) plus service-specific smoke tests; the recorded goldens then gate every PR through `GCP_DIFFERENTIAL_STRICT=1 make test-gcp-differential`. This stage is credentialed and therefore not part of CI. |
| **Emulator-only affordances** | **Policy, not a gate.** Production code must not depend on `/_jaiscloud/*`, reset/snapshot, lenient validation, absent authz, or the frozen clock (see [`testability.md`](testability.md) §8). |

Accepted-risk summary: the emulator is **wire-conformant within the declared matrix**; it is **not**
a substitute for real GCP on authz, LRO timing, quotas/throttling, or the data plane of any
`limited`/`preview` service.
