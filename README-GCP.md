# JaisCloud for GCP

> **Early Development Notice**
> `jaiscloud-gcp` is published from **`v0.1.1`** onward: that release carries the GCP binary, archives, deb/rpm packages, Homebrew cask, Scoop manifest and container image alongside the AWS ones. GCP services are tiered — some are `preview` or `limited` in the [fidelity matrix](docs/fidelity/fidelity-matrix.md), some operations may have incomplete implementations, behavioural differences from real GCP, or known bugs. What the emulator's fidelity matrix actually promises is the [wire contract](docs/gcp/wire-contract.md) ([§1](docs/gcp/wire-contract.md#1-what-ga-means-in-the-matrix) for what `ga` means, [§8](docs/gcp/wire-contract.md#8-accepted-risks) for the accepted risks) — and those two sections are the release notes of record. See [Known Limitations](#known-limitations) below, and please [open a GitHub issue](https://github.com/jaisrajms/jaiscloud/issues) for anything not already listed there.

**JaisCloud — a free GCP emulator for developers and CI.** It implements real GCP wire protocols — both the REST/JSON APIs and the native gRPC APIs official Google clients use (Storage, Pub/Sub, Firestore, Datastore, KMS, Secret Manager, Logging, Monitoring, Dataproc, Eventarc, Functions, Managed Kafka, Metastore, Service Usage, Workflows, Workflow Executions, Resource Manager, IAM, Cloud Scheduler, Cloud Tasks, GKE, Cloud Run) — no SDK shims, no proxy rewrites. Point an official Google client library at it and it works. Where real GCP is REST-only (Compute, Cloud SQL, Cloud DNS, BigQuery, BigLake Iceberg, Memorystore), only REST is exposed; each service row below states its transports.

**One binary per cloud.** `jaiscloud-gcp` is fully self-contained — no `--cloud` flag, no shared runtime with `jaiscloud-aws`. See the [main README](README.md) for the project-wide picture (AWS is the reference implementation; this document covers the GCP binary specifically).

## Supported GCP Services

| Service | Transport | Notes |
|---|---|---|
| Cloud Storage (GCS) | REST + gRPC v2 | Buckets, objects, resumable/multipart uploads, CMEK, CSEK, the project storage service account (`projects.serviceAccount.get`) and HMAC keys (`projects.hmacKeys.*`) |
| Cloud Pub/Sub | REST + gRPC | Topics, subscriptions, snapshots, seek, push/pull delivery, ordering keys, DLQ, exactly-once delivery (pull); topics carry the full mutable field set (CMEK, message storage policy, schema settings, message transforms, ingestion sources) through create/get/update masks — transforms and ingestion are store-only, see [Known Limitations](#cloud-pubsub-topic-fields-are-stored-and-served-not-run) |
| Secret Manager | REST + gRPC | Secrets, regional secrets, versions, rotation, CMEK envelope encryption |
| Cloud KMS | REST + gRPC | Key rings, crypto keys/versions, symmetric + asymmetric, rotation, key import + HSM/EKM trusted wrapping + KEM decapsulation; crypto ops honor a default-permissive cryptoKey IAM policy |
| Cloud IAM | REST + gRPC | Service accounts and keys (create, list, get, **upload** a caller-provided public key, disable/enable, delete), `signBlob`/`signJwt`, and the IAM Service Account Credentials API (`generateAccessToken`/`generateIdToken`); every method resolves the account through the registry, so a missing service account is `NOT_FOUND`, and the delegation chain is validated (see [Known Limitations](#iam-service-account-credentials-require-the-account-and-validate-the-delegation-chain)). The gRPC `google.iam.admin.v1.IAM` surface mirrors the service-account/keys/policy RPCs, and gRPC `IAMPolicy` covers project/resource policies — the role catalog is not modelled and authz is not enforced |
| Service Usage | REST + gRPC | Project service enable/disable/get/list (`services.enable`/`disable`/`batchEnable`/`batchGet`), `filter=state:ENABLED` |
| Cloud Resource Manager | REST + gRPC | Project lifecycle (create/get/list/delete/undelete), admin (`update`/`move the parent reference`/`search`) + project-level IAM policy (`getIamPolicy`/`setIamPolicy`/`testIamPermissions`); unknown ids still synthesize as `ACTIVE`, project numbers are deterministic, the org/folder hierarchy itself is not modelled, and a project etag rotates on update/move — authz not enforced |
| Cloud Billing | REST | Only the project↔billing-account association: `projects.getBillingInfo`/`projects.updateBillingInfo` over the `ProjectBillingInfo` singleton (an untouched project reads the four-field default with an empty `billingAccountName` and `billingEnabled: false`; the write stores the full `billingAccounts/{account}` resource name and derives `billingEnabled`, a non-resource-name value is `400`), an always-empty `billingAccounts.list`, and a default-permissive `billingAccounts.testIamPermissions` echo. That is what Terraform's `data "google_project"`/`resource "google_project"` and the `terraform-google-pubsub` module need. The billing-account catalog/sub-accounts, the services/SKU catalog and the billing-account IAM policy methods are not modelled (they fail loud with `501`), and authz is not enforced — see [Known Limitations](#known-limitations) |
| Cloud Scheduler | REST + gRPC | Cron jobs (`jobs` CRUD + `pause`/`resume`/`run`); a real cron engine fires `httpTarget`/`pubsubTarget` jobs on the emulator clock — see [Known Limitations](#known-limitations) |
| Cloud Tasks | REST + gRPC | Queues (`queues` CRUD + `pause`/`resume`/`purge`, queue IAM) and tasks (`tasks` CRUD + `batchCreate`/`batchDelete`, REST also `buffer`), plus the location CMEK config; a dispatch engine delivers due `httpRequest` tasks with rate limits and retries, and `run` forces an attempt — see [Known Limitations](#known-limitations) |
| Cloud Firestore (Native mode) | REST + gRPC | Documents, transactions, structured/aggregation/partition queries, composite indexes, `BatchWrite`/`Write`/`Listen` streaming, pipelines (read-only subset); the Admin control plane (databases, collection-group fields, backup schedules, backups, user creds, change streams) over REST (`firestore.googleapis.com/v1/…`) and gRPC (`google.firestore.admin.v1.FirestoreAdmin`; change streams are REST-only — the admin proto declares no ChangeStream RPC); a database's `cmek_config` is validated at create against the KMS store (shape, existence, same location, an `ENCRYPT_DECRYPT` key) and its `active_key_version` is derived per response from the key's `ENABLED` versions (create-only — a key change is `INVALID_ARGUMENT`) |
| Cloud Datastore mode | REST + gRPC | Entities, queries (structured + GQL), ID allocation, `ReserveIds`/`RunAggregationQuery`, transactions (read-set OCC) — see [Known Limitations](#known-limitations) |
| Cloud Functions (v1 + v2) | REST + gRPC | Deploy (LRO), invoke via `:call` or the deployed HTTPS trigger URL (mock echo by default; Docker/K8s run the **GCP Functions Framework** contract — `POST /` on `$PORT`, source at `/workspace` — with the legacy Lambda-RIE contract behind `JAISCLOUD_FUNCTIONS_EXECUTOR=lambda`), locations, source URLs, v2 `serviceConfig` instance/concurrency config (`minInstanceCount`/`maxInstanceCount`/`maxInstanceRequestConcurrency`/`availableCpu`, validated, surfaced + admission-enforced) and `ingressSettings` |
| Cloud Workflows | REST + gRPC | Workflow definitions + executions, real YAML expression engine; LROs complete synchronously by default, with an opt-in async mode (`JAISCLOUD_LRO_MODE=async`) |
| Cloud Dataproc | REST + gRPC | Clusters (GCE- or GKE-`virtualClusterConfig`-shaped; a GKE virtual cluster's node pools are reconciled against the emulated GKE API and read back through `container.v1`) + jobs + workflow templates (`WorkflowTemplate` CRUD; `instantiate`/`instantiateInline` execute the inline DAG over the job core) + resource-level IAM on clusters, jobs and workflow templates (`google_dataproc_{cluster,job}_iam_*`), **real Spark execution** in Docker/K8s executor mode (same model as AWS EMR); pollable async cluster/job long-running operations; `Job.scheduling` restart policy (k8s restart loop) and long-running/streaming job lifecycle; `SparkJob`/`PySparkJob` `jarFileUris` → `spark-submit --jars`; real driver output/control files in GCS; optional Metastore attachment; optional cluster/job lifecycle events on Pub/Sub. **Coverage:** 96 of 136 published Dataproc v1 REST methods are served — 32 have a cell, 62 are served only by the documented Serverless `501`/`UNIMPLEMENTED` stub, and 40 have no registered route (autoscaling policies, `nodeGroups.*`, `clusters.repair`/`injectCredentials`, `operations.*` IAM, location-scoped workflow templates); the gRPC surface is 36 of 36 served, 22 graded (the 14 Serverless RPCs answer `UNIMPLEMENTED`). See the [fidelity matrix coverage](docs/fidelity/fidelity-matrix.md#coverage) — a cell is a grade, not the whole published API |
| Dataproc Metastore | REST + gRPC | Control-plane CRUD (services/backups/metadata-imports) + Hive Metastore Thrift serving plane, **one catalog per Service** on its own port (`endpointUri`/`port` are real routing addresses; the base `:9083` serves the legacy shared catalog); databases/tables/partitions/locks served (including the Hive-3.x `get_table_meta` and `alter_table_with_cascade` paths), see [Known Limitations](#known-limitations) |
| BigLake Iceberg REST Catalog | REST | `org.apache.iceberg.rest.RESTCatalog` surface mounted at `/iceberg/` — namespaces, tables, atomic `CommitTableRequest` requirements/updates, see [Known Limitations](#known-limitations) |
| Managed Kafka | REST + gRPC | Clusters/topics/consumer groups with an optional real broker behind `JAISCLOUD_KAFKA_BROKER_MODE` — see [Known Limitations](#known-limitations) |
| Google Kubernetes Engine (GKE) | REST + gRPC | Metadata-only v1 control-plane mock: clusters `create`/`get`/`list`/`delete` plus the GKE `Operation` records they return (`get`/`list`), node-pool `create`/`get`/`list`/`delete`/`update` with the `:setAutoscaling`/`:setManagement`/`:setSize`/`:rollback` setters, and the cluster update/setter/rotation RPCs (`update`/`:updateMaster`/`:setAddons`/`:setLegacyAbac`/`:setLocations`/`:setLogging`/`:setMonitoring`/`:setNetworkPolicy`/`:setMaintenancePolicy`/`:setMasterAuth`/`:setResourceLabels`/`:startIpRotation`/`:completeIpRotation`/`:cancel`); instant-`RUNNING` mock clusters whose read carries the nested messages real GKE always returns (`legacyAbac`/`networkConfig`/`shieldedNodes`/`defaultMaxPodsConstraint`, so the `hashicorp/google` provider's `google_container_cluster` works), host (`container.*`) + `/container` prefix routing around the Managed Kafka path collision, and the native gRPC `ClusterManager` transport — no real Kubernetes control plane. **Coverage:** 31 of 71 published container.v1 REST methods are served (40 have no registered route — the `projects.zones.clusters.*` twins the codec does not serve, the location-scoped stubs such as `checkAutopilotCompatibility`/`getJwks`, and `listUsableSubnetworks`); the gRPC `ClusterManager` surface is 37 of 37 served and graded (30 `ga`, 7 explicit `unsupported` stubs). | BigQuery | REST | Datasets/tables/jobs/rows + a documented Standard SQL subset (`SELECT`, DDL/DML) on an in-process SQLite engine, plus `gs://` load jobs (NDJSON/CSV), see [Known Limitations](#known-limitations) |
| Cloud Monitoring | REST + gRPC | Metrics, alert policies (evaluated), notification channels + incidents, and declarative uptime check configurations (`uptimeCheckConfigs` create/get/list/update/delete, stored and echoed — the probe-derived `uptimeCheckIps` list is not served) — see [Known Limitations](#known-limitations) |
| Cloud Logging | REST + gRPC | Log entries, filtering, tailing, monitored-resource descriptors, sinks + exclusions (routing evaluated, not delivered), logs-based metrics |
| Eventarc | REST + gRPC | Triggers/channels + provider discovery, plus the advanced control plane (message buses, enrollments, pipelines, Google API sources, channel connections, Google channel config); Pub/Sub- and Cloud Storage-sourced triggers deliver to a `cloudFunction` destination, a `cloudRun` service, or POST a CloudEvents request to an `httpEndpoint` (delivery verified end-to-end on k3d by `make test-e2e-eventarc-k8s`) — see [Known Limitations](#known-limitations) |
| Cloud DNS | REST | Metadata-only managed zones + record sets/changes + zone-level IAM — no authoritative DNS server, see [Known Limitations](#known-limitations) |
| Memorystore for Redis | REST | Metadata-only instances + location discovery — no Redis data plane, see [Known Limitations](#known-limitations) |
| Cloud SQL Admin | REST | Metadata-only instances/databases/users/client SSL certificates — no SQL engine or data plane, see [Known Limitations](#known-limitations) |
| Compute Engine | REST | Metadata-only instances/disks/networks/firewalls/subnetworks plus the derived public-image catalog — no VM, disk, or network data plane, see [Known Limitations](#known-limitations) |

**Not implemented (out of scope):** Artifact Registry, Cloud Endpoints, Deployment
Manager, Firebase Auth (Identity Toolkit).

### Fidelity matrix

Every operation (per transport) is classified **ga / limited / preview / unsupported**, and each
cell also carries a **`verified`** signal — whether real recorded evidence backs it (a
schema-validated committed transcript response for REST, a passing official-client check for
gRPC). `ga` without `verified` is a registration claim, not a response guarantee; run
`make gcp-status-evidence` for the REST gaps. The coverage is gated: the conformance harness
synthesizes a probe for every Discovery-mapped operation and fails on any that has neither a
validated response nor a reasoned entry in
[`tests/gcpconformance/testdata/coverage-exemptions.json`](tests/gcpconformance/testdata/coverage-exemptions.json).
The matrix is *derived* — from the emulator's
operation registry, the official Discovery schemas, and the wire-conformance harness — so it
can't drift from the code:

- [`docs/fidelity/fidelity-matrix.md`](docs/fidelity/fidelity-matrix.md) — human-readable, grouped by service
- [`docs/fidelity/fidelity-matrix.json`](docs/fidelity/fidelity-matrix.json) — machine-readable canonical form
- [`docs/fidelity/fidelity-matrix.csv`](docs/fidelity/fidelity-matrix.csv) — flat, for spreadsheets/CI
- [`docs/fidelity-overrides.yaml`](docs/fidelity-overrides.yaml) — the curated contract (the only hand-maintained input)

Regenerate with `make gen-gcp-fidelity-matrix`; CI fails (`make check-gcp-fidelity-matrix`) if the
committed matrix drifts.

The matrix grades **cells**; it also reports **coverage** per service and transport, because a
rollup over cells alone makes absence read as completeness. The coverage table compares the
published method list — the vendored Discovery document for REST, the proto service descriptors
for gRPC — with the routes the emulator actually registers and the methods the cells grade:
`served` is a registration statement (a served method may answer the documented `UNIMPLEMENTED`
and be graded `unsupported`), `not served` means no route exists and no cell could grade it, and
`unavailable` says the published list cannot be derived from what is vendored rather than
guessing. The generated matrix ends with the full per-service not-served lists. For example,
container has 60 `ga` cells out of 67 but only **31 of 71** published REST methods are served;
Dataproc has 52 `ga` cells out of 55 but only **96 of 136** published REST methods are served, and
62 of the remaining 110 are served only by the documented Serverless `UNIMPLEMENTED` (one
`unsupported` cell) rather than absent. A service therefore cannot read as complete while most of
its published surface is missing.

### Field coverage

The matrix grades **operations**, not the fields inside a resource: a field can
be published in the proto/Discovery document, missing from the emulator's
mapping, and still pass every operation-level gate (the TGM1-3/TGM6/TGM11-1/TGM14
class). [`docs/fidelity/field-coverage.csv`](docs/fidelity/field-coverage.csv)
is the derived field inventory for the pilot resources — one row per field and
transport, classified `roundtrip`, `derived`, `immutable`, `output-only` or
`unsupported`, with the evidence pointer, formula, or written reason + future
review date each class requires. The evidence now includes the generated suite
(`tests/gcpparity/fieldcoverage_test.go`), which sets every `roundtrip` field to a
type-driven non-default value, reads it back on its transport, and reads the
same resource over the other transport for every field both classify as
round-trip — the TGM1-3 class — plus a per-field masked update, a negative write
per server-owned/create-only field, an absence create per optional block, and
delete→NOT_FOUND. The dataset is generated from this catalog by
`make gen-gcp-field-coverage` (`tests/gcpparity/zz_fieldcoverage_generated.go`),
so a new field cannot enter the catalog without a scenario; a recorded gap is a
`testdata/fieldcoverage-baseline.json` entry with a reason and an `FC3-n` id, and
an entry that stops failing fails the suite. The values a wire type cannot
determine (a real region, a CIDR, a reference that must exist) are pinned in
[`tools/fieldgen/scenario-values.yaml`](tools/fieldgen/scenario-values.yaml). Behavior comes from the definition annotations; the vendored
Storage v1 and Cloud DNS v1 Discovery snapshots declare no `readOnly` flags, so
those rows are classified by review rather than by drift detection. A `roundtrip` row whose
definition marks the field `OUTPUT_ONLY`/`IMMUTABLE`/`readOnly` must carry a
reason (a recorded deviation). It is generated by `make gen-gcp-field-coverage`
from the compiled proto descriptors (`google.api.field_behavior`,
`google.api.resource_reference`) and the vendored Discovery schemas (`readOnly`),
and `make check-gcp-field-coverage` fails CI when a definition field has no row, a
row is stale, behavior drifts, a `roundtrip` row's evidence no longer resolves, or
a review date has passed. Pilot scope: Storage `Bucket`, Firestore
`Database`/`BackupSchedule`, Functions v2 `Function`, KMS `CryptoKey`, Cloud DNS
`ManagedZone`, Monitoring `AlertPolicy`. The curated scope lives in
[`tools/fieldgen/scope.yaml`](tools/fieldgen/scope.yaml); the Terraform
provider-schema join is the documented FC6 hook.

### Reference coverage

A field the API annotates `google.api.resource_reference` names another
service's resource, and storing the name verbatim is the TGM11-1 defect class.
[`docs/fidelity/reference-coverage.csv`](docs/fidelity/reference-coverage.csv)
is the derived inventory — one row per annotated field — classified `validated`
(existence resolved against the referenced store: Firestore CMEK→KMS, Storage
notification→Pub/Sub, Pub/Sub subscription/dead-letter→Pub/Sub, Dataproc
cluster→Metastore, Eventarc trigger→Workflows), `format-only` (the name shape is
checked, existence is not), `unvalidated` (stored verbatim; a written reason and
a future review date, a scheduled `FC4-n` gap) or `not-modelled` (the emulator
does not parse or serve the field). `make check-gcp-field-coverage` fails when an
annotated field has no row, a row is stale, a target drifts, a
`validated`/`format-only` row's test no longer resolves, or an `unvalidated`
review date has passed. The universe is curated in `tools/fieldgen/scope.yaml`
(`references:` for annotated messages outside the field pilot,
`documented_references:` for Discovery-only references such as the Storage
notification topic).

### Fidelity & testing

The GCP reference docs live under [`docs/gcp/`](docs/gcp/README.md) (that index lists
each one and what it covers). The published wire contract — what `ga` means here, the
pinned API artifacts, client compatibility, the CI gates, and the surfaces that are
explicitly non-`ga` — is
[`docs/gcp/wire-contract.md`](docs/gcp/wire-contract.md). The one-command aggregate gate is
`make ga-check`.

[`docs/gcp/testability.md`](docs/gcp/testability.md) is the per-service local-testability
contract: what a local run proves, and what must be verified on real GCP.

The explicitly **accepted risks** — identity authz not enforced
(Cloud KMS crypto ops honor a default-permissive cryptoKey policy), LROs complete synchronously by
default (an opt-in async mode is available for local testing),
the metadata-only tier, and the real-GCP smoke requirement for Yellow/Red surfaces — are recorded
in [wire-contract.md §8](docs/gcp/wire-contract.md#8-accepted-risks).

## Install

Every release from `v0.1.1` on publishes `jaiscloud-gcp` next to `jaiscloud-aws` from the same tag.

### Docker

```bash
# Docker Hub (or ghcr.io/jaisrajms/jaiscloud-gcp:latest)
docker pull jaisraj/jaiscloud-gcp:latest
docker run --rm -p 8080:8080 -p 8081:8081 -p 4567:4567 \
  jaisraj/jaiscloud-gcp:latest start --ui

curl -s localhost:8080/_jaiscloud/health      # {"status":"ok"}
open http://localhost:4567/ui/                # embedded console
```

Ports: `8080` REST/admin, `8081` gRPC (h2c), `4567` console with `--ui`. The image declares
`8080`; publish `8081`/`4567` explicitly as above. Pin a version instead of `latest` in CI
(`jaisraj/jaiscloud-gcp:0.1.1`); `jaiscloud-gcp version` prints the tag the image was built from.

```bash
brew tap jaisrajms/homebrew-tap && brew install --cask jaiscloud-gcp
```


## Quick Start

### 1. Build from source

```bash
git clone https://github.com/jaisrajms/jaiscloud.git && cd jaiscloud
go build -o jaiscloud-gcp ./cmd/jaiscloud-gcp/
# or: make build-gcp
```

### 2. Start

```bash
./jaiscloud-gcp start
# Listening on http://localhost:8080  (gRPC on :8081)
```

### 3. Connect

Point any official Google client library at the emulator. Most services use plain endpoint overrides; gRPC-native clients connect to `:8081`, and the services with official emulator-host environment variables (Firestore, Datastore, Pub/Sub, Storage) can use them directly.

```bash
export GCP_EMULATOR_ENDPOINT=http://localhost:8080/    # REST services (GCS, BigQuery, Dataproc, Workflows, ...)
export FIRESTORE_EMULATOR_HOST=localhost:8081           # Firestore (gRPC)
export STORAGE_EMULATOR_HOST=http://localhost:8080      # GCS REST client
```

**Service-account credentials.** The emulator serves an OAuth2 token endpoint at the root (`POST /token`, also `/v1/token`) so `google-auth-library` service-account credentials can mint an access token instead of calling Google. Point `ServiceAccountCredentials`'s token server URI at `<endpoint>/token`; the JWT-bearer grant is implemented (`grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`), and the response is the standard `{access_token, token_type, expires_in}`. This is independent of the opt-in metadata server (`--gcp-metadata`); it is available whenever the REST transport is selected.

## Connect your SDK

### Go — REST-based services (GCS, BigQuery, Dataproc, Workflows, Secret Manager REST, ...)

```go
import "google.golang.org/api/option"

opts := []option.ClientOption{
    option.WithEndpoint("http://localhost:8080/"),
    option.WithoutAuthentication(),
}
```

### Go — Firestore (gRPC, real emulator-host support)

```go
import (
    "cloud.google.com/go/firestore"
    "google.golang.org/api/option"
)

// export FIRESTORE_EMULATOR_HOST=localhost:8081
client, err := firestore.NewClient(ctx, projectID, option.WithoutAuthentication())
```

### Go — Cloud Datastore (gRPC, real emulator-host support)

```go
import "cloud.google.com/go/datastore"

// export DATASTORE_EMULATOR_HOST=localhost:8081
client, err := datastore.NewClient(ctx, projectID)
```

### Go — Cloud Monitoring (gRPC, manual endpoint — no official emulator-host var for this client)

```go
import (

conn, err := grpc.NewClient("localhost:8081", grpc.WithTransportCredentials(insecure.NewCredentials()))
```

### Terraform / OpenTofu

The stock `hashicorp/google` provider talks to the emulator through its per-service custom endpoints (keep `user_project_override = false`; the provider needs a credential present, the emulator ignores its value):

```hcl
provider "google" {
  project                  = "test-project"
  region                   = "us-central1"
  user_project_override    = false
  dataproc_custom_endpoint = "http://localhost:8080/"
}
```

The full per-service endpoint block is generated from
[`tests/integration/gcp/terraform/terraform-endpoints.yaml`](tests/integration/gcp/terraform/terraform-endpoints.yaml);
`make gcp-terraform-endpoints` prints it. The same map drives the fixture, the
module driver and the web-corpus plan run (`make test-gcp-terraform-corpus`,
see the [suite README](tests/integration/gcp/terraform/README.md#web-corpus-tf2)),
which plans the provider's published examples against the emulator.

What a green Terraform gate proves — and what it explicitly does not — is the
trust boundary in [`docs/gcp/terraform-compatibility.md`](docs/gcp/terraform-compatibility.md).
The short version: the control-plane request/response contract and Terraform's
own convergence, not authorization, quotas, org policy or any data plane. A
small corpus is also recorded against real GCP and replayed against the
emulator (`make test-gcp-terraform-differential`, see the
[differential README](tests/integration/gcp/terraform/differential/README.md)),
so a provider-side quirk is classified as a provider quirk instead of being
mistaken for an emulator bug.

`google_dataproc_cluster` with `virtual_cluster_config` plans, applies and re-reads with no diff, and the node pools it reconciles are readable through the GKE API — that is the path `make test-gcp-terraform` gates. The plain `cluster_config` (Compute-Engine) shape applies and re-reads cleanly too: the read carries the service defaults real Dataproc reports (`config.softwareConfig.imageVersion`, the instance groups and a zone — see [Dataproc: Compute-Engine cluster read defaults](#dataproc-compute-engine-cluster-read-defaults)), so the provider no longer panics flattening an absent `software_config`. Resource-level IAM is served on clusters, jobs and workflow templates: `google_dataproc_cluster_iam_*` and `google_dataproc_job_iam_*` read-modify-write the stored policy over the shared `ResourceStore` (etag OCC, AIP-149 versions; the policy is never enforced), and the policy is dropped with the resource, so the fixture's cluster member and the Dataproc module case's job member both converge. Point `gke_cluster_target` at an existing GKE cluster: `gcloud container clusters create` works against the emulator with `CLOUDSDK_API_ENDPOINT_OVERRIDES_CONTAINER=http://localhost:8080/container/` (or a direct `POST /container/v1/projects/{p}/locations/{l}/clusters` with a `workloadIdentityConfig`, which Dataproc-on-GKE requires).

`google_container_cluster` works now that the GKE read is complete: it renders the nested messages the provider dereferences unconditionally on its read (`legacyAbac`, `networkConfig`, `shieldedNodes`, `defaultMaxPodsConstraint`), so the fixture creates the Dataproc-on-GKE prerequisite with the resource itself and a second `plan` reports no changes. It needs one thing the other services do not: a `container.`-prefixed host (`container_custom_endpoint = "http://container.localhost:8080/container/"`), because the emulator routes `container.v1` by host — the bare `/v1/projects/{p}/locations/{l}/clusters` path belongs to Managed Kafka — and the provider keeps only the scheme+host of a custom endpoint. `make test-gcp-terraform` derives that host from the endpoint.

`google_cloud_run_v2_service` is the served Cloud Run surface: the service/revision control plane, service IAM and the operation records, over both transports (see [Cloud Run: behavioural control plane, mock runtime](#cloud-run-behavioural-control-plane-mock-runtime-rest--grpc)). `cloud_run_v2_custom_endpoint = "http://localhost:8080/v2/"` (one trailing slash) points the provider at it. `make test-gcp-terraform` creates a raw service with a container `readiness_probe`, and `make test-gcp-terraform-cloudrun` drives [`GoogleCloudPlatform/terraform-google-cloud-run`](https://github.com/GoogleCloudPlatform/terraform-google-cloud-run)'s `modules/v2` submodule end to end (service + module-created service account + invoker IAM member, apply → plan No changes → in-place update → plan No changes → destroy). The repo's root module is the **v1** `google_cloud_run_service`, which is not served; Jobs, WorkerPools and v1 domain mappings are not modelled either (a request to `/v2/.../jobs` or `/v2/.../workerPools` is unclaimed and answers 404 `UnknownService`). Traffic targets are stored and reflected in `trafficStatuses`, but the split is not enforced, so the cases leave `traffic` empty.

`google_bigquery_dataset` and `google_bigquery_table` read back the dataset's description/location/labels/`defaultTableExpirationMs` and the dataset ACL, and the table's reference, friendly name, labels and schema; a schema column, labels, the description and an ACL entry all update in place with a clean re-plan. `big_query_custom_endpoint = "http://localhost:8080/bigquery/v2/"` points the provider at it, and `make test-gcp-terraform-bigquery` drives [`terraform-google-modules/terraform-google-bigquery`](https://github.com/terraform-google-modules/terraform-google-bigquery) end to end (apply → plan No changes → in-place update → plan No changes → destroy). Resource IAM is served on both planes the provider uses: a dataset's IAM is BigQuery's legacy `access` ACL — real BigQuery has no `datasets.getIamPolicy`, so the provider reads `GET .../datasets/{d}?accessPolicyVersion=3` and PATCHes the whole access list — and a table's is the `tables.getIamPolicy`/`setIamPolicy`/`testIamPermissions` mixin over the shared policy store (etag OCC, AIP-149 versions; the policy is stored but never enforced). `google_bigquery_dataset_iam_*` and `google_bigquery_table_iam_*` therefore both converge, and `make test-gcp-terraform` asserts both wire shapes.

`google_dns_managed_zone` applies and re-reads with no diff, and zone-level IAM converges: `google_dns_managed_zone_iam_*` read-modify-write the policy stored per zone over the shared `ResourceStore` (etag OCC, AIP-149 versions; never enforced), the zone must exist for every verb (an absent zone is `404`, not an empty policy), and the policy is dropped with the zone. `dns_custom_endpoint = "http://localhost:8080/dns/v1/"` points the provider at it; `make test-gcp-terraform` creates a zone and a zone IAM member, asserts the stored binding and the permission echo, re-plans with no changes, and checks the policy is gone after destroy. `make test-gcp-terraform-clouddns` drives the `terraform-google-cloud-dns` module end to end (zones, record sets, changes — the module creates no IAM).

`google_secret_manager_secret` read back both replication arms (`automatic` with a `global` CMEK key, `userManaged` with per-replica locations and keys), the labels, the event-notification `topics` list and the `rotation` schedule, and a version's payload is what `versions.access` returns; label, rotation-period, payload (a version replacement) and authoritative IAM-binding changes all re-plan clean. `secret_manager_custom_endpoint = "http://localhost:8080/v1/"` points the provider at it, and `make test-gcp-terraform-secret-manager` drives [`GoogleCloudPlatform/terraform-google-secret-manager`](https://github.com/GoogleCloudPlatform/terraform-google-secret-manager) end to end (two secrets — automatic + CMEK + rotation + topic, and user-managed replicas — a version each and an IAM binding). Regional secrets (`google_secret_manager_regional_secret*`) are **not** served (TF1-4).

`google_workflows_workflow` reads back its description, labels, source, service account, `state` and `revisionId`, and a source/description/label change updates in place and bumps the revision. `workflows_custom_endpoint = "http://localhost:8080/v1/"` points the provider at it, and `make test-gcp-terraform-workflows` drives [`GoogleCloudPlatform/terraform-google-cloud-workflows`](https://github.com/GoogleCloudPlatform/terraform-google-cloud-workflows)'s `modules/simple_workflow` submodule (the repo root always creates a Scheduler or Eventarc trigger). That module pins `hashicorp/google < 7.0`, so this case resolves 6.49.3 while the others use 7.46.2; the blueprint's `simple_workflow` also does not expose `deletion_protection` (provider default `true`), so the case removes the workflow from state and issues the DELETE the provider guards. Workflow CMEK and resource-level IAM are not implemented, and the provider has no workflow IAM resource type; `roles/workflows.invoker` is exercised as project-level IAM.

`google_cloud_scheduler_job` reads back its name, description, `schedule`, `timeZone`, `state`, `scheduleTime`, `attemptDeadline`, `retryConfig`, the HTTP target (including the server-filled `headers` map: `User-Agent: Google-Cloud-Scheduler`, plus `Content-Type: application/octet-stream` when the job carries a body) and the Pub/Sub target, and the `:pause`/`:resume` custom methods drive the state transitions (the provider's `paused` attribute is not a Job field, so it is deleted from every request body and mapped onto those methods). A job created without a `retryConfig` — including the all-zero `{ retry_count = 0 }` block the provider drops from the create body — reads back the documented RetryConfig defaults (`retryCount` 0, `minBackoffDuration` 5s, `maxBackoffDuration` 1h, `maxDoublings` 5, `maxRetryDuration` 0 = unlimited), while a supplied config is echoed verbatim; an unset field takes its documented default because `RetryConfig` is proto3 without field presence (TF3-4-2). `cloud_scheduler_custom_endpoint = "http://localhost:8080/v1/"` points the provider at it, and `make test-gcp-terraform-scheduler` drives [`GoogleCloudPlatform/terraform-google-cloud-scheduler`](https://github.com/GoogleCloudPlatform/terraform-google-cloud-scheduler) end to end with two enabled far-future jobs — one header-less HTTP target and one Pub/Sub target — so the cron engine never fires (apply with the module's default `retry_config` → the provider's POST + `:resume` on the already-ENABLED jobs → plan No changes → in-place update to a non-default retry config → plan No changes → pause → resume → destroy). That module pins `hashicorp/google < 7.0`, so the case resolves 6.49.3; its HTTP target input exposes no `headers` field, which is exactly the shape the provider used to crash on before TF3-4-1 made the emulator answer the synthesized map.

`google_cloud_tasks_queue` reads back `state`, `rateLimits`, `retryConfig` and `stackdriverLoggingConfig`, and the queue IAM surface (`queues.getIamPolicy`/`setIamPolicy`) backs `google_cloud_tasks_queue_iam_member`. `cloud_tasks_custom_endpoint = "http://localhost:8080/v2/"` points the provider at it, and `make test-gcp-terraform-tasks` drives [`GoogleCloudPlatform/terraform-google-cloud-tasks`](https://github.com/GoogleCloudPlatform/terraform-google-cloud-tasks) end to end (queue + rate limits + retry config + logging config + one IAM member, apply → plan No changes → rate/retry/IAM update → plan No changes → destroy, no task created so the dispatch engine never runs). The module also pins `hashicorp/google < 7.0`, so the case resolves 6.49.3. `rate_limits.max_burst_size` is computed-only in 6.x, so the create body omits it and the emulator applies the documented Cloud Tasks default and reads back 100 (`maxConcurrentDispatches` defaults to 1000 when omitted too), which the case asserts (TF3-4-3).

`google_dataproc_job` submits through `jobs:submit`, reads back its placement, labels, pyspark driver and `status.state`, and deletes through `jobs.delete`; `dataproc_custom_endpoint = "http://localhost:8080/"` points the provider at the API. `make test-gcp-terraform-dataproc` drives [`GoogleCloudPlatform/terraform-google-dataproc`](https://github.com/GoogleCloudPlatform/terraform-google-dataproc) end to end: the module renders a GCE-shaped cluster, a root-module pyspark job runs in it, labels and the worker count update in place, and both re-plan clean before destroy. The module's internal default-service-account data source is pruned with `-target`: Compute `projects.get` is served, but the IAM read the data source performs on the returned account is not (TF2-1-1), so the IAM prerequisite is recorded rather than worked around; the cluster and job paths are the measured surface.

`google_service_account` and project IAM back the CFT service-accounts and IAM modules. `make test-gcp-terraform-service-accounts` drives [`terraform-google-modules/terraform-google-service-accounts`](https://github.com/terraform-google-modules/terraform-google-service-accounts) (three accounts, two project roles each, a role-set change) and `make test-gcp-terraform-iam` drives [`terraform-google-modules/terraform-google-iam`](https://github.com/terraform-google-modules/terraform-google-iam)'s project, bucket and Pub/Sub topic submodules in additive mode with multiple members per role. Both run every phase with `-parallelism=10` and assert the policies keep every surviving member and gain the new ones (the etag OCC path). `iam_custom_endpoint`, `iam_beta_custom_endpoint` and `resource_manager_custom_endpoint` point the two IAM clients and the project-policy client at the emulator; folder/organization IAM is outside the project-scoped surface.

`google_sql_database_instance`, `google_sql_database` and `google_sql_user` are driven end to end by the CFT [`terraform-google-sql-db`](https://github.com/terraform-google-modules/terraform-google-sql-db) `modules/postgresql` submodule (`make test-gcp-terraform-sql-db`): the module's full `settings` block (tier, availability, backup configuration, maintenance window, disk settings, labels) applies through `google-beta`, the instance reads back `RUNNABLE`, a tier/label change PATCHes in place and re-plans clean, and destroy leaves it `404`. `sql_custom_endpoint = "http://localhost:8080/sql/v1beta4/"` points both providers at it; the module's default-zone read additionally needs `compute_custom_endpoint`. The metadata-only SQL engine is not modelled (no real database server), so the case asserts control-plane state only. `PLAN_ONLY=1` (or `make test-gcp-terraform-plan-only CASE=sql-db`) runs it as init → validate → plan without applying.

GKE and Datastore have no apply tier yet. `make test-gcp-terraform-gke` drives the CFT [`terraform-google-kubernetes-engine`](https://github.com/terraform-google-modules/terraform-google-kubernetes-engine) root module **plan-only**: the plan must carry the cluster, the default node pool and the node service account, and the module's `data.google_container_engine_versions` read must reach Container `GetServerConfig`. Nothing is applied, because GKE is a metadata-only control plane here (see [the GKE notes](#google-kubernetes-engine-gke-metadata-only-cluster-mock-rest--grpc)); the fixture's raw `google_container_cluster` remains the apply gate. `container_custom_endpoint` must carry the `container.` host (the provider keeps only scheme+host).

`make test-gcp-terraform-datastore` drives the CFT [`terraform-google-cloud-datastore`](https://github.com/terraform-google-modules/terraform-google-cloud-datastore) module **plan-only** as well: it has no `google_*` resource at all — it renders the caller's `index.yaml` and shells out to `gcloud datastore indexes` — so the gate asserts the rendered index document and its gcloud resource, and no apply runs. The Datastore Admin `projects.indexes.*` / export / import surface is not served (the fidelity matrix lists those ten published methods under "no registered route"); the served Datastore surface is the data API, covered by the service and conformance suites.


The provider's own schema also requires `kubernetes_cluster_config.kubernetes_namespace` and `node_pool_config.locations`, which the API marks optional, so a real-GCP config that omits them needs them added. There is no `google_dataproc_cluster` data source and no import support upstream, so inspection is `terraform state show`, `terraform plan -refresh-only`, or the REST API.

The customer-shaped version of these notes — a zonal `google_container_cluster`, a `google_dataproc_cluster` with `virtual_cluster_config`, the input/output/staging buckets and a `google_dataproc_job`, then Helm and the official Java clients — is [`demo/dpgke-lifecycle/`](demo/dpgke-lifecycle/README.md), gated by `make test-dpgke-demo-terraform` and `make test-e2e-dpgke-demo-k3d`.

**Throttle runtime control.** The injector policy can be changed mid-test without a restart via the admin plane: `POST /_jaiscloud/throttle` with a JSON body (`mode`, `rps`, `burst`, `services`, `failFirst`, `failEvery`, `failCount`, `status`, `retryDelay`) fully replaces the running configuration and clears accumulated counters; `GET /_jaiscloud/throttle` returns the current state. It is wired even when `JAISCLOUD_GCP_THROTTLE` is unset, so a test can arm a failure on demand; an unarmed injector is a no-op (local testing only — see [Known Limitations](#known-limitations)).

**Transport selection.** `--transports` sets the global default and `--transport-overrides` refines it per service (an override wins). A service is constructed and registered only when at least one transport is selected for it, and only the selected listeners bind — `--transports=rest` opens no `:8081`, while `--transports=grpc` serves the GCP REST API nowhere but keeps the always-on `/_jaiscloud/*` admin plane (and `/metrics`) on `--port`. Per-service selection gates construction and which gRPC services register; `none` removes a service from both transports (a later request for it fails with a registry `no handler` error). The REST API is mounted as one route set, so it is gated by the global `--transports` setting rather than per service. Per-service override names are the **wire** names: `storage`, `pubsub`, `secretmanager`, `kms`, `iam`, `firestore`, `firestoreadmin`, `datastore`, `logging`, `monitoring`, `functions`, `workflows`, `workflowexecutions`, `dataproc`, `managedkafka`, `metastore`, `eventarc`, `serviceusage`, `resourcemanager`, `bigquery`, `dns`, `sqladmin`, `compute`, `iceberg`, `redis` (Memorystore), `scheduler`, `tasks`. An unknown service or transport token fails startup loudly.

```bash
./jaiscloud-gcp start --transports=rest                                  # REST + admin only (no :8081)
./jaiscloud-gcp start --transports=grpc                                  # gRPC + admin only (no GCP REST surface)
./jaiscloud-gcp start --transport-overrides=storage=grpc,pubsub=rest     # mixed per service
./jaiscloud-gcp start --transport-overrides=redis=none                   # disable one service
```

Storage model (identical semantics to the AWS binary — see the [main README](README.md#configuration)): default is memory + periodic `state.json` saves; `--dsn` stores everything in PostgreSQL; `--ephemeral` is purely in-memory with no disk writes.

```bash
./jaiscloud-gcp start                                              # default: memory + periodic saves
./jaiscloud-gcp start --dsn "postgres://user:pass@localhost:5433/jaiscloud"
./jaiscloud-gcp start --ephemeral                                  # CI / unit tests
```

**Current GCP surface:**

- **Pub/Sub** — topics and subscriptions over `/api/ui/v1/gcp/pubsub`: list/create/delete, topic/subscription detail, publish, subscription updates, and topic/subscription IAM.
- **Firestore** — collections and documents over `/api/ui/v1/gcp/firestore`: browse root collections and documents, and create/update/delete documents with the typed field encoding.
- **Compute Engine** — instances over `/api/ui/v1/gcp/compute`: an aggregated list across zones with detail, start, stop and delete.
- **Cloud Run** — services and revisions over `/api/ui/v1/gcp/run`: services aggregated across regions, service/revision detail, and delete.
- **BigQuery** — datasets, tables and jobs over `/api/ui/v1/gcp/bigquery`: list/create/delete datasets and tables, view a table's schema and a read-only row preview, and list/inspect/cancel/delete jobs.

## Known Limitations

This section documents deliberate simplifications and known correctness edge cases — distinct from ordinary bugs, these are behaviours a developer relying on this emulator should know about up front.

### Throttle/quota: injected failures, not real quota values

No real quota plane is modelled. With `JAISCLOUD_GCP_THROTTLE` unset (the default), no path is ever throttled and backoff/quota-exhaustion handling never runs locally — that is the normal state, and production code must not depend on the injector. When the injector is armed it refuses matching REST and gRPC requests before dispatch with a synthetic `429 RESOURCE_EXHAUSTED` or `503 UNAVAILABLE`, together with a `Retry-After` header and a `google.rpc.RetryInfo` detail, so a client's retry/backoff/idempotency path can be exercised deterministically (`fault` mode is counter-based and needs no timing; `rate` mode is a per-project token bucket refilled on the real clock). It injects **configured** limits, never real per-project/per-metric quota values; quota behaviour must still be verified on real GCP. The policy can also be armed, retuned, or disarmed at runtime through `POST /_jaiscloud/throttle` (`GET` reads it back) instead of restarting with new env — see [Configuration](#configuration). `make test-throttle-gcp` exercises the fault mode and the runtime control end-to-end.

### OAuth2: the service-account assertion signature and audience are not verified

The token endpoint (`POST /token`) parses the JWT-bearer assertion and enforces that it is a well-formed, unexpired JWT identifying a service account, but it does **not** verify the assertion's signature or its `aud` claim: the client signs with a key the emulator has never registered and hardcodes the audience to `https://oauth2.googleapis.com/token` regardless of the configured token server, and JaisCloud likewise never verifies the signature of the bearer tokens it accepts (identity is decoded, not authenticated — see the metadata server). The minted access token is a JaisCloud HS256 JWT carrying the service-account email and project, not an opaque Google token. `refresh_token` is accepted but there is no real refresh-token store — any non-empty value mints a fresh access token.

### IAM: service-account credentials require the account and validate the delegation chain

Every IAM Credentials method (`generateAccessToken`, `generateIdToken`, and the `signBlob`/`signJwt` methods they share with IAM) resolves the service account through the IAM registry before doing any work, on both transports. A service account that was never created is `NOT_FOUND` (`404`) — the emulator no longer lazily materialises an RSA key for an arbitrary email — and `projects/-` keeps working for an account that does exist, because the project is resolved from the email. A refused request stores nothing.

`delegates[]` is validated instead of accepted and ignored: every entry must be the documented `projects/-/serviceAccounts/{ACCOUNT_EMAIL_OR_UNIQUEID}` name, must name an existing service account, must not repeat, and must not name the target (the docs exclude the caller and the target from the chain). The credential always represents the target account, exactly as the delegated flow documents. Two things are deliberately *not* enforced: the per-hop `roles/iam.serviceAccountTokenCreator` grants, because the emulator stores but never evaluates IAM policies, and any maximum chain length, because Google publishes none. A unique-id delegate cannot be scoped through `projects/-` (the resource store is per-project and has no global unique-id index; the same limitation the management surface records as DC29), so it is `NOT_FOUND` while the email form works.

`generateIdToken`'s `organizationNumberIncluded` (REST only — the v1 proto has no such field, so a gRPC client cannot send it) adds the documented `google.organization_number` claim. The value comes from the project's `organizations/{id}` parent reference (Cloud Resource Manager keeps one); a project with no registry entry, a folder parent, or an unset/non-numeric parent reports the documented `null`.

### Cloud Pub/Sub: ordering, exactly-once and redelivery deviations

The messaging surface (ack / `ModifyAckDeadline`, seek, ordered delivery, pull and streaming-pull framing) is exercised against real GCP by the differential harness (`tests/gcpdifferential`) — the PSM1 oracle — so those fidelity cells rest on recorded behaviour rather than emulator self-tests. The differences that remain are deliberate and are documented here rather than left as an unearned `ga`:

- **Ordering keys.** A subscription with `enableMessageOrdering` is honoured and the ordered-delivery contract is modelled: a `Pull`/`StreamingPull` returns **every available message for an ordering key in one batch** (in publish order), a key with an outstanding batch is withheld until it is acked, a later ack is **held** until every earlier message for the key is acked, and redelivering a message (a negative ack, or a lapsed ack deadline) redelivers it and **all subsequent messages for the key, including ones acknowledged in the same round**. Acknowledged keyed messages are retained (up to the subscription's message-retention window) so they can be redelivered, rather than deleted on ack. The exact redelivery schedule and cross-key delivery interleavings remain best-effort and are never asserted. Independent of ordering keys, the emulator delivers in ascending `PublishTime`; real GCP guarantees **no** delivery order without an ordering key, so code must not rely on publish-time order — the emulator's ordering of non-keyed messages is extra determinism, not real behaviour. (An unkeyed message is deleted on ack and is not resurrectable by a later `ModifyAckDeadline`.)
- **Exactly-once acknowledgement IDs.** `enableExactlyOnceDelivery` is honoured end to end: the ack ID embeds the delivery attempt and, on an exactly-once subscription, `Acknowledge`/`ModifyAckDeadline` reject a superseded (a newer delivery exists) or expired (the ack deadline lapsed) ID with `INVALID_ARGUMENT` plus a `google.rpc.ErrorInfo` detail (`reason: EXACTLY_ONCE_ACKID_FAILURE`, `metadata: {"<ackId>": "PERMANENT_FAILURE_INVALID_ACK_ID"}`), matching real GCP so the official clients' `AckWithResult` returns `InvalidAckID`. A plain subscription keeps accepting any decodable ID, and a re-ack of an already-acked ID is `OK`. The streaming ack path does not populate `StreamingPullResponse.acknowledge_confirmation` (the official clients resolve the result from the unary RPC's `ErrorInfo`). See `internal/gcp/store/pubsub/ackid.go`.
- **Dead-lettering.** A subscription's `deadLetterPolicy` is honoured: a message not acknowledged within `maxDeliveryAttempts` is forwarded to the dead-letter topic wrapped in a **new message** that preserves the publisher's attributes and ordering key, mints a **fresh server-assigned `messageId`** and a **forward-time `publishTime`** (the original publish time is preserved only in the `CloudPubSubDeadLetterSourceTopicPublishTime` attribute — verified against real GCP, PSM5), and adds real GCP's four `CloudPubSubDeadLetterSource*` attributes — `Subscription` (the source subscription's short id), `SubscriptionProject`, `DeliveryCount`, and `TopicPublishTime` (the original publish time). The forward fires on the claim after the `maxDeliveryAttempts`-th delivery; real GCP forwards on a best-effort basis (its docs note a message "might forward ... after fewer attempts than configured, or ... a few more times"), so the numeric `DeliveryCount` is not asserted as a contract — the PSM2 differential golden (`tests/gcpdifferential`) pins the attribute set and names (source subscription short id, project) and folds both the count and the publish-time value; the unit tests pin the millisecond `+00:00` publish-time layout and the fresh-id/forward-time/ordering-key identity of the forwarded copy.
- **Timing / best-effort.** Redelivery schedules, flow-control interleavings, publish-side duplicates and multi-region ordering are not modelled and are never asserted as `ga`.

### Cloud Pub/Sub: topic fields are stored and served, not run

A topic's whole mutable surface round-trips through both transports: `labels`, `messageRetentionDuration` (10 minutes–31 days, canonical `"600s"` form), `kmsKeyName`, `messageStoragePolicy`, `schemaSettings`, `ingestionDataSourceSettings` and `messageTransforms` are stored on create and updated through `updateMask` (REST `topics.patch` / gRPC `UpdateTopic`), including nested AIP-134 paths and the clear contract (a field absent under its mask is removed; an absent storage policy means "no constraint" here, where real GCP falls back to the project/organization policy). The `terraform-google-pubsub` module's `labels`/`kms_key_name`/`message_retention_duration`/`message_storage_policy`/`schema_settings` inputs converge with no diff and no `400` (`make test-gcp-terraform-pubsub-topic`). Three boundaries are deliberate:

- **CMEK is store-and-serve.** `kmsKeyName` is format-validated only: the emulator has no Pub/Sub service agent, so it does not check the key's existence or grants. Envelope encryption does use the key on publish, and a rotation affects only later publishes — an old message keeps its per-message DEK and still decrypts. See [Cloud Pub/Sub: ordering, exactly-once and redelivery deviations](#cloud-pubsub-ordering-exactly-once-and-redelivery-deviations).
- **Message transforms and ingestion sources are not executed.** JavaScript UDFs, AI inference and the GCS/Kinesis/MSK/Event Hubs/Confluent ingestion pollers are validated, stored and echoed, but no transform runs on publish and no source is polled.
- **There is no `projects.schemas` API.** `schemaSettings.schema` is format-checked and served verbatim, but the emulator cannot create or resolve a schema (the Terraform module's `schema` input, which needs a `google_pubsub_schema`, therefore cannot run; the update gate exercises `schemaSettings` on a raw `google_pubsub_topic`). No publish is validated against a schema. That surface belongs to a future schemas service, not this one.

### Cloud Storage: range reads are served from a whole-object decrypt

The Cloud Storage v2 gRPC service implements both read surfaces: the server-streaming `ReadObject` (metadata + bounded 2 MiB data chunks, with `read_offset`/`read_limit`) and the bidirectional `BidiReadObject` used by the official Go client's `Reader` (with `experimental.WithGRPCBidiReads`) and `MultiRangeDownloader`. `BidiReadObject` serves multiple independent ranges per stream (negative offsets count back from EOF, `read_length` 0 reads to EOF, an offset past EOF is `OutOfRange`), honors `generation` and the `if_generation_match`/`if_generation_not_match`/`if_metageneration_match`/`if_metageneration_not_match` preconditions, and mints an opaque `read_handle` the client can pass back to open a subsequent stream without repeating the object identity. Unsupported request surface (the deprecated `read_mask`, the redirect-only `routing_token`) fails loud with `codes.Unimplemented`. The bucket/object write, copy, restore, IAM, and resumable-upload surfaces are all implemented.

**Correctness caveat (shared with `ReadObject`):** objects are stored as a single AES-256-GCM blob (`iv || ciphertext+tag`) for both CSEK and the server/CMEK envelope, and one GCM tag authenticates the whole ciphertext. A byte window therefore cannot be decrypted without processing the entire object, so true partial decryption is not possible for the on-disk format. A range read reads the blob via `blobfs.GetStream`, decrypts it (at most once per `BidiReadObject` stream, reusing the plaintext across that stream's ranges), and streams the requested window in bounded chunks. The full ciphertext and the full decrypted plaintext are therefore both in memory for the read, and a very large object costs one full decrypt per read stream.

`RestoreObject` models GCS soft-delete as versioning tombstones (`timeDeleted` set): restoring a non-live generation flips it live and marks the current live generation non-live, honoring the `if_generation_match`/`if_metageneration_match` preconditions atomically. `restore_token` and `copy_source_acl` are accepted but ignored (the emulator has no ACL plane and no hierarchical namespaces). `UpdateBucket` applies the field-mask paths it models — `labels`, `versioning`, `storage_class`, `retention_policy`, `lifecycle`, `cors`, `encryption`, `soft_delete_policy`, `iam_config` and the CFT-module blocks — and bumps the bucket metageneration; unknown paths are ignored rather than rejected. A `Bucket.etag` on the update is an optimistic-concurrency precondition: a stale etag is `ABORTED`, matching the IAM policy etag contract. The `retention_policy.is_locked`/`effective_time` and `soft_delete_policy.effective_time` members are output-only on both transports (a caller value is ignored and the server stamps the canonical one), `soft_delete_policy` is settable over gRPC like REST v1, the read serves `project` in the project-number form real GCS uses, and `location` is **creation-only** (the proto marks it IMMUTABLE: "Attempting to update this field after the bucket is created results in an error"): a masked update that carries the stored location is a no-op (compared in the canonical uppercase form, so a case-only resend is accepted), while any other value is `400 INVALID_ARGUMENT` and leaves the bucket untouched — on both transports, since the gRPC `UpdateBucket` enforces the same rule.

### Terraform: empty label values never converge (provider-side)

GCP accepts an empty label value (`team = ""`), and the emulator stores and serves it exactly as the API does — verified for Cloud KMS crypto keys, Cloud Storage buckets, Pub/Sub topics and subscriptions, Secret Manager secrets, BigQuery datasets, Cloud Run services, Cloud Workflows and Resource Manager projects. But `hashicorp/google` 5.x and later (7.46.2 included) strips empty-valued labels out of the request before sending it: a captured create carries only the non-empty entries (provider issue [#16528](https://github.com/hashicorp/terraform-provider-google/issues/16528), which upstream closed as "cannot be resolved"). The API never sees the label, so `effective_labels`/`terraform_labels` keep proposing it on every plan — against real GCP as much as against this emulator. Give the label a non-empty value (`_` or `true`), or keep it out of the diff with `lifecycle { ignore_changes = [terraform_labels["team"]] }`.

### Firestore: optimistic-concurrency conflict detection

Firestore's `documents.patch` and transform-carrying `commit`/`batchWrite` writes are protected against concurrent lost updates via an optimistic-concurrency check: the document's `UpdateTime` at read time is captured and re-validated, atomically with applying the write, against the live document's current `UpdateTime` — a conflicting concurrent write causes the loser to receive `409 ABORTED` instead of silently overwriting the winner.

`UpdateTime` is the version token, and it is kept **strictly monotonic per document** even when the emulator's clock is frozen (`POST /_jaiscloud/clock` with `{"mode":"fixed",...}`, used for deterministic tests). Every write stamps `max(clock.Now(), current.UpdateTime + 1µs)` (truncated to microseconds — the precision of the persistent `TIMESTAMPTZ` column), so two writers that read the same document simultaneously can no longer both present the same token: the first commit advances it and the second aborts. Under a live (or offset) clock `clock.Now()` already advances between writes, so the conditional advance is a no-op.

We evaluated content-hash version tokens and rejected them (a document that changes and then reverts produces the same hash — the classic ABA problem), and a second internal version counter decoupled from `UpdateTime` (real GCP's `Precondition` proto carries only `exists`/`update_time`, and official clients read and pass forward the real `updateTime`), so the monotonic `UpdateTime` guard is the token both transports already agree on.

### Firestore: change streams are a stored configuration, not a feed

`projects.databases.changeStreams` (create/get/list/delete) is served as a durable **configuration** resource: the emulator validates and stores the change stream — `changeStreamId` grammar (4–63 characters, lowercase letters/digits/hyphens, letter-first, letter-or-digit-last), a required `retentionPeriod` of 1–7 whole days, exactly one scope (`databaseScope` or `collectionGroupScope.collectionGroupId`) — enforces the documented uniqueness rules (one database-scoped stream per database, one per collection group) and echoes the record back with `createTime`/`updateTime` and an `etag` the `delete` etag precondition checks (a stale etag is `FAILED_PRECONDITION`, as on `deleteDatabase`). A duplicate id or a second stream for the same scope is `ALREADY_EXISTS`; a deleted stream reads back `NOT_FOUND`.

It emits **no change records**. Real Firestore records every matching mutation into a per-stream event log read back with a resume token, but admin v1 declares no read method for the stream — there is no wire surface on which a feed could be observed — and the emulator does not fabricate one. `startTime` (documented as the time recording started) is therefore left unset rather than back-dated to `createTime`. The Firestore `Listen` API remains the emulator's actual change feed.

### Firestore: the implicit `(default)` database has no location until a client creates it

Every project has an implicit `(default)` database, and the emulator materialises it on first read with its output fields (uid, timestamps, etag) but **no `location_id`**: there is no project region to source one from. A client create (`projects.databases.create` with `databaseId=(default)` — the Firebase shape `google_firestore_database { name = "(default)" }`) records the requested location and is `ALREADY_EXISTS` while a live default exists, so a default materialised only by a read and then imported into Terraform reports no `locationId` and plans a forced `location_id` replacement.

### Firestore: a database's location is creation-only and its mode needs an empty database

`Database.location_id` is fixed at creation: Firestore documents that, once you provision a database, you cannot change its location. `projects.databases.patch` (and gRPC `UpdateDatabase`) therefore accepts a masked resend of the stored value as a no-op, but a mask that names it with a different value is `INVALID_ARGUMENT`/`400` and leaves the record untouched — on the explicit path (e.g. `updateMask=locationId`), on an explicit `*` replacement and on an implied `*` (an omitted `update_mask`). `Database.type` is mutable under the precondition `database.proto` documents on `DatabaseType` ("Mode changes are only allowed if the database is empty"): the emulator applies a Native/Datastore switch while the database holds no documents and answers `INVALID_ARGUMENT` once it does. A mask that names neither field ignores a body value, per AIP-134; a mask that names a field without supplying a value is a no-op (neither field can be cleared), and `databaseEdition` is guarded like `location_id`.

### Firestore: a deleted database's id is reusable immediately

Deleting a database tombstones it (`GET` is then `404`; `showDeleted=true` still lists it with its `deleteTime`), and a create reusing that id replaces the tombstone in place — a `terraform destroy` followed by `apply`, or the delete+create half of a ForceNew replacement, therefore converges at once. Real GCP keeps a deleted database and refuses to reuse its id for about five minutes ("You cannot reuse a database ID until 5 minutes after the delete happens"); that cooldown is a server-side convenience for production safety, and the emulator deliberately does not model it, because making a dev loop wait adds friction without exercising any client-visible contract. The delete operation's response still carries the tombstoned `Database`, and `showDeleted` still reports it until a create replaces it.

The delete also removes what the database **owns**: its documents, composite indexes, collection-group fields (including TTL policies), user creds, change streams and backup schedules — a backup schedule "is owned by the database it is backing up, and is deleted along with the database". A delete → create cycle therefore starts clean (before the cascade, the orphaned schedule made the next `backupSchedules.create` answer `409 backup_schedule already exists`, and a re-created database inherited the old data). A create that replaces a tombstone re-runs the purge, which also converges state left behind by an older build. The purge runs after the tombstone write, so a store failure surfaces as an error on an already-deleted database; re-creating the id re-runs the purge and converges. The data plane does not consult the database record, so a client that *writes documents to a deleted (or never-created) database* can still create data that a subsequent create will purge.

**Backups are deliberately retained.** Firestore documents that "Deleting the source database does not automatically delete related backups": existing backups stay readable and listable until their retention window closes or a client deletes each one, and a re-created database sees them (with the old `databaseUid`) but produces no new ones because its schedule is gone.

### Firestore: one daily and one weekly backup schedule per database

`projects.databases.backupSchedules` allows "up to one daily backup schedule and up to one weekly backup schedule" per database, and `BackupSchedule.name` is OUTPUT_ONLY — the server assigns the id on both transports (a name supplied on create is ignored, as AIP-133 requires). The emulator assigns the lowest free numeric id, returns `ALREADY_EXISTS` for a second schedule of a recurrence that already exists (an unset recurrence is classified as the daily default, the same way the materializer reads it), and validates a weekly `day` (`DAY_OF_WEEK_UNSPECIFIED is not allowed`) and the documented 14-week retention maximum. An omitted retention keeps the emulator's 7-day materialization fallback. A schedule's **recurrence is immutable** ("You can update the retention period ... but you cannot update its recurrence"): a patch that would change it is `INVALID_ARGUMENT`, so the one-per-recurrence rule cannot be bypassed through an update. A deleted database's schedules are deleted with it, so the ids and recurrences are free again; backup ids carry the schedule incarnation, so a re-created schedule cannot overwrite a retained backup.

### Firestore: `ExecutePipeline` implements a read-only subset

The Firestore pipeline RPC (`google.firestore.v1.Firestore/ExecutePipeline`) is implemented over the same query engine as `RunQuery`, covering the read-only relational subset: the `collection`, `collection_group`, `database`, `documents` and `literals` source stages followed by `where` (comparison `FieldFilter`s and `and`/`or` composites), `sort`/order-by, `select`/projection, `distinct`, `limit` and `offset`. The pipeline DSL is open-ended, so any other stage (`aggregate`, `update`, `delete`, `unnest`, `find_nearest`, …) fails loudly with `codes.Unimplemented`, as do expressions the relational engine cannot represent (non-field sort keys, computed or otherwise aliased projections, and boolean functions outside the comparison/composite subset) rather than fabricating a result. `PartitionQuery` runs the request's structured query and splits the ordered result set into up to `partition_count` cursors, returning none when the query has too few documents to partition (the proto's documented signal for a single full-range partition).

### Datastore: transactions are optimistic with a read-set

The Datastore gRPC service supports real transactions using GCP's optimistic read-set model. `BeginTransaction` returns an opaque transaction handle; `Lookup`, `RunQuery`, and `RunAggregationQuery` issued with that handle record a read-set; a `Commit` with the `TRANSACTIONAL` mode re-validates every read key against current state and applies all mutations atomically. A concurrent modification to a read key aborts the whole commit with `ABORTED` (no mutations applied), and a per-mutation `base_version`/`update_time` precondition mismatch fails with `FAILED_PRECONDITION`. `Rollback` discards the transaction, and a `TRANSACTIONAL` commit without a handle (or with an unknown/expired one) is `INVALID_ARGUMENT`. Non-transactional `Commit`, `Lookup`, and `RunQuery` are fully supported. `ReserveIds` advances the ID allocator so reserved IDs are never reissued by `AllocateIds`. `RunAggregationQuery` evaluates `count`/`sum`/`avg` over the nested query (kind + filter), honors aliases, and participates in transactions.

### Datastore: `update_time` is a strict optimistic-concurrency token

A Datastore mutation may carry a `base_version` or an `update_time` conflict-detection precondition. `update_time` is the timestamp token, and it is kept **strictly monotonic per entity** even when the emulator's clock is frozen (`POST /_jaiscloud/clock` with `{"mode":"fixed",...}`): every write stamps `max(clock.Now(), current.UpdateTime + 1µs)`, truncated to microseconds (the precision of the persistent `TIMESTAMPTZ` column). Two writers that read the same entity simultaneously can therefore no longer both present the same token — the first commit advances it and the second is reported as `conflict_detected` (non-transactional) or `FAILED_PRECONDITION` (transactional) instead of silently overwriting the winner. `update_time` is returned on `EntityResult` (`lookup`/`runQuery`) and `MutationResult` (`commit`) over both REST and gRPC, so a client can read the token from a response and pass it forward as the next mutation's precondition. Under a live (or offset) clock `clock.Now()` already advances between writes, so the conditional advance is a no-op.

GQL is supported on both transports: `runQuery`/`RunQuery` accept a `gqlQuery` (`SELECT` with `WHERE`, `IN`, `IS [NOT] NULL`, `DATETIME`/`KEY`/`BLOB` literals, and named `@name`/positional `@N` bindings), and `runAggregationQuery`/`RunAggregationQuery` accept `AGGREGATE COUNT(*) | COUNT_UP_TO(n) | SUM(p) | AVG(p) OVER (SELECT ...)`. A GQL filter is translated to the same structured filter the engine already executes. Documented approximations: the emulator's query engine models only kind/filter/offset/limit, so GQL projection, `ORDER BY`, and cursor bindings are parsed/ignored, not applied; `HAS ANCESTOR`/`HAS DESCENDANT`, `CONTAINS`, and `NOT` are rejected (the same limitations the structured query surface has). Literals are accepted only when `allow_literals` is set, matching real Datastore.

Documented approximations: the query read-set tracks the returned entities' versions (real Datastore validates the query's read *range*), transactions are single entity-group, and an unused transaction handle expires after ~270 seconds (real Datastore also expires transactions).

### BigQuery: documented Standard SQL subset (single in-process SQLite engine)

`jobs.query` and `jobs.insert` (query configuration) evaluate a bounded BigQuery **Standard SQL subset** on a single in-process, pure-Go SQLite engine (`modernc.org/sqlite`) in both memory and `--dsn` modes, and encode results into the Discovery `jobs.query`/`getQueryResults` shapes with plan-inferred column types. Supported: `SELECT`/`WHERE`/`GROUP BY`/`HAVING`/`ORDER BY`/`LIMIT`/`OFFSET`/`DISTINCT`, `INNER`/`LEFT` joins, subqueries, CTEs, `UNION ALL`, aggregates (`COUNT`/`SUM`/`AVG`/`MIN`/`MAX`), window functions, a bounded string/math/null function set (`LENGTH`/`UPPER`/`LOWER`/`SUBSTR`/`TRIM`/`LTRIM`/`RTRIM`/`REPLACE`/`INSTR`/`ABS`/`ROUND`/`COALESCE`/`NULLIF`/`IFNULL`), FLOAT64 division, and DDL/DML (`CREATE`/`DROP` dataset/table, `CREATE TABLE … AS SELECT`, `INSERT`/`UPDATE`/`DELETE`/`TRUNCATE`). The **store stays the source of truth**: SQL writes go through the store and SQLite is disposable per-query scratch, never persisted, so snapshots/export/import/`--dsn` durability are unaffected.

Unsupported constructs — `UNNEST`/`ARRAY`/`STRUCT`, `GEOGRAPHY`, wildcard/`TABLE_SUFFIX` tables, `INFORMATION_SCHEMA`, scripting/stored procedures, `MERGE`, `SAFE.` functions, `QUALIFY`, date/format functions, DDL/DML beyond the accepted set, and legacy SQL — **fail loud** with `400 invalidQuery` instead of returning wrong rows. Documented simplifications: DDL/DML jobs complete synchronously (`jobComplete: true`); `getQueryResults` serves the immutable result materialised when the job ran, and every page token is an offset into that snapshot (writes between pages are never visible); DML execution spans are serialized so concurrent statements cannot lose updates, and `CREATE TABLE … AS SELECT` creates the table and its rows atomically; `maxResults`/`pageToken` page the result set; job-statistics/timing fields (`cacheHit`, `creationTime`, `queryId`, bytes/latency counters, ...) are not synthesized; and arithmetic/comparison type errors and division by zero fail loud with `400 invalidQuery` (the numeric INT64/FLOAT64/NUMERIC family coerces as BigQuery does; `SAFE_DIVIDE` is not in the subset). `routines` and `rowAccessPolicies` are stored CRUD resources (their wire bodies round-trip over the same store in both memory and `--dsn` modes, including the `etag` update precondition; a routine body is stored, never executed, and a row access policy predicate is stored, never enforced), while `models` remains an explicit `501` stub because the emulator executes no model training.

`tabledata.insertAll` validates rows against the table schema (missing `REQUIRED` fields and unknown fields are rejected unless `ignoreUnknownValues` is set), honors `skipInvalidRows`, and best-effort suppresses duplicate `insertId`s over a bounded, in-memory window (the dedup state is not persisted across restarts). Field *types* are not enforced, and `templateSuffix` is not supported. `tabledata.list` honors `startIndex` (offset pagination). `projects.getServiceAccount` returns a synthetic `bq-{project}@gcp-sa-bigquery.iam.gserviceaccount.com` rather than a real service account.

`jobs.insert` also accepts a **`configuration.load`** job. One or more `gs://bucket/object` sources (a plain URI, a single-`*` wildcard, or a list) — or a file uploaded through the media endpoint the official clients use for `load_table_from_file` (a `multipart/related` `jobs.insert`, or a resumable session: `POST /upload/bigquery/v2/projects/{p}/jobs?uploadType=resumable` returning a session `Location`, then `PUT` chunks with `Content-Range`) — is decoded as `NEWLINE_DELIMITED_JSON`, `CSV`, `Parquet` or `Avro`, coerced to the destination table's schema (or a supplied `configuration.load.schema`; Parquet/Avro take the file's embedded schema; CSV/JSON can derive one with `autodetect`), auto-creating the table, and written per `writeDisposition` (`WRITE_APPEND`/`WRITE_TRUNCATE`/`WRITE_EMPTY`), synchronously, with `statistics.load` (`inputFiles`/`inputFileBytes`/`outputRows`/`badRecords`) on the job. Sources are **streamed, not buffered whole**: each `gs://` object is read through the storage seam into a spool one object at a time (so a wildcard/list load peaks at one source), a `multipart/related` media part and each resumable chunk are streamed off the request rather than read into the gateway buffer, and a source spills to a temp file past 4 MiB (removed when the load finishes, fails, or the session is reset or expires); gzip CSV/JSON is decompressed as a stream. An uploaded body is capped at 256 MiB. `skipLeadingRows`, `fieldDelimiter`, `nullMarker`, `maxBadRecords`, `ignoreUnknownValues`, `useAvroLogicalTypes`, `decimalTargetTypes` and `parquetOptions.mapTargetType` are honored, and gzip-compressed CSV/JSON is auto-detected (real BigQuery's `JobConfigurationLoad` has no `compression` field). Parquet and Avro values are decoded schema-aware: a `DECIMAL(P,S)` keeps its unscaled integer and scale end to end and loads as the exact decimal string of the type `decimalTargetTypes` selects (`NUMERIC`/`BIGNUMERIC`/`STRING`, default `["NUMERIC"]`; a value the selected type cannot hold is a `400` `InvalidArgument`), a Parquet `MAP` loads as the Discovery `mapTargetType` shape (`struct { repeated struct key_value { key value } }`, or `repeated struct { key value }` with `ARRAY_OF_STRUCT`), Parquet `GEOMETRY`/`GEOGRAPHY` load into `GEOGRAPHY` as hex-encoded WKB, and Avro `map<T>`, `duration`, `decimal` and unions with more than one non-null type follow Google's Avro conversion table (a repeated `{key,value}` RECORD, 12-byte `BYTES`, and a RECORD with one nullable field per branch, respectively). Everything outside that subset — `ORC`, Parquet `VARIANT` (no documented batch-load mapping), a Parquet type/annotation combination outside the load type table, an Avro array of arrays, partitioning/clustering, a non-default `quote`, non-UTF-8 encoding, and a `jobs.insert` `uploadType=media` request (which carries no load configuration) — **fails loud** (`400`/`501`) rather than mis-loading. A data-level failure (too many bad records, or `WRITE_EMPTY` on a non-empty table) is reported in the job's `status.errorResult` (`invalid`/`duplicate`) like real BigQuery, not as an HTTP error. Note: the standalone `bq` CLI cannot reach the emulator at all (it fetches a `$discovery` document the emulator does not serve); the official-client gate is the Python `google-cloud-bigquery` `load_table_from_uri` / `load_table_from_file`.

### Cloud Scheduler: real cron engine; App Engine targets stored only

Cloud Scheduler v1 is served over REST (`cloudscheduler.googleapis.com/v1`) and gRPC
(`google.cloud.scheduler.v1.CloudScheduler`) from one transport-neutral core and store. Jobs support
`create`/`get`/`list`/`patch`/`delete` plus `pause`/`resume`/`run`. A real cron engine fires due
`httpTarget` and `pubsubTarget` jobs on the **emulator clock** (`clock.Now()`): advance the clock
(`POST /_jaiscloud/clock`) and the engine delivers on its next tick, or call
`POST /_jaiscloud/scheduler-tick` (or `jobs.run`) to fire deterministically. An `httpTarget`
delivery performs the documented HTTP request (method, headers, body, with the `X-CloudScheduler*`
headers: `X-CloudScheduler: true`, `X-CloudScheduler-JobName`, and `X-CloudScheduler-ScheduleTime` —
the run's cron slot as RFC3339, held constant across the run's retries so a target can dedupe them)
and treats a 2xx as success; a `pubsubTarget` reuses the Pub/Sub publish path, so the
message fans out to the topic's pull subscriptions. Failures are retried with exponential backoff
honoring `retryConfig.retryCount`/`minBackoffDuration`/`maxBackoffDuration`, then fall back to the
cron schedule. `:pause` and `:resume` are idempotent: repeating either answers `200` with the job
unchanged (no `FAILED_PRECONDITION`, no `userUpdateTime` bump), which is how real Cloud Scheduler
behaves and what the Terraform provider's post-create `:resume` on an enabled job relies on.
Pausing removes the run state with the next run: a `PAUSED` job answers no `scheduleTime`,
`lastAttemptTime` or `status` (measured; real Cloud Scheduler drops the next run and clears the
last attempt), and `:resume` schedules a fresh run.

Limitations: `appEngineHttpTarget` is stored and echoed but **never delivered** (the emulator has no
App Engine router) — the attempt is recorded as `Unimplemented` and is terminal: the job is attempted
once, no retries are consumed, and it waits for its next cron slot (it is never retried into a
silent drop); English-like schedules ("every 5
minutes") are not parsed (unix-cron plus `@` descriptors only; anything else is `InvalidArgument`);
`oauthToken`/`oidcToken` attach a synthetic emulator-local bearer token rather than a real Google
token; and `updateCmekConfig` is not implemented.

### Cloud Scheduler → Dataproc submit hop (demo recipe)

Real Cloud Scheduler has no Dataproc target, so the demo's periodic Spark SQL rollup is triggered by
an `httpTarget` job whose uri points at a small submitter that calls `dataproc.jobs.submit`. Verified
end-to-end by `make test-e2e-scheduler-k8s` (`tests/persistent_mode/gcp/scheduler/`, tag
`scheduler_e2e`): the gate deploys an in-cluster submitter (a Pod + ClusterIP Service running an
inline Python handler), creates a Dataproc cluster and an `httpTarget` cron job pointed at it, forces
a tick on a fixed clock, and asserts the submitter received the request with `User-Agent:
Google-Cloud-Scheduler`, `X-CloudScheduler: true`, `X-CloudScheduler-JobName`,
`X-CloudScheduler-ScheduleTime`, and an `Authorization` bearer (from the `oidcToken`), then called
`dataproc.jobs.submit` and the job reached DONE. A retry is asserted against a target that answers
500 once: the first attempt records the 500 and the `minBackoffDuration` next fire, the retry
succeeds, and both attempts carry the same `X-CloudScheduler-ScheduleTime`. The gate runs the
emulator's Spark executor in mock mode (the hop, not a Spark run); the demo can use any in-cluster
submitter (a Cloud Run service reached by its ClusterIP, a function, or a small Deployment).

### Cloud Tasks: dispatch engine over the control plane

Cloud Tasks v2 is served over REST (`cloudtasks.googleapis.com/v2`) and gRPC
(`google.cloud.tasks.v2.CloudTasks`) from one transport-neutral core and store. Queues support
`create`/`get`/`list`/`patch`/`delete` plus `pause`/`resume`/`purge` and queue IAM
(`getIamPolicy`/`setIamPolicy`/`testIamPermissions`). Tasks support `create`/`get`/`list`/`delete`
plus `batchCreate`/`batchDelete` on both surfaces (REST `tasks:batchCreate`/`tasks:batchDelete`, gRPC
`BatchCreateTasks`/`BatchDeleteTasks`, each a synchronously-completed operation) and the REST-only
`tasks:buffer`. Both `httpRequest`
(url/method/headers/body/`oauthToken`/`oidcToken`) and `appEngineHttpRequest` are accepted and
echoed, and created tasks get a `scheduleTime`, `createTime`, and default `dispatchDeadline`.

A dispatch engine delivers due `httpRequest` tasks on RUNNING queues against the emulator clock:
advance `/_jaiscloud/clock` (or `POST /_jaiscloud/tasks-tick`) to fire deterministically. Delivery
attaches the documented `X-CloudTasks-QueueName`/`-TaskName`/`-TaskRetryCount`/`-TaskExecutionCount`
/`-TaskETA` and `User-Agent: Google-Cloud-Tasks` headers, is gated by the queue's
`rateLimits` (`maxDispatchesPerSecond`/`maxBurstSize` token bucket and `maxConcurrentDispatches`),
and a 2xx response deletes the task while a failure retries with exponential backoff
(`minBackoff`/`maxBackoff`/`maxDoublings`) until `maxAttempts` (-1 = unlimited) or
`maxRetryDuration` is exhausted. `RunTask` (gRPC) / `tasks:run` (REST) forces one synchronous
attempt, bypassing the queue's paused state and rate limits.

Limitations: `appEngineHttpRequest` is stored and echoed but never delivered (no App Engine
router) — the task is attempted once, the attempt is recorded as an `Unimplemented` failure, and the
task is deleted immediately rather than retried (terminal: no retry budget is consumed, and the
failure is never a silent drop after a retry storm). A task-level `retryConfig`
overrides the queue's wholesale, and a task is deleted 31 days after its `scheduleTime` (the
maximum task retention) by the dispatch tick. REST-only `tasks:buffer` accepts a full task (the
emulator models no queue-level `httpTarget`, so a body-only buffer request is `INVALID_ARGUMENT`);
`locations.getCmekConfig`/`updateCmekConfig` are stored per project+location over REST and gRPC but
are metadata only — payloads are kept in plaintext. IAM enforcement (queue policies are stored but
not enforced) and `oauthToken`/`oidcToken` Google-token minting (a synthetic emulator-local bearer
token is attached instead) are not modelled. Rate-limit and retry state is in-memory and not
persisted across restarts; the engine polls once per second, so sustained throughput is bounded by
`maxBurstSize` per second rather than `maxDispatchesPerSecond`.

### Managed Kafka: metadata control plane, optional real broker

A cluster is a logical record; the emulator is metadata-only by default and returns the documented synthesized `bootstrap.{cluster}.{location}.managedkafka.{project}.cloud.goog` address, at which nothing listens. With `JAISCLOUD_KAFKA_BROKER_MODE=docker|k8s|native` (or a global `JAISCLOUD_EXECUTOR_MODE`), creating a cluster starts a single-node Redpanda broker — the Redpanda image as a container on the local Docker daemon for `docker` (publishing a chosen loopback port and advertising `127.0.0.1:<port>` to clients; needs only the Docker daemon, no cluster and no host `rpk` toolchain), a Pod plus a ClusterIP Service in a per-cluster namespace for `k8s` (provisioned with the cluster via the shared namespace seam, reused when it already exists, and deleted with the cluster or `/_jaiscloud/reset` only when the emulator created it; falls back to the process-wide `JAISCLOUD_K8S_NAMESPACE` when namespace RBAC is unavailable), or an `rpk redpanda start` subprocess on loopback ports for `native` — and `bootstrapAddress` becomes the broker's live endpoint; deleting the cluster reaps it. The broker is a real Kafka-wire endpoint: topic create/update/delete is mirrored onto it, topic `configs` are applied as Kafka property overrides (create sets them; update applies an incremental set/delete, and a broker-rejected key or value is returned as `InvalidArgument` with the metadata rolled back), and consumer groups are read from (and reset through) its group coordinator — `ListConsumerGroups` lists the broker's groups with their committed offsets, and get/update/delete operate on them (an offset reset while members are joined is rejected, matching real GCP). ACL create/update/add-entry/remove-entry/delete are mirrored onto the broker's Kafka ACL table too (the `aclId` resource pattern maps to a Kafka resource binding): any mutation replaces the broker's bindings for that pattern, and with no broker the ACL metadata is metadata-only. Enforcement is deliberately left to the broker: ACLs are installed but, matching the emulator's non-enforcing IAM posture, Redpanda only acts on them when its own `kafka_enable_authorization` is turned on, which stays off by default. With no broker (the default) the topic metadata remains authoritative while the consumer-group list is empty and get/update/delete return `NOT_FOUND`. Broker liveness and broker bytes are runtime state, not persisted: `/_jaiscloud/reset` stops and reaps every broker, a startup sweep removes broker Pods/Services, containers, or data dirs left by a previous instance, and `--dsn` snapshots carry only control-plane metadata — so a restarted or imported emulator never advertises a dead address. A cluster persisted across a restart (or restored from an import) re-ensures its broker lazily on the first `GetCluster` or data-plane call, and broker data is ephemeral (a k8s `emptyDir`, a native scratch dir, or a Docker container's writable layer, all removed on stop/reset). The data plane is proven end to end by the k3d gate `make test-managedkafka-broker-k8s` (`tests/persistent_mode/gcp/managedkafka-broker`): a real franz-go client runs inside the cluster, produces and consumes records across the topic's partitions at `bootstrapAddress`, joins a consumer group, commits offsets with zero lag, and the group's committed offsets are read back through the Managed Kafka API. The docker backend is proven by the local-daemon gate `make test-managedkafka-broker-docker`, which runs the same franz-go probe from the host against the broker's advertised `127.0.0.1:<port>`.

Cluster create/update/delete return a proper `google.longrunning.Operation` (`name`, `metadata` with `@type=type.googleapis.com/google.cloud.managedkafka.v1.OperationMetadata`, `done: true`, `response`) inline; the operation is also persisted under `projects/{project}/locations/{location}/operations/{id}` and served by the registered `GetOperation`/`ListOperations` handlers. That operations path is shared with Cloud Workflows' LRO surface on the single emulator host: the default host keeps it on Workflows, while the service's canonical host (`managedkafka.localhost` / `managedkafka.googleapis.com`, first DNS label `managedkafka`) serves Managed Kafka's own `GetOperation`/`ListOperations`. By default every Managed Kafka operation is returned already done, so no client needs to poll it, while in the opt-in async mode (`JAISCLOUD_LRO_MODE=async`) a poll is resolved against the Managed Kafka store.

### Google Kubernetes Engine (GKE): metadata-only cluster mock, REST + gRPC

GKE is a metadata-only mock of the v1 control plane (`container.googleapis.com`): cluster `create`/`get`/`list`/`delete` plus the GKE `Operation` records they return (`get`/`list`), node-pool `create`/`get`/`list`/`delete`/`update` and the node-pool setters (`:setAutoscaling`/`:setManagement`/`:setSize`/`:rollback`), and the cluster update/setter/rotation RPCs (`update`/`:updateMaster`/`:setAddons`/`:setLegacyAbac`/`:setLocations`/`:setLogging`/`:setMonitoring`/`:setNetworkPolicy`/`:setMaintenancePolicy`/`:setMasterAuth`/`:setResourceLabels`/`:startIpRotation`/`:completeIpRotation`/`:cancel`), served over both the REST surface and the native gRPC `google.container.v1.ClusterManager` transport (the stock `ClusterManagerClient` defaults to gRPC; the legacy `project_id`/`zone`/`cluster_id`/`node_pool_id` and the canonical `name`/`parent` addressing both work). Every mutating call returns a GKE `Operation` with the correct `operationType` and a `DONE` status by default, and the recorded fields are echoed on the next read. A cluster is stored as an instantly-`RUNNING` record (a default master version, `network`/`subnetwork`, `masterAuth.clusterCaCertificate` empty); a create that carries inline `nodePools` materializes those pools in the same call (each with its canonical `selfLink`, `RUNNING` status, the cluster's node version and its `initialNodeCount` node count) through the same core materialiser `nodePools.create` uses, so both paths assign the same fields; the duplicate-name rule is stated once there — a name repeated inside one create request is `400` and stores nothing, while `nodePools.create` with a name already taken on the cluster stays `409` — while a create that carries none gets the generated `default-pool`, built from the legacy `initialNodeCount`/`nodeConfig` pair (Discovery: the config "will be used to create a NodePool object with an auto-generated name"), so it carries the same `selfLink`/`RUNNING` status/version/node count and the caller's `nodeConfig` as its `config`. Combining `nodePools` with a legacy default-pool field is rejected the way real GKE rejects it — a positive `initialNodeCount` returns `400` "It's invalid to specify both cluster.initial_node_count and a node pool. Please only provide a node pool.", a `nodeConfig` returns the same with `cluster.node_config` (it wins when both are set), and `initialNodeCount: 0` ("no default node pool") is accepted ([real-GCP capture](docs/gcp/gke-create-pool-conflict.md)). A *negative* cluster-level `initialNodeCount` is `400` "Cluster.initial_node_count must be zero or higher." only when the request carries no `nodePools`; with pools the value is accepted and ignored, exactly as real GKE behaves. On read the cluster-level `nodeConfig` is rendered from the first node pool's `config` (Discovery: "this field will be populated with the node configuration of the first node pool"), so the legacy create shape round-trips; a node pool's own `config` is fully populated even when the create named none — `machineType` `e2-medium`, `imageType` `COS_CONTAINERD`, a 100 GB `pd-balanced` boot disk, the project's `default` service account and the six default OAuth scopes (captured in [gke-node-pool-config-defaults.md](docs/gcp/gke-node-pool-config-defaults.md)) — and a node-pool read carries the same rendering as the cluster read. The read also renders the nested response messages real GKE always returns and clients dereference unconditionally — `legacyAbac.enabled` (`false` unless `:setLegacyAbac` enabled it), `networkConfig.network`/`subnetwork` (the relative resource names derived from `network`/`subnetwork` whatever spelling the caller used — a short name, a project-relative partial resource name or a Compute self-link, with a zone reduced to its region and the link's own project kept so a Shared-VPC host project is not rewritten into the cluster's), `shieldedNodes.enabled` (on by default, honouring a create-time `false`), `defaultMaxPodsConstraint.maxPodsPerNode` (`110` by default, honouring a create-time value) and the `logging.googleapis.com/kubernetes`/`monitoring.googleapis.com/kubernetes` service defaults — which is what makes `google_container_cluster` usable against the emulator (the provider dereferences four of them on its read). `autopilot.enabled` and `workloadIdentityConfig.workloadPool` are recorded at create and echoed on read, because a Dataproc-on-GKE create validates them (a standard, Workload-Identity-enabled cluster is required); `nodeConfig.accelerators` (`acceleratorCount`/`acceleratorType`/`gpuPartitionSize`) and `nodeConfig.bootDiskKmsKey` are stored and echoed on create, node-pool create and update; a `bootDiskKmsKey` outside the documented `projects/{p}/locations/{l}/keyRings/{r}/cryptoKeys/{k}` form, or an accelerator entry with no type or a non-positive count, is `400`. `getServerConfig` is served on both transports as a derived catalog: the one Kubernetes version the mock supports as `defaultClusterVersion` and the only `validMasterVersions`/`validNodeVersions` entry, `COS_CONTAINERD` as `defaultImageType` with its `validImageTypes` peers, and the `RAPID`/`REGULAR`/`STABLE`/`EXTENDED` channel entries — on the locations path and the legacy `zones/{zone}/serverconfig` path. Discovery's `ServerConfig` has no `masterAuthorizedNetworksConfig` member and the container API documents no `projects.locations.get`/`list`, so neither is synthesized. There is **no real Kubernetes control plane** behind it and no Artifact Registry/OCI pull path, so `checkAutopilotCompatibility`, `fetchClusterUpgradeInfo`/`fetchNodePoolUpgradeInfo`, `completeControlPlaneUpgrade`/`completeNodePoolUpgrade`, `getJsonWebKeys` and `listUsableSubnetworks` remain explicit `Unimplemented` stubs on the gRPC `ClusterManager` surface (graded `unsupported`); the REST codec registers no route for them, so the coverage report lists them as not served on REST. GKE's concurrent-operation rules are modelled behind an opt-in simulated in-flight window: `JAISCLOUD_GKE_OPERATION_WINDOW` (a Go duration) makes a mutation's operation `RUNNING` — with no `endTime` — for that long, settling to `DONE` when it is next read; a mutating call that overlaps an operation still running on its target is the `400` `FAILED_PRECONDITION` real GKE answers ("Cluster is running incompatible operation <operation-id>"), and the granularity is one operation per node pool, so different pools of a cluster still mutate in parallel while a cluster-level change waits for all of them. `JAISCLOUD_GKE_CONCURRENT_OPERATIONS` caps the operations in flight per project/location and rejects the next mutation with `429` `RESOURCE_EXHAUSTED`. Left unset (the default), every operation is instant-`DONE` and both rules are inert. GKE shares the canonical `/v1/projects/{p}/locations/{l}/clusters` path with Managed Kafka on the single emulator origin, so it is disambiguated by host (a request whose first DNS label is `container`, e.g. `container.googleapis.com` or `container.localhost`) or by the `/container` path prefix Terraform/gcloud use; Managed Kafka's routing for the default host is unchanged. Two things narrow that ambiguity without a host token: GKE node-pool subpaths, the cluster/node-pool custom verbs only GKE declares (`:setAddons`, `:updateMaster`, `:setNodePoolSize`, …) and the `jwks`/`well-known/openid-configuration` paths are GKE's outright, and when a bare-host `clusters` request names a project+location where the GKE control plane actually holds a cluster the adapter routes it to GKE instead of answering with Managed Kafka's empty list. The version surface is `v1` **and** `v1beta1` (both routed to the same core and codec, on the `container` host and under `/container/`), because real GKE publishes both and `gcloud beta container` / the `google-beta` provider request `/v1beta1/`; `v1beta2` and `v1alpha1` are not published by Google any more and are not served. The Discovery wildcard parent `projects/{p}/locations/-` ("matches all zones and all regions") is honoured on `clusters.list` and `operations.list`, so a plain `gcloud container clusters list` — which sends it — lists every cluster in the project. `clusters.create` honours a pinned `initialClusterVersion`, resolving `latest` and the `1`/`1.X`/`1.X.Y` prefixes, and rejects an unsupported release with real GKE's `Master version "<v>" is unsupported.` instead of rewriting it. A Dataproc-on-GKE `gkeClusterTarget` may be regional **or zonal**: the target's own location keys the GKE lookup (a `locations/{zone}` or `zones/{zone}` target resolves), with the same-region rule still enforced.
### Cloud Run: behavioural control plane, mock runtime (REST + gRPC)

Cloud Run Admin v2 (`run.googleapis.com`) is implemented as the service/revision/IAM/operations control plane, served over both the REST surface and the native gRPC `google.cloud.run.v2.Services`/`google.cloud.run.v2.Revisions` transports (the stock Go/Java `run` client defaults to gRPC): service `create`/`get`/`list`/`update` (PATCH, `updateMask`)/`delete`, revision `list`/`get`/`delete` (one revision per create, bumped on a template-changing update; only a **retired** revision can be deleted — deleting the one serving traffic is a `FAILED_PRECONDITION`, per the API's contract), service IAM (`getIamPolicy`/`setIamPolicy` with etag OCC /`testIamPermissions` — metadata only, authorization is not enforced), and the `google.longrunning.Operation` records the mutations return (`get`/`list`/`wait`/`delete`/`cancel`; `metadata`/`response` typed `Any`s carry the `Service`, or the `Revision` for a revision delete). Service `create`/`update`/`delete` and revision `delete` honor `validateOnly` (a dry run validates, previews the resource inline and persists nothing), service `update` honors `allowMissing` (upsert), and a delete honors the request `etag` (an `update` the service body `etag`) as an `ABORTED`/409 optimistic-concurrency precondition. Every mutation returns a **done** operation inline; with `JAISCLOUD_LRO_MODE=async` the operation is persisted in-flight and settled lazily on read. The synthesized `uri` is `https://{service}-{token}.{location}.run.app` (override the suffix with `JAISCLOUD_CLOUDRUN_URL_SUFFIX`); the token is a 12-hex-char SHA-256 prefix of the project, as in real GCP.

The runtime is behind a `RuntimeManager` seam. By default it is a **mock**: nothing is scheduled and a request addressed to a generated `*.run.app` host resolves `503` (no ready runtime), so a service is a stored metadata record. Set `JAISCLOUD_CLOUDRUN_EXECUTOR_MODE=k8s` (or `JAISCLOUD_EXECUTOR_MODE=k8s`) to run the **k8s executor**: each revision's template image is launched as a Pod + ClusterIP Service (via the shared `internal/k8shelpers` workload lifecycle, also used by Managed Kafka), with `PORT`/`K_SERVICE`/`K_REVISION`/`K_CONFIGURATION` injected; the executor waits for the container port and reverse-proxies data-plane requests to it. Set `JAISCLOUD_CLOUDRUN_EXECUTOR_MODE=docker` to run the **docker executor** instead: each revision's image is launched as one container on the local Docker daemon (dialled over `/var/run/docker.sock`; a `DOCKER_HOST` override is ignored, matching the Lambda/ECS executors) with an ephemeral published loopback port and the same injected environment, and the proxy dials `127.0.0.1:<port>`. When the emulator itself runs as a container (`JAISCLOUD_DOCKER_MODE=container`, as `docker-compose.yml` sets), nothing is published: the revision joins `JAISCLOUD_DOCKER_NETWORK` and the proxy dials the container name, since a host-published port is unreachable from the emulator's own network namespace (CDE1). Both executors tear down the same way and share the routing/proxy code, so they cannot drift. In docker/k8s mode the synthesized `uri` becomes `http://{service}-{token}.{location}.{suffix}[:port]` (suffix from `JAISCLOUD_CLOUDRUN_URL_SUFFIX`, external port from `JAISCLOUD_CLOUDRUN_URL_PORT`) so a client can send the authority back as a `Host` header. Revisions are always-on: a runtime is torn down only on service delete, a template-changing update, `/_jaiscloud/reset`, or the startup orphan sweep (there is no idle reaper). The proxy maps a missing service to `404`, no ready runtime to `503`, a connection failure to `502`, and a timeout to `504`. Cloud Run shares the `/v2/projects/{p}/locations/{l}` namespace with Cloud Functions and Cloud Tasks on the single emulator origin, so it is claimed by resource segment (`services`/`revisions`) and by run-prefixed operation ids (`operation-run-<uuid>`); the bare `.../operations` list path is path-ambiguous and stays with Cloud Functions by design (run operations remain reachable by their prefixed id), and Terraform/gcloud reach the same surface under a `/run` path prefix; the gRPC surface is the same core, so the transports cannot drift, and the stock `run/apiv2` client is gated by the gRPC conformance suite. Jobs, WorkerPools, traffic splitting, autoscaling/scale-to-zero, sidecars, secrets/Cloud SQL/emptyDir volumes, custom domains, probes and IAM invocation enforcement are not modelled. The execution paths are verified end to end by `make test-e2e-cloudrun-k8s` (k3d, `tests/persistent_mode/gcp/cloudrun/`) and `make test-e2e-cloudrun-docker` (local Docker, same suite); the optional floci-gcp Java interop smoke suite (`make test-e2e-cloudrun-java`) is corroborating evidence only, not a compliance gate.

**Browser reachability (SPK4).** A browser cannot set an arbitrary `Host` header, so it cannot address a synthesized data-plane authority while the default suffix (`*.run.app`) does not resolve. To open a deployed service's page (the demo's leaderboard) from a browser, set `JAISCLOUD_CLOUDRUN_URL_SUFFIX=run.localhost` and `JAISCLOUD_CLOUDRUN_URL_PORT` to a host-forwarded port, then forward that port to the emulator's REST port (`kubectl -n jaiscloud port-forward svc/jaiscloud-gcp 18080:8080`); every `*.localhost` name resolves to loopback, so `http://{service}-{token}.{location}.run.localhost:18080/` loads the service at the authority the API reports. If an on-camera `.run.app`-shaped host is wanted instead, add a hosts entry (`{service}-{token}.{location}.run.app 127.0.0.1` — per host, no wildcard) or put a `Host`-preserving reverse proxy in front of the emulator. Gated by `make test-e2e-cloudrun-browser` (`tests/persistent_mode/gcp/cloudrun/`, tag `cloudrun_e2e`), which dials the synthesized `*.localhost` authority with no `Host` override.

**Browser reachability from a remote recording machine (SPK7).** The `*.localhost` recipe only works on the emulator host — anywhere else it resolves to the *viewer's* loopback, so it cannot reach a remote emulator's data plane. To record the demo from a browser on another machine, serve the data plane on the emulator host's LAN address under a **nip.io wildcard authority**: set `JAISCLOUD_CLOUDRUN_URL_SUFFIX=run.<lan-ip>.nip.io` and `JAISCLOUD_CLOUDRUN_URL_PORT=<rest-port>`, then forward the REST port on every interface (`kubectl -n jaiscloud port-forward --address 0.0.0.0 svc/jaiscloud-gcp 8080:8080`). Any name under `run.<lan-ip>.nip.io` resolves (public wildcard DNS) to the emulator host's LAN IP, so `http://{service}-{token}.{location}.run.<lan-ip>.nip.io:8080/` loads the service and the browser sends the `Host` the data plane routes on — no `/etc/hosts` edit, no proxy. `make demo-browser-lan` applies the config, checks the LAN address, and keeps the `0.0.0.0` forward up for the recording; gated by `make test-e2e-cloudrun-browser-lan`, which dials the nip.io authority with no `Host` override. Fallbacks: a per-host hosts entry or a `Host`-preserving reverse proxy in front of the emulator.

**Recording take (SPK7).** `make record-gcp-demo` (`scripts/demo-record.sh`) captures the take from an isolated `Xvfb :99` display with real OS cursor/clicks: it starts Xvfb, opens the page in Chrome (`--kiosk --app`), records with `ffmpeg -f x11grab -draw_mouse 1` and verifies the result with `ffprobe`. ### Cloud Monitoring: alert policies are evaluated for `condition_threshold` and `condition_absent`

Alert policies are evaluated by a background worker (30s tick, matching the AWS CloudWatch alarm evaluator). Two condition types are evaluated: **`condition_threshold`** and **`condition_absent`**. `condition_matched_log`, `condition_monitoring_query_language`, `condition_prometheus_query_language`, and `condition_sql` are stored but never evaluated (and never fire).

The policy's output-only `creationRecord`/`mutationRecord` audit messages are always served on both transports, derived from the stored create/update clock and the documented default service identity — never from a request body, whose supplied record is ignored. Every `conditions[].name` is assigned server-side (`projects/{p}/alertPolicies/{policy}/conditions/{position}`): a name supplied at create is ignored, while an update that names an existing condition keeps that name (`alert.proto` `AlertPolicy.Condition.name`), so a read-modify-write keeps condition identities stable.

For `condition_threshold`, the evaluated filter subset is equality clauses joined by `AND` on `metric.type`, `resource.type`, `metric.label.{key}`, and `resource.label.{key}`; unknown clauses are ignored. The matching series' latest point in each alignment window is reduced across series (`REDUCE_SUM`/`MEAN`/`MAX`/`MIN`/`COUNT`, default mean), then compared to `threshold_value`; `duration` requires the comparison to hold across every alignment window it spans, and `trigger` count/percent is honored when no reducer is set.

For `condition_absent`, the same filter subset is used: a matching series is treated as **absent** when it has no data point within the condition's `duration` window, and `trigger` count/percent selects how many absent series are required (when unset, any absent series fires — the real "Any time series violates" default). Mirroring real Cloud Monitoring, a metric that has **never** produced a measurement does not fire (absence requires prior data), and the condition's per-series aligner / cross-series reducer / `group_by_fields` are not applied to the absence evaluation.

A firing policy opens an incident and delivers notifications. An open incident is closed — and a resolution notification delivered — when the policy stops firing: for `condition_threshold`, a below-threshold evaluation or a window with no matching data; for `condition_absent`, fresh data (a point inside the window). Incidents have no public API, so they are observable via the snapshot/export surface, the logs, and — for a `pubsub` channel — the topic's subscriptions. A `pubsub` channel publishes the Cloud Monitoring notification packet (schema **version 1.2**: `{"version":"1.2","incident":{...}}` with lowercase `state`, `incident_id`, `policy_name`, `condition_name`, `started_at`/`ended_at`) through the normal Pub/Sub fan-out on `labels.topic`, so every pull subscription, push endpoint, and Cloud Functions trigger on the topic receives a copy (a missing topic fails the delivery, as in real Pub/Sub); `email`/`webhook`/`sms` notifications are recorded on the incident and logged but not sent. `POST /_jaiscloud/monitoring-tick` runs one evaluator pass synchronously, so a test or the demo does not wait for the 30s ticker (mirrors `/_jaiscloud/scheduler-tick`); the end-to-end gate is `TestMonitoringAlertPolicyFiresIncident` in `tests/integration/gcp/monitoring_alert_test.go`.

`GetMonitoredResourceDescriptor` serves a canonical catalog of well-known types (`gce_instance`, `gcs_bucket`, `pubsub_topic`, `pubsub_subscription`, `k8s_container`, `k8s_pod`, `k8s_node`, `dataproc_cluster`, `cloudsql_database`, `api`); an unknown type returns `NotFound`. `CreateServiceTimeSeries` mirrors `CreateTimeSeries` — in real GCP the two differ only in the identity/permission used, and the emulator has no authz plane. `DISTRIBUTION`-typed point values (linear/exponential/explicit buckets, bucket counts, count, mean, sum of squared deviations, optional range and exemplars) round-trip through `CreateTimeSeries`/`ListTimeSeries`. `ListMetricDescriptors`/`ListMonitoredResourceDescriptors` honor a discovery filter subset — equality (`type = "x"`, `metric.type = "x"`, `resource.type = "x"`) and `starts_with("prefix")` clauses joined by `AND`, over the descriptor type or its `name`; any other key, operator, or malformed clause fails with `InvalidArgument`. `ListTimeSeries` supports a `metric.type`/`resource.type`/label equality and `starts_with` filter subset and requires the filter to constrain exactly one `metric.type` (a filter matching more than one metric is rejected with real Monitoring's message); per-series alignment and cross-series reduction are applied, with aligned buckets anchored on the request interval's end time. The full Monitoring Query Language is not implemented. `NotificationChannelService` supports CRUD for `pubsub`/`email`/`webhook`/`sms` channels. `ListNotificationChannelDescriptors`/`GetNotificationChannelDescriptor` serve a static catalog of well-known channel types (`email`, `sms`, `pubsub`, `webhook_tokenauth`, `slack`); an unknown type returns `NotFound`. `SendNotificationChannelVerificationCode` is a no-op success (the emulator delivers nothing), `GetNotificationChannelVerificationCode` returns a deterministic synthetic code, and `VerifyNotificationChannel` marks the channel `VERIFIED`.

### Cloud Monitoring: uptime check configurations are stored, never probed

`google.monitoring.v3.UptimeCheckService`'s `uptimeCheckConfigs` resource is the control-plane half of uptime checks, and the emulator serves it declaratively over both transports: `create`/`get`/`list`/`patch`/`delete` (REST `/v3/{parent}/uptimeCheckConfigs…` and gRPC `UptimeCheckService`). A configuration is validated against the Discovery schema (required `display_name`, exactly one of `monitored_resource`/`resource_group`/`synthetic_monitor`, `timeout` between 1s and 60s, `period` one of 60s/300s/600s/900s, the documented HTTP content-type/request-method consistency rules, and the server-assigned `name`), stored in the shared resource store (so it survives `--dsn` restarts and snapshots), and returned exactly as declared — no field is invented. `patch` honours the Discovery document's `update_mask` contract: an empty mask replaces the whole configuration, a non-empty one updates only the listed paths (proto `snake_case` and REST `camelCase` spellings both resolve, a nested path such as `httpCheck.path` merges inside that message, and an omitted masked field is cleared), and a path naming no field is `INVALID_ARGUMENT`. This is what makes `terraform apply`/`destroy` of `google_monitoring_uptime_check_config` work end to end (`make test-gcp-terraform`).

What the emulator cannot do is run the check: there is no egress probe plane, so **no** probe result is fabricated. The probe-derived surfaces stay explicit `UNIMPLEMENTED` (`501` over REST, `UNIMPLEMENTED` over gRPC): `uptimeCheckIps` (the static checker address list). A stored configuration therefore never reports checker state or uptime results, and an alert policy that references an uptime check is stored but never evaluated against one. `delete` also does not refuse a configuration referenced by an alert policy (real Monitoring fails such a delete) because the emulator does not track the reference.

### Cloud Logging: `TailLogEntries` is a bounded polling approximation

`ListMonitoredResourceDescriptors` returns the canonical catalog of well-known monitored resource types shared with the Monitoring service (`gce_instance`, `gcs_bucket`, `pubsub_topic`/`subscription`, `k8s_container`/`pod`/`node`, `dataproc_cluster`, `cloudsql_database`, `api`), each with `type`, `display_name`, `description`, and `labels`; `page_size`/`page_token` are honored. Unlike Monitoring, the Logging descriptors leave `name` unset, and the `ListMonitoredResourceDescriptorsRequest` in this proto revision carries no `parent` or `filter` fields (only page size/token), so the catalog is global and unfiltered.

`TailLogEntries` is implemented as a **bounded, store-polling** tail rather than a true push feed. After accepting the initial `resource_names`/`filter`/`buffer_window`, the server records the store's monotonic write id as its cursor and re-reads the store on a timer derived from `buffer_window`, streaming entries written after the stream began whose fields satisfy the same filter engine `ListLogEntries` uses. This is the closest correct behavior the emulator's store allows, and it never returns `Unimplemented` and never busy-spins. The documented deviations from real Cloud Logging are:

- **Delivery is at-most-once against each read snapshot**, not the real API's at-least-once. An entry inserted with a higher store id is emitted exactly once; a client that disconnects before the next poll does not get it, and there is no server-side retention or replay.
- **`buffer_window` is realized as the poll interval**, not as a reordering buffer. The emulator's store already returns entries in `(timestamp, id)` order, so there are no late-arriving out-of-order entries to absorb; the window only controls latency. Absent/`nil` uses the real 2 s default, explicit `0` is clamped to 50 ms to avoid a spin, and values are capped at 60 s (the spec's maximum).
- **Filter (and project) changes on further client requests are applied** to subsequent polls; a project change re-seeds the id cursor so the new project's pre-existing backlog is not replayed.
- The session terminates cleanly on client half-close (`Recv` → `EOF`) or context cancel.

### Cloud Logging: sinks and exclusions are configured, routing is evaluated (not delivered)

The config plane is implemented over both transports for **sinks** (`sinks.create`/`get`/`list`/`update`/`patch`/`delete`, gRPC `CreateSink`/`GetSink`/`ListSinks`/`UpdateSink`/`DeleteSink`) and **resource-level exclusions** (`exclusions.create`/`get`/`list`/`patch`/`delete`, gRPC `ConfigServiceV2` exclusions). Sinks and exclusions are project-scoped and persisted (memory + Postgres + snapshots); the sink's inline `exclusions` and the `writer_identity` output field round-trip, and masked updates honor the REST `updateMask`/gRPC `FieldMask` paths (`destination`, `filter`, `description`, `disabled`, `exclusions`, `include_children`). A filter that the emulator's advanced-log subset cannot parse is rejected at write time (`InvalidArgument`) rather than silently routing nothing.

`WriteLogEntries` **evaluates** routing: resource-level exclusions are applied first, then each enabled sink's inline exclusions, then the sink filter, and the matched sink resource names are recorded (debug log). The emulator has **no export destination delivery** — no bytes are written to the sink's bucket/dataset/topic — so a sink is configuration + routing evaluation only. Sink/exclusion filters use the same filter engine as `ListLogEntries` (the documented subset), so filters the engine does not understand are rejected loud. The gRPC `ConfigServiceV2` bucket/view/link, CMEK/settings, and `CopyLogEntries` RPCs are explicit `Unimplemented` stubs (the emulator has no log-bucket storage plane).

### Cloud Logging: logs-based metrics are definitions, not computed time series

Logs-based metrics are implemented over both transports (`metrics.create`/`get`/`list`/`update`/`delete`, gRPC `MetricsServiceV2` `CreateLogMetric`/`GetLogMetric`/`ListLogMetrics`/`UpdateLogMetric`/`DeleteLogMetric`). A metric is a project-scoped, persisted definition (`filter`, `description`, `disabled`, `bucket_name`, `value_extractor`, `label_extractors`, `bucket_options`, and the descriptor's `metric_kind`/`value_type`/`unit`/`display_name`/`labels`) stored in the memory and Postgres backends and included in snapshots/export/import. The filter is compiled by the same advanced-log engine as `ListLogEntries`, so an unparseable filter is rejected at write time (`InvalidArgument`); a `DISTRIBUTION` metric requires a `value_extractor`, and every descriptor label must have a matching `label_extractors` entry (and vice versa).

The output-only `metric_descriptor.name`/`type`/`description` are synthesized from the metric id/description (`logging.googleapis.com/user/{METRIC_ID}`), and `metric_kind`/`value_type` are immutable across updates (existing label value types are too; new labels may be added). The emulator **does not compute metric time series** — there is no Monitoring writer on the log write path — so a logs-based metric is a definition only. Metric ids may contain slashes (e.g. `nginx/requests`); the id is percent-encoded (`%2F`) in the canonical resource name and accepted either encoded or raw on a read.

### Cloud KMS: rotation schedule is executed lazily on read

`CryptoKey` `labels`, `rotationPeriod`, and `nextRotationTime` are persisted and returned by both the REST and gRPC surfaces. A `rotationPeriod` is an automatic rotation schedule: when set, `nextRotationTime` is derived (`createTime + rotationPeriod` on create, `now + rotationPeriod` on update) and clearing the period clears `nextRotationTime`. `UpdateCryptoKey` honors the `labels` and `rotation_period` update-mask paths (unmasked fields are preserved); any other path fails loud with `Unimplemented`.

The schedule **is** executed, lazily on read (the emulator has no background scheduler): when a due key is read (`GetCryptoKey`/`ListCryptoKeys`, and `Encrypt` before it resolves the primary), a new ENABLED `CryptoKeyVersion` is created, made the primary, and `nextRotationTime` advances to `now + rotationPeriod`. A key therefore rotates on its next read after the schedule comes due. Because the schedule advances to `now + rotationPeriod` rather than by one period per elapsed interval, a clock jump far past the due time is coalesced into a single rotation — a deliberate approximation. Cloud KMS **managed/external** rotation (external key managers, `rotate-master-key`) remains out of scope; key import itself is supported (see below).

The gRPC KMS surface also implements the delete side (`DeleteCryptoKeyVersion`, `DeleteCryptoKey`, plus the `RetiredResource` records that block name reuse), the raw AES-GCM primitives (`RawEncrypt`/`RawDecrypt`, purpose `RAW_ENCRYPT_DECRYPT`), and the full key-import surface. Key-ring deletion is **REST-only**: the Cloud KMS Discovery documents `projects.locations.keyRings.delete` (`DELETE v1/{+name}`, an LRO) but the `google.cloud.kms.v1.KeyManagementService` proto declares no `DeleteKeyRing` RPC, so no generated gRPC client can call it. The REST method permanently deletes an **empty** key ring (a ring that still holds a `CryptoKey` is `400 FAILED_PRECONDITION`, mirroring `cryptoKeys.delete`'s version precondition), answers the inline-done `Operation` with an empty response, and leaves the ring's name reusable — Discovery's `RetiredResource` models deleted `CryptoKeys` only, so the retired crypto-key records of a deleted ring stay behind and those key names remain unusable. `ImportJob`s (`CreateImportJob`/`GetImportJob`/`ListImportJobs`) expose the wrapping key; `ImportCryptoKeyVersion` unwraps caller-supplied material (RSA-OAEP, optionally with an AES-KWP RFC 5649 layer, or the post-quantum HPKE-KEM methods) and creates a version; the `ImportTrustedKeyWrappedCryptoKeyVersion`/`ExportTrustedKeyWrappedCryptoKeyVersion` pair wraps and unwraps key material with an HSM AES-256-KWP key for EKM trusted wrapping; and `Decapsulate` recovers shared secrets for the KEM key types (`ML_KEM_768`, `ML_KEM_1024`, `KEM_XWING`), with `GetPublicKey` returning the raw NIST-PQC / X-Wing encapsulation key. These are served on **both** transports (REST `cryptoKeyVersions:import`/`:decapsulate`/`:importTrustedKeyWrappedCryptoKeyVersion`/`:exportTrustedKeyWrappedCryptoKeyVersion` and `importJobs`).

Trusted wrapping enforces the Discovery rules on both transports. `trustedWrappingEnabled` — the `cryptoKeys.create` query parameter / `CreateCryptoKeyRequest.trusted_wrapping_enabled`, the `CryptoKeyVersion` field on `CreateCryptoKeyVersion`, and `ImportCryptoKeyVersionRequest.trusted_wrapping_enabled` — requires a version template at `HSM_SINGLE_TENANT` and is rejected with `INVALID_ARGUMENT` for `ENCRYPT_DECRYPT` keys; on key create it lands on the implicit first version. An `importing_key` (import) or `wrapping_key` (export) must be an **ENABLED** `AES_WRAPPING` key with the `AES_256_KWP` algorithm at `HSM_SINGLE_TENANT` (`hsm_trusted`), or the call fails `FAILED_PRECONDITION`; `importing_key` may name a `CryptoKey` (its primary version is used) or a `CryptoKeyVersion`, as the Discovery documents. The export response is the documented `wrappedKey` + `wrappedKeyCrc32c`.

Still out of scope: EKM connection/instance control planes (`ekmConnections`, `singleTenantHsmInstances`), Cloud KMS **managed/external** rotation, and EKM key material itself. External key material is created and stored in the customer's EKM and "is never shared with Google" (<https://cloud.google.com/kms/docs/ekm>); there is no API that exports it. An `EXTERNAL`/`EXTERNAL_VPC` key or version therefore fails loud with `UNIMPLEMENTED` (501) instead of fabricating SOFTWARE material, and reimporting into an existing `CryptoKeyVersion` (`ImportCryptoKeyVersionRequest.crypto_key_version`) is likewise `UNIMPLEMENTED` rather than silently creating a new version.

A cryptoKey's IAM policy is enforced on its crypto operations (`encrypt`/`decrypt`/`asymmetricSign`/`asymmetricDecrypt`/`macSign`/`macVerify`/`getPublicKey`), **default-permissively**: a key with no policy — or with no bindings — allows every operation, and only a policy scoped to roles that omit the required `cloudkms.cryptoKeyVersions.useTo*` permission returns `403 PERMISSION_DENIED`. Binding **members** and **conditions** are not evaluated (the emulator does not resolve the caller's identity), mirroring the AWS KMS emulator's key-policy check. Identity IAM remains shape-only (see [wire-contract.md §8](docs/gcp/wire-contract.md#8-accepted-risks)).

### Secret Manager: regional secrets use a location-qualified namespace

Regional secrets (`projects.locations.secrets`) are served on both transports with the same `Secret`/`SecretVersion` messages and the location in the resource name. A regional secret has no replication policy (the location is its storage location), so `replication` is rejected and the CMEK configuration is the top-level `customerManagedEncryption` field, whose key must reside in the secret's own location; a version reports the top-level `customerManagedEncryption` status instead of a `replicationStatus`. The store keys a regional secret by its location-qualified relative name, so a project-level `secrets.list` returns the global secrets only and a location-scoped list returns that location's secrets. The bare `projects.locations.get`/`list` discovery methods remain unserved: on a single origin that path is shared by every location-scoped service, so it cannot be attributed to Secret Manager.

### Secret Manager: rotation is stored, managed rotation is emulated without a Cloud SQL data plane

A `Secret`'s `rotation` schedule (`nextRotationTime` + `rotationPeriod`) is persisted and honored by a background sweep on both transports: at `nextRotationTime` a `SECRET_ROTATE` notification is published to the secret's topics and the schedule advances, with no client read required (ordinary rotation never creates a version — Cloud SQL managed rotation does). The same sweep proactively deletes expired secrets (`SECRET_DELETE`, `deleteType: EXPIRATION`) and applies due delayed version destruction (`SECRET_VERSION_DESTROY`); every read also enforces those due instants immediately, so an unread or not-yet-swept record cannot be accessed past its boundary. Cloud SQL **managed rotation** is served on both transports (`secrets:enableManagedRotation` / `secrets:rotateSecret` on REST, `EnableManagedRotation` / `RotateSecret` on gRPC): enabling validates the Cloud SQL single-user credentials, records the managed-rotation config and status (`managedRotationStatus.state = ACTIVE`) and stores a generated password as a new secret version; `rotateSecret` then adds a fresh password version. Enabling is one-shot and rotating requires it (both fail `FAILED_PRECONDITION` otherwise), and a schedule update preserves the managed-rotation status (it is output-only). Because the emulator has no Cloud SQL data plane, the generated password is not applied to a database user — it is only stored as the secret version (the linked Cloud SQL instance is metadata-only; see GA7-D1).

### Cloud Workflows: synchronous execution, AIP-160 filters

Cloud Workflows is implemented over a real YAML expression engine: workflow definitions and executions are stored, and `executions.create` runs the workflow synchronously and returns it already in a terminal state (there is no asynchronous execution queue). Workflow/execution `filter` and `orderBy` use the shared AIP-160 subset, and `operations.list` evaluates the standard `done`/`name`/`state`/metadata filter (AND/OR/NOT, implicit AND and parentheses) through the shared operations compiler; a `switch` with no matching condition fails the execution loudly; `http.*` auth is not modelled; `retry.predicate` fails loud; and subworkflows, IAM, and CMEK are not implemented.

### Dataproc workload placement: one Kubernetes namespace per cluster

A cluster may be created with a `virtualClusterConfig` (Dataproc-on-GKE) instead of a `config` (Dataproc-on-Compute-Engine). The emulator validates the virtual cluster's structure — `kubernetesClusterConfig.gkeClusterConfig.gkeClusterTarget` or a non-empty `nodePoolTarget` is required, supplying both `config` and `virtualClusterConfig` is `InvalidArgument` — and so is supplying neither, since Discovery requires exactly one of the two — and the `GkeNodePoolTarget` rules are enforced: `nodePool` must be the full `projects/{project}/locations/{location}/clusters/{cluster}/nodePools/{pool}` resource name (a bare pool id is `InvalidArgument`, as on real GCP), roles are required and enumerated, each role may be given to only one target, at least one target must be `DEFAULT`, Spot/preemptible nodes are rejected on a `CONTROLLER` target and on `DEFAULT` when no `CONTROLLER` exists, `autoscaling` must satisfy `0 <= minNodeCount <= maxNodeCount` with `maxNodeCount > 0`, and every pool must sit in one zone of the cluster's region. Unknown sub-fields are accepted and preserved. The GKE v1 control plane **is** emulated (see [GKE](#google-kubernetes-engine-gke-metadata-only-cluster-mock-rest--grpc)), and the Dataproc path **reconciles against it**: `gkeClusterTarget` is resolved at create (same project and region, must exist, must be a standard — not Autopilot — cluster with Workload Identity enabled, else the create is rejected; when the request names node pools but no target, the target is taken from the pools' resource names, which must all name one cluster), and every target — including the `default-pool` synthesized when the request names a target but no pools — is created through the GKE API with the requested shape and the `goog-dataproc-cluster-name`/`-cluster-uuid`/`-location`/`-environment` auto labels — or, when the pool already exists, verified field by field and adopted as-is if the caller sent no `nodePoolConfig`. A pool the service creates gets the documented autoscaler defaults (min 1, max 10). A mismatch does not fail the create: the request is accepted, the cluster is persisted in `ERROR` with a `status.detail` naming the pool and field, and the create's long-running operation completes successfully carrying that `ERROR` cluster as its response ([wire contract](docs/gcp/wire-contract.md#5-explicitly-non-ga-surfaces)). `nodePoolConfig` is input-only and is never returned by a read. Node pools are **not** deleted with the virtual cluster, and the virtual cluster is not scheduled onto a GKE cluster — its jobs run on the configured executor backend (k8s, docker or mock), and there is no autoscaler behaviour or drift detection behind the recorded pools.

A virtual cluster is **recreate-only**: `clusters.patch` may update labels and the worker-instance counts of a GCE cluster, but a patch whose `updateMask` applies `virtualClusterConfig` or `config` is `InvalidArgument` — the release-note rule real GCP follows, and it is why the documented recipe drops `kubernetesNamespace` and re-creates. The mask decides, as it does for the persisted fields: an empty mask means "everything supplied applies", so an unmasked patch carrying either placement field is rejected, while a full resource sent under a `labels`-only mask is applied for labels and leaves the placement alone. The effective namespace defaults to the cluster name, and a second live virtual cluster claiming a namespace already owned on the same GKE cluster is `FailedPrecondition` ("`kubernetesNamespace … is already used by Dataproc virtual cluster …`"); dropping the namespace (so it defaults to the new cluster's name) is what makes delete-then-recreate work. `kubernetesSoftwareConfig` is optional, and a present one must carry a non-empty `componentVersion` whose only supported entry is `SPARK` (an absent software config is accepted; a present-but-empty one is `InvalidArgument`); `latest`, `<major>`, `<major.minor>` and the image-line alias `dataproc-<major.minor>` are dereferenced at create to a concrete `<major.minor>-dataproc-<n>` release (an unknown alias or release is `InvalidArgument`). Of the image-line aliases, real GCP accepts exactly `dataproc-2.2` (the Dataproc image line the GKE engine releases are built on, resolving to `3.5-dataproc-28` like `latest`); every other line (`dataproc-2.1`, `dataproc-2.3`, `dataproc-3.0`, …) is rejected there too, so it is `InvalidArgument` here rather than inferred — [real-GCP capture](docs/gcp/dataproc-gke-version-aliases.md). `stagingBucket` must be a bare bucket name.

Jobs, however, get a real placement/isolation boundary in K8s executor mode: each cluster runs in its own Kubernetes namespace — the caller's `kubernetesClusterConfig.kubernetesNamespace` when supplied, else a deterministic derived name (`gcp-dataproc-<project>-<cluster>-<hash8>`) — provisioned on cluster create and removed on cluster delete or `/_jaiscloud/reset` **only when the emulator created it** (a pre-existing namespace is adopted and left in place; its jobs are still reaped on cluster delete, while reset reclaims only emulator-owned namespaces). When the emulator's ServiceAccount cannot manage cluster-scoped namespaces, or in mock execution mode, the cluster falls back to the process-wide `JAISCLOUD_K8S_NAMESPACE`. The effective namespace and its ownership are recorded on the cluster record (`namespace`/`namespaceOwned`). The required RBAC — the `jaiscloud-executor` ClusterRole and a per-namespace RoleBinding, plus the `jaiscloud-namespace-admin` ClusterRole for namespace create/delete — is in `deploy/k8s/rbac.yaml`.

The **docker executor** is the k8s-free path (`JAISCLOUD_SPARK_EXECUTOR_MODE=docker`, or `JAISCLOUD_EXECUTOR_MODE=docker`): each job runs as a one-shot container on the local Docker daemon, where the configured Spark image (`JAISCLOUD_K8S_SPARK_IMAGE`) executes `spark-submit --master local[*]` in client mode with the same GCS-connector env/`--conf`s the k8s driver pods receive. The emulator host is reachable from the container as `host.docker.internal` (a loopback `STORAGE_EMULATOR_HOST` is rewritten for the container), or, when the emulator itself is containerized (`JAISCLOUD_DOCKER_MODE=container`), by its name on `JAISCLOUD_DOCKER_NETWORK`, which the driver joins (CDE1). The driver's stdout/stderr is streamed from the container log into the job's `driverOutputResourceUri`, and cancel, cluster delete and `/_jaiscloud/reset` reap the container. Like the Cloud Run/Lambda/ECS executors it dials `/var/run/docker.sock` (ignoring `DOCKER_HOST`) and falls back to mock when no daemon is reachable. Docker and k8s are interchangeable implementations of one executor seam and change no wire surface — the executor choice never affects a fidelity tier (`docs/gcp/testability.md` §8). Verified by `make test-e2e-dataproc-docker` (`tests/persistent_mode/gcp/dataproc/`, local Docker).

### Dataproc: Compute-Engine cluster read defaults

A `config`-shaped (Compute-Engine) cluster always reads back the default fields real clients dereference, even when the create request omitted them: `config.softwareConfig.imageVersion` (the service default is the latest GA Debian image; the emulator reports `2.3.3-debian12` unless the caller pins a version, and a pinned version is echoed verbatim), `config.gceClusterConfig.zoneUri` (the full Compute self-link for the caller's zone, else `<region>-a` — real Dataproc picks a zone in the region when none is named), and the instance groups (1 master / 2 primary workers on `n1-standard-4` with a 500 GB boot disk when the whole group is absent), filling only what the caller left unset. When the create names neither `networkUri` nor `subnetworkUri`, the read also names the project's `default` network (`projects/{p}/global/networks/default`), which is the network real Dataproc uses then; it does **not** materialise a `subnetworkUri` for that case (a real get leaves one out too — see [dataproc-gce-network-default.md](docs/gcp/dataproc-gce-network-default.md)). Every Compute Engine link in the config is answered as the absolute self-link a real get returns, whatever spelling the caller used: `gceClusterConfig.zoneUri`/`networkUri`/`subnetworkUri` and the instance groups' `machineTypeUri` accept a short name (`us-central1-a`, `default`, `n1-standard-4`), a partial resource name (`regions/us-central1/subnetworks/default`) or a full URL, and read back as `https://www.googleapis.com/compute/v1/...` under the cluster's own project (a short subnetwork takes the cluster's region). The defaults and the canonical links are rendered per read, never written into the stored config, so the record stays exactly what the caller sent. This matters to real clients: the `hashicorp/google` provider reads `config.softwareConfig.imageVersion` without a nil check, so a `google_dataproc_cluster` with a plain `cluster_config` used to panic inside the provider on its read-back, and a client parsing `zoneUri`/`machineTypeUri` would otherwise see a different resource name than real GCP reports. `virtualClusterConfig`-shaped clusters are unaffected and still carry no `config`. The other fields a real read also reports are not materialised: `instanceNames`, `imageUri`, `preemptibility`, `configBucket`, and the remaining Compute links (`nodeGroupAffinity.nodeGroupUri`, `accelerators[].acceleratorTypeUri`, `autoZoneExcludeZoneUris`) are echoed as sent rather than canonicalised.

### Dataproc: asynchronous cluster/job state machine

Cluster create/update/start/stop/delete return a pollable `google.longrunning.Operation` (`Done=false`) whose status advances lazily on each `operations.get` read — there is no background goroutine. A create shows the cluster `CREATING` then `RUNNING` (the readiness delay is clock-driven and overridable via `JAISCLOUD_DATAPROC_CLUSTER_READY_DELAY`); a delete keeps the `DELETING` record until the transition fires, then removes it. `ERROR` is reachable through the test failure-injection hook and, for a Dataproc-on-GKE cluster, through a real provisioning mismatch (a `nodePoolConfig` that disagrees with an existing GKE pool), which leaves the cluster `ERROR` with the pool and field in `status.detail`. Likewise `jobs.submit` writes `PENDING` and advances `SETUP_DONE → RUNNING → DONE` as the job is polled, and `jobs.cancel` walks `CANCEL_PENDING → CANCEL_STARTED → CANCELLED`. Under a real executor `jobs.cancel` also reaps the running driver — deleting the client-mode k8s Job (and, by cascade, its pod) in K8s mode, or force-stopping the driver container in Docker mode — so a running driver actually stops rather than continuing after the job reports `CANCELLED`. On the gRPC surface the generic `google.longrunning.Operations` stub does not read the Dataproc store, so a `SubmitJobAsOperation` LRO can only be `Wait`-polled once the job is terminal in the default mock executor; the REST `operations.get` path always reflects the store.

### Dataproc: long-running and restartable jobs

A job is treated as **long-running (streaming)** when its type-job `properties` set a `spark.sql.streaming.*` or `spark.streaming.*` key: in mock mode it stays `RUNNING` (never auto-settling to `DONE`) until `jobs.cancel`; under the Docker/K8s executor it is an ordinary job that stays `RUNNING` while the driver pod lives and reaches `DONE` only on driver exit `0`. Real GCP has no streaming marker — detection from `properties` is an emulator approximation (a streaming job is simply one whose driver never exits, so a never-exiting driver that sets no streaming property is not detected). The real-k3d smoke `make test-dataproc-streaming-k8s` stages a `readStream.format("rate")` driver with a `gs://` checkpoint and sink, asserts the job stays `RUNNING` while micro-batches commit, then cancels it and asserts `CANCELLED` plus the driver k8s Job/pod being reaped. The Kafka-source variant `make test-dataproc-streaming-kafka` reads from the live Managed Kafka (Redpanda) broker `bootstrapAddress` — the `spark-sql-kafka` connector (not bundled in `apache/spark:3.5.0`) is staged on GCS and passed through `jarFileUris` — and additionally asserts checkpoint `offsets`/`commits` and the checkpoint-log Kafka consumer offsets advance across a second seeding wave.

`Job.scheduling` (`maxFailuresPerHour` / `maxFailuresTotal`; REST and gRPC) is parsed, validated against the documented maxima (`0..10` / `0..240`; `0` or omitted = no restart, the API default) and echoed back. Under a real executor (docker or k8s) a non-zero driver exit restarts the driver while within both limits and not thrashing (`>4` non-zero exits in a 10-minute window), recording `ATTEMPT_FAILURE` between attempts; success is strictly driver exit `0` and exhaustion reaches `ERROR`. Restart counters live only for the job's current execution (they are not persisted across a restart/resubmission of the same `jobId`) and the per-hour window is modelled as a fixed window; the mock executor echoes the fields but never restarts. `SparkJob.jarFileUris` and `PySparkJob.jarFileUris` are passed to `spark-submit --jars` (additional driver/executor classpath jars — the documented way to add connector jars); `SparkRJob` has no such field and `SparkSqlJob.jarFileUris` was already wired.

### Dataproc: job-type support matrix

`jobs.submit` runs the Spark family (including Spark SQL); every other type-job is fail-loud. The emulator is metadata-not-engine for the non-Spark engines — the Hive Metastore plane is served separately (see [Dataproc Metastore: control plane + Hive Thrift serving plane](#dataproc-metastore-control-plane--hive-thrift-serving-plane)) — so it does not attempt to execute Hive/Pig/Presto/Trino/Flink work.

| Type-job | Behaviour |
|---|---|
| `sparkJob` / `pysparkJob` / `sparkRJob` | Run via the Spark executor (mock, or real driver under `JAISCLOUD_SPARK_EXECUTOR_MODE=docker|k8s`; docker runs `spark-submit --master local[*]` in the configured Spark image, k8s a client-mode Job). |
| `sparkSqlJob` | Runs the real Spark SQL CLI (`spark-sql`) over the same executor in docker/k8s mode (mock mode simulates it): `queryList.queries` via `-e`, `queryFileUri` via `-f` (a `gs://` script is read through the wired GCS connector), `jarFileUris` via `--jars`, `scriptVariables` via `--hivevar`, and `properties` via `--conf`. Fail-loud if neither `queryFileUri` nor `queryList.queries` is set. |
| `hadoopJob`, `hiveJob`, `pigJob`, `prestoJob`, `trinoJob`, `flinkJob` | Fail loud (see below). |

Submitting an unsupported type does **not** return an RPC error: the job is created and immediately lands in `ERROR` with details `job type <X> is not supported by the emulator`, so the client observes a terminal job rather than a transport failure. In particular **hiveJob** is fail-loud because execution is engine-bearing (a Hive/Pig/Presto/Trino/Flink runtime or query engine) while the emulator is metadata-not-engine; the Hive Metastore plane is a separate surface (see the Metastore subsection below).

Because the emulator is metadata-not-engine, **hiveJob** stays fail-loud rather than being silently approximated: HiveQL is a superset of Spark SQL, so running it on Spark would diverge on Hive-specific constructs. If you need Hive execution, point your own engine at the emulator: the Hive Metastore Thrift plane serves the catalog (one catalog per Metastore Service, plus the legacy shared catalog on the base port — see the Metastore subsection below), so a HiveServer2 or Spark deployment attached to it can execute queries while the emulator stores the table metadata.

### Dataproc: driver output is captured from the client-mode driver

A job's `driverOutputResourceUri`/`driverControlFilesUri` are allocated at submit and point into a staging bucket (`config.tempBucket`/`config.configBucket`, else a derived `dataproc-staging-<project>-<region>-<hash8>`; real Dataproc uses `dataproc-staging-<region>-<projectNumber>-<random>`, but the name is opaque to clients). At terminal state the driver's stdout/stderr is written to `<driverOutputResourceUri>.000000000` and a control file under `driverControlFilesUri`, so `gcloud dataproc jobs wait` and log readers resolve real objects in the emulated GCS. Capture is from the client-mode `spark-submit` main container only (no YARN/cluster-mode driver logs, no multi-container multiplexing) and is byte-capped at 4 MiB; in mock mode a small synthetic line is written so the advertised URI still resolves. Driver output is staged only at termination (there is no continuous/streamed output), so a long-running job's advertised URI resolves to nothing until the job is cancelled or its driver exits. Executor pods receive the `fs.gs.*` connector config plus `spark.executorEnv.*` mirrored from the driver, and caller `properties` cannot strip the injected connector confs.

### Dataproc: `Reset` does not drain in-flight Spark job goroutines

`POST /_jaiscloud/reset` wipes the Dataproc store but does not cancel or wait for jobs currently executing (Docker/K8s executor mode). This matches AWS EMR's own `Reset` behaviour in this codebase, which is a no-op for the same reason — not a GCP-specific gap. If you reset while a job is mid-execution and then resubmit a job with the *same* `(project, region, jobId)` before the stale run finishes, the stale run's completion could overwrite the new job's state. Avoid reusing job IDs across a reset boundary while a prior run may still be in flight.

for Apache Spark** — is not implemented. That is the whole `locations/{location}`

It fails loud and identically on both transports rather than being invisible:

### Dataproc WorkflowTemplates: only the latest version is retained

`WorkflowTemplateService` is served over REST + gRPC (`create`/`get`/`list`/`update`/`delete`, plus `instantiate`/`instantiateInline`). Only the **latest** version of a template is stored: `create` stores version 1, `update` requires the request version to match the current one (`ABORTED` on mismatch) and bumps it, and a `get`/`delete` naming a non-current explicit version returns `NotFound` (real GCP keeps a version history). Instantiation runs the template's `OrderedJob` DAG through the same job core, so only the Spark-family job types (`sparkJob`/`pysparkJob`/`sparkSqlJob`/`sparkRJob`) execute; other job types fail loud exactly as `SubmitJob` already does (see [Dataproc: job-type support matrix](#dataproc-job-type-support-matrix)). The `workflowTemplates` IAM trio (`getIamPolicy`/`setIamPolicy`/`testIamPermissions`) is served over the shared policy store, and the same three verbs are served on `clusters` and `jobs` (etag OCC, AIP-149 versions; the policy is stored but never enforced).

A placement's `managedCluster` goes through the same create path as `clusters.create` (one core entry point, so both transports agree): `ManagedCluster.config` is Required, so a placement without one is the same `INVALID_ARGUMENT` a config-less create returns, the cluster gets the ordinary validation/defaults/namespace ownership, and a failed create leaves no cluster or namespace behind. An existing cluster of that name is reused untouched (not workflow-owned); one the workflow creates is deleted when the workflow ends.

### Dataproc lifecycle events on Pub/Sub (emulator-defined)

Every cluster and job state transition publishes one message to a configured Cloud Pub/Sub topic, so event-driven consumers can observe the Dataproc lifecycle without polling `operations.get`/`jobs.get`. **This is an emulator-defined contract** — real GCP has no native Dataproc Pub/Sub event source — so it is opt-in and off by default.

- **Enable:** start the emulator with `JAISCLOUD_DATAPROC_EVENTS_TOPIC=<topic>` (a topic ID or full `projects/{p}/topics/{t}` name; a bare ID is scoped to the transition's project). Publishing is disabled unless that variable is set or a cluster carries the per-cluster label below.
- **Per-cluster override:** set the cluster label `jaiscloud-events-topic` to route that cluster's — and its jobs' — events to a different topic. The label alone enables publishing for that cluster even when the env default is unset.
- **Message body:** a structured [CloudEvents 1.0](https://cloudevents.io) JSON envelope (`specversion`, `id`, `source` `//dataproc.googleapis.com/projects/{p}/regions/{r}/clusters/{c}`, `type`, `datacontenttype`, `time`, `data`). Types are `google.cloud.dataproc.v1.job.v1.stateChange` and `google.cloud.dataproc.v1.cluster.v1.stateChange`; `data` carries `projectId`, `region`, `clusterName`, `jobId`/`clusterUuid`, `previousState`, `state`, `stateStartTime` (and `attempt` for jobs).
- **Message attributes:** the same key fields are mirrored as string attributes (`eventType`, `projectId`, `region`, `clusterName`, `jobId`, `previousState`, `state`, `attempt`) so a subscription `filter` can select them.
- **States:** jobs emit the full machine (`PENDING`, `SETUP_DONE`, `RUNNING`, `CANCEL_PENDING`, `CANCEL_STARTED`, `CANCELLED`, `DONE`, `ERROR`, `ATTEMPT_FAILURE`); clusters emit `CREATING`, `UPDATING`, `STARTING`, `STOPPING`, `RUNNING`, `STOPPED`, and a terminal `DELETED` when the record is removed (`DELETED` is emulator-only — `ClusterStatus` has no such state). A cluster reaches `ERROR` only through the failure-injection path the tests use (real provisioning failures are not observable), and `attempt` on a job event is `1` today because the Spark engine does not retry (the emulator never begins a second attempt).
- **Best-effort:** a transition never fails because of eventing; a publish error (e.g. the topic does not exist) is logged and dropped. If Cloud Functions is enabled, each transition is also dispatched directly to any function whose event trigger names the matching Dataproc event type **and** the specific job/cluster resource (the trigger `resource` must match the event's `jobs/{id}` / `clusters/{name}`).

### Dataproc cluster Metastore attachment

A cluster may attach an existing Dataproc Metastore service through `config.metastoreConfig` (GCE) or `virtualClusterConfig.auxiliaryServicesConfig.metastoreConfig` (GKE). The `dataprocMetastoreService` reference is validated at cluster create/update: the canonical `projects/{p}/locations/{l}/services/{s}` name and the short forms `locations/{l}/services/{s}`, `services/{s}` and a bare `{s}` are accepted (missing project/location default to the cluster's), a malformed name is `InvalidArgument`, an unknown service is `NotFound`, and a service in a region other than the cluster's is rejected (`InvalidArgument`) — real Dataproc requires the cluster and its Metastore service to share a region. The raw reference is echoed back on get/list. At job submit the attachment is injected into the Spark driver/executor confs as `spark.hadoop.hive.metastore.uris` plus `spark.sql.catalogImplementation=hive`; caller job `properties` override the injected values (Spark last-value wins). The injected endpoint is the attached Service's own `endpointUri` — `thrift://<id>.<location>.metastore.jaiscloud.local:<service-port>` — so a job reads exactly its Service's catalog and not another Service's. The hostname is not resolvable from Spark pods, so set `JAISCLOUD_DATAPROC_HMS_ENDPOINT=<reachable-host>` (a bare host, `host:port`, or a `thrift://` URI) to substitute a pod-reachable host. The override replaces the **host only**: the port stays the Service's catalog port, which is what selects the catalog (a port in the override is ignored, so existing `host:9083` settings keep working).

### Dataproc: Iceberg on the Hive Metastore catalog

A Dataproc-submitted Spark job can use the emulator's Hive Metastore as an **Iceberg** catalog. The deployed `spark-gcs` image ships only the GCS connector, so the self-contained `iceberg-spark-runtime` jar is staged on the emulator's GCS and passed through the job's `jarFileUris` (→ `spark-submit --jars`, the documented Dataproc mechanism — no image change needed). The job's `properties` then point Iceberg's `SparkCatalog` at the Thrift metastore with the connector-backed `HadoopFileIO` data path (the emulator's protected `fs.gs.*` wiring is injected and cannot be stripped):

```
"spark.sql.catalog.hms":              "org.apache.iceberg.spark.SparkCatalog",
"spark.sql.catalog.hms.catalog-impl": "org.apache.iceberg.hive.HiveCatalog",
"spark.sql.catalog.hms.uri":          "thrift://<reachable-hms-host>:9083",
"spark.sql.catalog.hms.warehouse":    "gs://<bucket>/<prefix>/",
"spark.sql.catalog.hms.io-impl":      "org.apache.iceberg.hadoop.HadoopFileIO"
```

`CREATE TABLE hms.<db>.<table> (...) USING iceberg LOCATION 'gs://…'` then commits metadata JSON and Parquet data files to GCS and registers the table in the Thrift catalog (`CREATE DATABASE IF NOT EXISTS hms.<db>` first — HiveCatalog does not auto-create the namespace). Point `spark.sql.catalog.hms.uri` (and `spark.hadoop.hive.metastore.uris`) at the attached Service's `endpointUri` host/port pair — its host replaced with a pod-reachable one — to use that Service's catalog; the base port `9083` addresses the legacy shared catalog instead. Verified end-to-end by `make test-e2e-iceberg-k3d` (`tests/persistent_mode/gcp/iceberg-k3d/`, tag `iceberg_k3d_e2e`): a GKE-`virtualClusterConfig` cluster attached to a Metastore service has a `pysparkJob` write the table, a second job reads back the row count and snapshot list, and the test asserts real `metadata/*.json` + `data/*.parquet` objects in GCS. The k3d deployment (`deploy/k8s/jaiscloud-gcp.yaml`) exposes the HMS Thrift base port `9083` plus the per-Service catalog port block `9084-9093` on the emulator Service and sets `JAISCLOUD_DATAPROC_HMS_ENDPOINT=jaiscloud-gcp.jaiscloud.svc.cluster.local:9083` so pods can reach a catalog (the port in that value is ignored; the Service's own port is used). A deployment with more than ten Services must widen that port block (and keep `--hms-port` at 9083 so the numbering matches).

### Dataproc: Iceberg Structured Streaming sink

The same catalog accepts a Spark Structured Streaming sink. The Job stages the Kafka connector closure on GCS alongside the Iceberg runtime (both go in `jarFileUris`), the driver creates the table (`CREATE TABLE … USING iceberg LOCATION …` — Iceberg's streaming `toTable` requires the table to exist), and the stream is written with `writeStream.format("iceberg").outputMode("append").option("checkpointLocation", "gs://…").toTable("hms.<db>.<table>")`. Append mode commits **one Iceberg snapshot per micro-batch** while the `gs://` checkpoint tracks the Kafka source offsets, so the committed metadata/snapshot log grows under the table LOCATION and the job stays RUNNING. Verified end-to-end by `make test-e2e-iceberg-streaming-k3d` (`tests/persistent_mode/gcp/iceberg-k3d/`, tag `iceberg_k3d_e2e`, needs `JAISCLOUD_KAFKA_BROKER_MODE=k8s`): a live Managed Kafka source → Iceberg append sink; the gate seeds two Kafka waves, asserts the snapshot (`metadata/snap-*.avro`) and Parquet (`data/*.parquet`) files grow across them while RUNNING, cancels (asserting the driver k8s Job is reaped and the broker reaped), then reads the table back (row + snapshot counts). The append sink runs on the memory-tight k3d node, so like the batch gate it needs host headroom: the client-mode driver pod has no memory limit, and a co-resident workload can push the node into OOM-killing it before the first micro-batch.

### Dataproc Metastore: control plane + Hive Thrift serving plane

The management plane is implemented (`Service` / `Backup` / `MetadataImport` / `Federation` CRUD with long-running operations; the separate `google.cloud.metastore.v1.DataprocMetastoreFederation` gRPC service and the REST `federations` resource are served, and a federation's `endpointUri` names the legacy shared `:9083` catalog, because a federation has no catalog of its own). The `google.iam.v1.IAMPolicy` mixin is served at the service/backup/database/table/federation levels over the shared policy store (metadata-only; authorization is not enforced): REST exposes `:getIamPolicy`/`:setIamPolicy`/`:testIamPermissions` exactly where the Discovery declares them (`testIamPermissions` on services and federations only), and the gRPC mixin is dispatched through the shared `IAMPolicy` router alongside Pub/Sub/KMS/Eventarc (the pinned metastore proto defines no IAM RPCs). Database/table IAM is keyed by the resource name without an existence check, because the emulator models no database/table control-plane record — those live in the separate Hive Thrift catalog (the admin/DR operations do reach that catalog through the serving plane; the policy plane stays metadata-only and existence-free). The table-metadata plane is served by Hive Metastore **Thrift** listeners that answer the database, table, partition, and lock methods Spark's Hive/Iceberg clients use. Real Dataproc Metastore gives every Service its own HMS, and so does the emulator: **each Service has its own catalog, served on its own port**. Creating a Service binds a listener for it and stores the port on the Service: a `port` in the request is honored (the API field is Optional and real Metastore echoes it, as the Terraform provider's Optional+Computed `port` expects), while a request without one gets `--hms-port` + 1 and then upward; the port is a real routing address, so a requested one must be free (no other Service holds it) and must not be the base `--hms-port` (a duplicate is `ALREADY_EXISTS`, the reserved base `INVALID_ARGUMENT`); an update may move it (`updateMask=port`) and rebinds the listener; the wire `port` and `endpointUri` (`thrift://<id>.<location>.metastore.jaiscloud.local:<port>`) are that listener, so two Services — in the same project or in different projects/locations — never collide on a database name, each has its own `default`, and Iceberg commit locks are scoped per catalog so a commit on one Service cannot block another. Deleting a Service closes its listener and drops its catalog. The Thrift protocol carries no service identity, so the listener (the port) is what selects the catalog — point a client at a Service's `endpointUri` port, and the Dataproc attachment injection does that automatically. The base port `:9083` (`--hms-port`) keeps serving the **legacy shared catalog**: a client that names no Service — the plain-HMS/off-the-shelf-client path, the pre-per-Service tests, and the local Iceberg docker setup — still sees one global catalog there, and a snapshot taken before per-Service catalogs restores into it. (The AWS Glue Data Catalog in this emulator remains one catalog per account+region shared by every job; Glue models no per-service catalog.) Partition support covers the generic Hive/Hadoop-migration path — add/get/list (by name, prefix, filter, spec), alter, rename, and drop, over a `jc_hms_partitions` store (memory + Postgres + snapshot, partitioned by the same catalog identity; a batch add — `add_partitions`, and `add_partitions_req` even when its entries name different tables — is one atomic unit, so a mid-batch failure such as a missing table or a duplicate rolls back every partition the request already inserted) — while Iceberg keeps its own partition metadata. The Hive-3.x paths — `get_table_meta` (the pattern-based bulk table-metadata lookup) and `alter_table_with_cascade` (an alias of `alter_table`; stored partition descriptors are not cascaded) — are served; the client-connect identity method `set_ugi` and the request-struct table reads `get_table_req`/`get_table_objects_by_name_req` are served too, so Hive 2.3+/3.x clients (and off-the-shelf Go HMS clients) connect and read tables without relying on `UNKNOWN_METHOD` fallbacks; the niche partition methods (`exchange_partition(s)`, `drop_partitions_req`, `get_partition_values`, `get_partitions_by_expr`, event marking) return an explicit unsupported error; the gRPC control plane (`Service`/`Backup`/`MetadataImport` CRUD) is implemented over the official `DataprocMetastore` proto. The catalog admin/DR operations are split by whether the emulator can back them with real catalog state. `MoveTableToDatabase` and `AlterMetadataResourceLocation` are **served** on both transports: each mutates the Service's own catalog — the same store its Thrift plane serves — so a move re-keys the table and all of its partitions onto the destination database (name, Hive struct and storage location preserved, no data copied) and an alter re-points the addressed resource's location (`databases/{db}`, `…/tables/{t}`, or `…/partitions/{p}` with the Hive partition name), leaving its children's locations alone; an unknown database/table/partition is `NOT_FOUND`, a destination collision `ALREADY_EXISTS`, and a malformed name `INVALID_ARGUMENT`. Each returns the done operation carrying its empty method response. `ExportMetadata`, `RestoreService`, and `QueryMetadata` remain `Unimplemented` by decision, because serving them would require a metadata format the emulator does not store: `ExportMetadata` would have to write a MySQL dump or Avro files of the Hive metastore backend's RDBMS schema (`DBS`/`TBLS`/`SDS`/…), `RestoreService` would have to consume such an artifact (or a backup containing one; emulator backups are control-plane records with no artifact), and `QueryMetadata` would need a read-only SQL engine over that same schema plus a Cloud Storage result manifest. Each fails loud (`501` / `UNIMPLEMENTED`) with a message naming the missing plane, rather than fabricating a result. On the single host, `locations/{l}/operations/{id}` is path-identical to Cloud Workflows' LRO surface: the default host routes it to Workflows, while Metastore's canonical host (`metastore.localhost` / `metastore.googleapis.com`, first DNS label `metastore`) serves its own `GetOperation`/`ListOperations`. By default Metastore's own operations are returned inline (`done: true`), so no client needs to poll them, while in the opt-in async mode (`JAISCLOUD_LRO_MODE=async`) a poll is resolved against the Metastore store over REST and gRPC.

### Long-running operations (gRPC): endpoint-scoped shared service

Real GCP serves `google.longrunning.Operations` on each service's own host, so `ListOperations(parent=…)` returns only that endpoint's operations. The emulator serves one `Operations` on the single gRPC listener and discriminates by the HTTP/2 `:authority`: a client configured for a service's endpoint (`{service}.localhost`, `{service}.googleapis.com`, or `grpc.WithAuthority`) is served only by that service — the gRPC analogue of the REST `Host` token. Registered endpoints are Managed Kafka (`managedkafka`), Dataproc Metastore (`metastore`), Cloud Run (`run`), Cloud Functions (`cloudfunctions`, v1+v2), Dataproc (`dataproc`), Workflows (`workflows`), and — in the opt-in async LRO mode — Service Usage (`serviceusage`) and Resource Manager (`cloudresourcemanager`). A request to an unregistered endpoint (`localhost:8081`) keeps the shared name-based `Get`/`Wait` and an empty `List` page rather than crossing services. Verified end-to-end by the gRPC conformance suite (`ListOperations (… endpoint)` checks, each asserting Get+List at the owning endpoint and sibling isolation).

### BigLake Iceberg REST Catalog: DB-backed, standard REST spec

The BigLake Iceberg REST Catalog is mounted at `/iceberg/` (Spark configures `uri=http://host:port/iceberg/`) and speaks the standard `org.apache.iceberg.rest.RESTCatalog` protocol. It models GCP's real BigLake Metastore managed-Iceberg product, whose catalog is the standard Apache Iceberg REST spec — Spark, Trino, and Flink attach over that spec. (Dataproc Metastore's own table plane is the Hive Metastore Thrift server, a separate product.) The catalog is database-backed (Polaris-style): it stores the `TableMetadata` JSON and a synthesized `metadata-location` pointer (`{location}/metadata/{version:05d}-{uuid}.metadata.json`) but never writes `metadata.json`/`version-hint.text` to object storage itself — the client's `FileIO` does that. `CommitTableRequest` requirements (`assert-table-uuid`, `assert-ref-snapshot-id`, schema/spec/sort-order assertions, …) and updates (`assign-uuid`, `add-schema`, `add-snapshot`, `set-properties`, …) are applied atomically, so concurrent commits cannot lose updates. `set-statistics`/`remove-statistics`/`set-partition-statistics`/`remove-partition-statistics` persist to `TableMetadata.statistics`/`partition-statistics` (upsert and remove keyed by `snapshot-id`), and the `POST /tables/{table}/metrics` report endpoint validates the table and `report-type` and acknowledges with `204` (reports are not retained — the spec exposes no read-back, so aggregation is left to the caller/backend).

### Eventarc: trigger CRUD + Pub/Sub & Cloud Storage → Cloud Functions / Cloud Run / HTTP delivery

Eventarc is implemented as trigger-based metadata CRUD, **not** the AWS EventBridge "bus + rule + event-pattern + target" fan-out model (the two are different models despite the shared "event routing" purpose). A `Trigger` is a stored record with a `destination` (Cloud Run service, Workflows, HTTP endpoint, GKE, or Cloud Functions), a `transport.pubsub.topic` source, and `eventFilters` (at least one of which must have `attribute: "type"`, as real Eventarc requires; a trigger whose `type` names a Cloud Storage event must also carry a non-empty `bucket` filter, as real Eventarc rejects a Cloud Storage trigger without one); a `Channel` is a 3rd-party-source registration record referencing a `provider`; and `Provider` resources are read-only discovery (a small catalogue of real providers — `pubsub.googleapis.com`, `storage.googleapis.com` — not invented ones). `destination.cloudFunction` is accepted (it must name an existing function, else `404`) and is executed: when a message is published to the trigger's `transport.pubsub.topic`, the emulator matches the trigger's `eventFilters` (including the `type`) and invokes the destination function (see [Cloud Functions](#cloud-functions-metadata-crud-real-execution-v2-deploy-end-to-end)). A `destination.httpEndpoint` trigger is delivered too: the produced event is matched and POSTed as a binary-mode CloudEvents request (`ce-id`/`ce-source`/`ce-specversion`/`ce-type`/`ce-time`, `application/json`), fire-and-forget with no retries — a Pub/Sub publish carries the push-delivery body (`message`/`subscription`), while a **Cloud Storage** object finalize/delete is selected by its `type`/`bucket` (and optional `object`) `eventFilters` and carries the object-metadata JSON (`StorageObjectData`) with source `//storage.googleapis.com/projects/_/buckets/{bucket}` and type `google.cloud.storage.object.v1.finalized`/`deleted`. A `destination.cloudRun` trigger is delivered as the same CloudEvents request, forwarded through the Cloud Run runtime to the named service's latest ready revision (resolved by service + region, honoring `path`) rather than an HTTP call to the generated host, so it needs a ready revision and works without DNS. The remaining destinations (GKE, Workflows) remain stored metadata references only — no Workflow execution is created; only a `destination.cloudFunction` trigger provisions a backing Pub/Sub subscription, exposed as the output-only `transport.pubsub.subscription` and used as the dead-letter surface (see [Cloud Functions](#cloud-functions-metadata-crud-real-execution-v2-deploy-end-to-end)). Source/destination references are validated structurally — a `transport.pubsub.topic` must name an existing Pub/Sub topic, a `destination.workflow` an existing Workflow, and a `destination.cloudFunction` an existing function (`NotFound` otherwise) — and a channel's `pubsubTopic`/`activationToken` are synthesized placeholders.

Trigger and Channel writes honor `updateMask` (masked paths take the incoming value, unmasked paths retain the stored value, merged inside the store's atomic mutate closure), support `validateOnly=true` (validate then skip the write), and enforce `etag` optimistic concurrency control: a deterministic content-checksum etag is recomputed on every create/update, and a stale etag on patch/delete is rejected with **409 `ABORTED`**. A trigger/channel `uid` is a UUID4, and a newly created unconnected Channel reports `state: PENDING` (it only becomes `ACTIVE` once a provider connects). Trigger/Channel IAM (`getIamPolicy`/`setIamPolicy`/`testIamPermissions`) is implemented via the shared policy store (etag OCC included), not `Unimplemented`.

The Eventarc advanced surface is served on both transports as control-plane metadata CRUD: `MessageBus`, `Enrollment`, `Pipeline`, and `GoogleApiSource` are location-scoped collections with `create`/`get`/`list`/`update`(patch)/`delete` (`validateOnly`, `updateMask`, and `etag` OCC as for triggers), `ChannelConnection` has `create`/`get`/`list`/`delete` plus an output-only `activationToken`, and the `GoogleChannelConfig` is a per-location singleton with `get`/`update` (returned inline, not via an operation). Records are stored in the shared resource store (memory + `--dsn` Postgres identical), echo the request body verbatim, and are reached over REST under `/v1/projects/{p}/locations/{l}/{messageBuses|enrollments|pipelines|googleApiSources|channelConnections|googleChannelConfig}` and over gRPC with the official `cloud.google.com/go/eventarc` client. `messageBuses/{bus}:listEnrollments` returns the names of the enrollments attached to a bus; the reference contract is enforced (an enrollment's `messageBus` and a channel connection's `channel` must exist, else `404`); and the IAM trio is served on every new resource through the shared policy store and `google.iam.v1.IAMPolicy` router.

Known debt for Eventarc: list `filter`/`orderBy` are **not** honored (`ListTriggers`/`ListChannels` ignore them and return the full page, as do the advanced-surface lists); output-only fields (`name`/`uid`/`etag`/times/`state`/`activationToken`/`pubsubTopic`) are overlaid on read but a client-supplied output-only field in a create/patch body is not rejected, it is echoed into the stored config; non-function delivery is fire-and-forget (no retries or dead-lettering) and the GKE/Workflows destinations are not delivered (a `cloudRun` destination is delivered only when a ready revision exists — otherwise it is logged and dropped) — the delivered `subscription` is a synthesized reference because the emulator only provisions a backing Pub/Sub subscription for a `cloudFunction` trigger; and the advanced surface (message buses, enrollments, pipelines, Google API sources, channel connections, Google channel config) is **control-plane metadata only** — it records the routing graph but the emulator runs no message-bus/pipeline delivery engine, so an enrollment/pipeline does not actually route events (a `ChannelConnection` records the channel reference and mints an activation token; no SaaS provider connect is modelled).

### Cloud Functions: metadata CRUD, real execution, v2 deploy end-to-end

Cloud Functions v1 and v2 are implemented as metadata CRUD over the shared function store, plus `call` invocation through the shared container executor (mock echo by default; Docker/K8s under `JAISCLOUD_FUNCTIONS_EXECUTOR_MODE` or `JAISCLOUD_EXECUTOR_MODE` run the GCP Functions Framework contract, source mounted at /workspace). A function whose source is referenced by a **GCS object** — v1 `sourceArchiveUrl` (`gs://bucket/object`) or v2 `buildConfig.source.storageSource` — has that archive fetched through the emulated Cloud Storage (decrypted via the storage provider), persisted in the blob store with a sha256 revision hash, and mounted into the container in Docker/K8s mode, so a deployed function really executes. In K8s mode the archive is fetched by a `code-fetch` init container over the admin API (`{JAISCLOUD_FUNCTIONS_CODE_URL}/lambda/code/{project}/{location}.{id}/$LATEST`); the mount is enabled only when `JAISCLOUD_FUNCTIONS_CODE_URL` (or a cluster-reachable `JAISCLOUD_GCS_EMULATOR_ENDPOINT`, with `/_jaiscloud` appended) is configured, otherwise the init container is skipped. v2 `generateUploadUrl` provisions a `gcf-v2-sources-{project}-{location}` GCS bucket and returns a `storageSource` plus an **emulator-reachable** `uploadUrl` (so a raw PUT lands in the emulated GCS; real GCP returns a `storage.googleapis.com` URL), which makes `gcloud functions deploy --gen2` run end-to-end (upload → create → poll). Each deploy bumps a persisted revision counter, so a deployed function renders `serviceConfig.revision` — the backing Cloud Run service revision (`…/services/{id}/revisions/{id}-{NNNNN}-{sha8}`) — and `allTrafficOnLatestRevision`; there is no real container build (the archive is only checked non-empty). A function is always born `state: ACTIVE` with a synthesized HTTPS trigger URL (unless an `eventTrigger` is supplied). That URL is served: a request addressed to the trigger host (`{location}-{project}.cloudfunctions.net/{id}`, detected by Host, any HTTP method; the rest of the path is ignored) invokes the function with the raw request body as its payload and returns the result, a `500` for an executor error or function timeout, and `404` for an unknown or event-only function. Function-level CORS is not modelled. `Create`, `Update` (PATCH), and `Delete` return a **done `google.longrunning.Operation`** — `done: true`, typed `metadata`/`response` `Any`s — and the operation is persisted (memory + Postgres + snapshot), so `operations.get`/`list` and REST `:wait` return it after a restart.

`UpdateFunction` honors the `updateMask` query parameter (accepted spellings include lowerCamel and snake_case, with an optional `function.` prefix): only masked fields are overlaid on the stored function (unmasked fields are retained), an empty mask overlays every mutable field present in the body, and the merge runs inside the store's atomic read-modify-write (`UpdateFunctionAtomic`) so concurrent disjoint-field PATCHes cannot lose updates. An unrecognized mask path fails loud with **501 `UNIMPLEMENTED`** rather than being silently ignored. `locations.list`/`locations.get` return a synthesized region set and honor `pageSize`/`pageToken`; the bare `/v1/projects/{p}/locations[/{l}]` path is shared with Memorystore and is served by the Memorystore handler (which returns the same `google.cloud.location.Location` records), so the route does not collide.

Input validation is deliberately shallow: a create requires a non-empty `runtime` and a function id (from `?functionId=` or the body `name`), and `name`/`path` resource names must match `locations/{l}/functions/{id}` (full `projects/{p}/…` form also accepted) — otherwise **400 `INVALID_ARGUMENT`**. Source archive contents/URLs (other than a non-empty check) and runtime/entry-point compatibility are **not** validated. Memory and the v2 `serviceConfig` instance/concurrency settings **are** range-validated against the real API — v1 `availableMemoryMb` must be one of 128/256/512/1024/2048/4096/8192, v2 `availableMemory` 128M–32Gi, `minInstanceCount`/`maxInstanceCount` 0–1000 with `min ≤ max`, `maxInstanceRequestConcurrency` 1–1000, and `availableCpu` one of 1/2/4/6/8 vCPU or a sub-vCPU value 0.08–0.99 in increments of 0.01 (a milli suffix is normalized; below 1 vCPU the request concurrency must be 1) — and surfaced on the v2 `serviceConfig`; a configured `maxInstanceCount` (× `maxInstanceRequestConcurrency`) and a project-wide account cap (the shared executor's `JAISCLOUD_FUNCTIONS_CONCURRENCY_LIMIT`, default 1000) are enforced on every invocation entry point by an admission gate that returns **429 `RESOURCE_EXHAUSTED`** once the capacity is exceeded, but no separate project quota/account-settings API is modelled (FD11): Cloud Functions declares no account/quota method, so Lambda's `GetAccountSettings` has no GCP analogue to model. Function IAM (`getIamPolicy`/`setIamPolicy`/`testIamPermissions`) is implemented via the shared policy store. `call` is synchronous and returns the executor's echo/error inline (an executor failure is surfaced as `error` with HTTP 200, matching v1's `CallFunctionResponse`); the synthesized HTTPS trigger URL (`{location}-{project}.cloudfunctions.net/{id}`) is served (Host-scoped, raw body → `CallFunction`, HTTP 500 on an executor error/timeout, 404 for an unknown or event-only function); the v2 surface, `ListRuntimes`, per-deploy revisions, `allTrafficOnLatestRevision`, and event-trigger delivery (retry + dead-letter records) are implemented. The v2 1st→2nd gen upgrade/traffic control plane — `setupFunctionUpgradeConfig` (config overrides), `redirectFunctionUpgradeTraffic` / `rollbackFunctionUpgradeTraffic` (traffic target), `commitFunctionUpgrade` / `commitFunctionUpgradeAsGen2` (finalize), `abortFunctionUpgrade`, and `detachFunction` — is served over REST with a persisted `upgradeInfo` state machine; traffic is moved only by the upgrade redirect/rollback, since real Cloud Functions exposes no general traffic-percentage API. Those seven methods are served **REST-only in practice**. Google's RPC reference documents them as `google.cloud.functions.v2.FunctionService` RPCs, but the public `googleapis` proto mirror (unchanged since April 2025) and every generated client (Go, Java, Python, Node) omit them, so the emulator's generated-proto gRPC server cannot register them; the Discovery-generated REST client `google.golang.org/api/cloudfunctions/v2` exposes all seven.

Event triggers are live. A function deployed with an `eventTrigger` (v1 `{eventType, resource, service, failurePolicy.retry}` or v2 `{eventType, pubsubTopic, retryPolicy}`) is invoked when a matching event is produced: a **Pub/Sub publish** (v1 `google.pubsub.topic.publish` / legacy `providers/cloud.pubsub/eventTypes/topic.publish`), a **GCS object finalize/delete** (`google.storage.object.finalize`/`.delete` or the v1 `object.change` catch-all), or an **Eventarc trigger** whose destination is the function. Both the legacy v1 and v2/Eventarc event-type spellings, and the short and fully-qualified resource forms, are matched. Delivery runs on a bounded background worker: the function is invoked through the same executor as `call`, a failure is retried (v1 `failurePolicy.retry`; v2 `RETRY_POLICY_RETRY`) with bounded exponential backoff, and every attempt is recorded in a persisted delivery record (`delivered` / `failed` / `dead_letter`) that survives a restart under `--dsn`. Under the GCP-native profile an event invocation is delivered as a **CloudEvent** in binary content mode (`ce-specversion`/`ce-id`/`ce-source`/`ce-type` + the event data body), so a Functions-Framework `@functions_framework.cloud_event` handler receives it. A Pub/Sub event trigger materializes a **backing Eventarc trigger** — the v2 render exposes it as the output-only `eventTrigger.trigger`, and `projects/{p}/locations/{l}/triggers/{id}` shows its `transport.pubsub.subscription` — whose platform-provisioned Pub/Sub subscription (`eventarc-{location}-{trigger}`) is the dead-letter surface: set `deadLetterPolicy.deadLetterTopic`/`maxDeliveryAttempts` on it with `subscriptions.patch` (REST `PATCH /v1/projects/{p}/subscriptions/{s}`, gRPC `UpdateSubscription`), and an exhausted delivery is republished to the dead-letter topic with the `CloudPubSubDeadLetterSource{Subscription,SubscriptionProject,DeliveryCount,TopicPublishTime}` attributes, recorded as `dead_letter` with its `deadLetterTopic`. The subscription's `maxDeliveryAttempts` (5–100) bounds the retries in place of the emulator's default cap, and its `retryPolicy.minimumBackoff`/`maximumBackoff` drive the exponential retry curve (an optional `maxDoublings` bounds the doubling steps); with no policy the emulator keeps its observable 200 ms → 2 s default. A delivery the invocation admission gate refuses (**429 `RESOURCE_EXHAUSTED`**, see above) is treated as back-pressure, not a failure: the function was never invoked, so the engine re-polls with bounded backoff **without consuming an attempt** and never dead-letters it. A throttle that outlasts that bounded in-process re-poll leaves the record `pending` (attempt budget untouched) and is not resumed on its own — a deliberate emulator divergence from Pub/Sub, which would keep counting attempts toward the subscription's `maxDeliveryAttempts`. Delivery is unauthenticated (as everywhere), and the retry window is bounded rather than real GCP's seven days.

### Cloud DNS: metadata only, no authoritative DNS server

Cloud DNS is implemented as metadata CRUD over the shared `ResourceStore`, mirroring the AWS Route53 provider. `ManagedZone`s, `ResourceRecordSet`s, and `Change`s are stored records — the emulator never stands up an authoritative DNS server, so `nameServers` are synthesized `ns-cloud-*.googledomains.com.` placeholders and zones never resolve queries. `managedZones.{create,get,list,patch,update,delete}`, `managedZones.{get,set}IamPolicy`/`testIamPermissions`, `resourceRecordSets.{create,get,list,patch,delete}`, `managedZoneOperations.{get,list}` and `changes.create` are supported. `changes.create` applies its `additions`/`deletions` to the stored record sets synchronously and returns `status: "done"`. `managedZones.patch`/`update` return the `dns#operation` the Discovery document declares (type `update`, status `done`, with the pre-/post-operation zone in `zoneContext`), recorded per zone so an official client's `managedZoneOperations.get` poll settles on the first call; the mutation is applied when the operation is created, so the next `managedZones.get` shows the change. `clientOperationId` on either mutation is used as the operation id and must be unique within the zone. `projects.get` returns a synthesized `dns#project` with a `quota` block. The `id` of a managed zone and the project `number` are stable numeric strings derived from the resource name.

Zone-level IAM is served over the shared policy plane: `managedZones.getIamPolicy`/`setIamPolicy`/`testIamPermissions` read-modify-write a policy stored per zone (etag OCC, AIP-149 versions; the policy is stored but never enforced, and no `google_dns_managed_zone_iam_*` caller can be denied). The zone must exist before any verb (an absent zone is `404 NOT_FOUND`, not an empty policy), and the policy is dropped with the zone, so a zone re-created under the same name starts from the empty default. Known debt for Cloud DNS: DNSSEC (`dnsKeys`) and `policies`/`responsePolicies` are **not** implemented and fail loud with `501 UNIMPLEMENTED`. List pagination honors `maxResults`/`pageToken` (and `sortBy` for `managedZoneOperations.list`); `managedZones.patch` and `managedZones.update` share merge semantics (description/visibility/labels are overlaid, unmasked fields retained, and `dnsName` is immutable/ignored). Operations are only recorded for those two mutations (the surface where the Discovery document declares them) and are always done: the emulator has no asynchronous authoritative-server propagation to wait on, and deleting a zone drops its operation history. Only `name`, `dnsName`, `description`, `visibility`, and `labels` are persisted — the other managed-zone config blocks (`dnssecConfig`, `forwardingConfig`, `peeringConfig`, `privateVisibilityConfig`) are accepted but dropped, so no DNSSEC, forwarding, peering, or private-zone visibility behavior is applied.

### Memorystore for Redis: metadata only, no Redis data plane

Memorystore for Redis is implemented as metadata CRUD over the shared `ResourceStore`, mirroring the Cloud DNS provider and keyed by project + location (region). The emulator never stands up a Redis server, so an instance is born in `state: READY` with a synthesized `host` (a stable `10.x.y.z` placeholder) and `port: 6379` that nothing listens on — there is no data plane, no `AUTH`, no persistence, and no failover. `instances.create` takes `?instanceId=`, defaults `tier` to `BASIC` (rejecting anything but `BASIC`/`STANDARD_HA` with `400`), defaults `memorySizeGb` to `1` and `redisVersion` to `REDIS_7_0`, and stores `displayName`, `labels`, `redisConfigs`, and the location. `instances.get/list/delete` and `instances.patch` (which applies `updateMask`; unsupported mask paths fail loud with `400`) are supported, and `instances.upgrade` applies the requested `redisVersion`. List pagination honors `pageSize`/`pageToken`, and `locations.get`/`locations.list` return synthesized `projects/{p}/locations/{l}` records.

Create/Update/Delete return the `google.longrunning.Operation` **inline** with `done: true` and the resulting instance in `response` (the Dataproc/Metastore convention): the shared `locations/{location}/operations/{id}` path is path-identical to Cloud Workflows' LRO surface on the single emulator host, so Memorystore does not claim it and operations are never persisted or pollable. Location discovery is the one bare `/v1/projects/{p}/locations[/{l}]` path claimed by Memorystore; no other emulator service serves it. Deferred surfaces — `instances.import`/`export`/`failover`/`rescheduleMaintenance`/`getAuthString`, backup collections, and the Redis Cluster surface — are not routed and fall through to the generic `404` rather than silently succeeding.

### Cloud SQL Admin: metadata only, no SQL engine

Cloud SQL Admin (`sqladmin.googleapis.com/sql/v1beta4`) is implemented as metadata CRUD over the shared `ResourceStore`, mirroring the Cloud DNS/Memorystore providers and the AWS RDS provider, keyed by the project at `store.GlobalRegion`. The emulator never stands up a database server, so an instance is born in `state: RUNNABLE` with a synthesized `connectionName` (`{project}:{region}:{instance}`), `selfLink`, `serviceAccountEmailAddress`, `settings` defaults (`tier` `db-f1-micro`, `dataDiskSizeGb` `"10"`, `availabilityType` `ZONAL`, ...), a synthesized per-instance server CA as `serverCaCert` (the `server-ca.pem` a real client downloads), and a cosmetic `PRIMARY` IP that nothing listens on — there is no SQL engine, no data plane, and no AuthN/AuthZ. `instances.{insert,get,list,update,patch,delete,restart}`, `databases.{insert,get,list,update,patch,delete}`, `users.{insert,get,list,update,delete}`, and `sslCerts.{insert,get,list,delete}` are supported, plus the synthesized `flags.list`, `tiers.list`, and `connectSettings.get` discovery surfaces.

`sslCerts.insert` mints real certificate material: a self-signed X.509 client certificate (PEM), its private key (returned once, like real Cloud SQL — the `SslCert`/list shapes carry no key field), the instance's server CA, and the `sql#sslCertsInsert` envelope with an `UPDATE` operation. `get`/`delete` address the certificate by its uppercase-hex SHA-1 fingerprint (the emulator accepts either case), and the documented per-instance cap of 10 client certificates and the `[a-zA-Z.-_ ]+` common-name constraint are enforced. The certificates are self-signed (there is no TLS endpoint to chain them to) and live for the documented 10 years.

Every mutation returns Cloud SQL's own `Operation` envelope (`kind: "sql#operation"`, with `operationType`, `targetId`, `targetLink`, `selfLink`, and `insertTime`) inline with `status: "DONE"` — **not** a `google.longrunning.Operation` — and the same operation is persisted so `operations.get`/`operations.list` read it back. List responses use Cloud SQL's envelopes (`sql#instancesList`, `sql#databasesList`, `sql#usersList`, `sql#sslCertsList`, `sql#operationsList`), and pagination honors `maxResults`/`pageToken`.

Known debt for Cloud SQL: the engine-less design means `Instances.Update` and `Instances.Patch` share merge semantics (body fields overlay the stored instance, `settings` sub-fields are deep-merged, and the server-owned `region`/`state`/`selfLink`/`ipAddresses` are immutable/ignored); a user's `password` is accepted but never stored or echoed; `settings` blocks other than the fields the emulator defaults are preserved verbatim without any behavioral effect; the certificates carry no TLS chain (the server CA signs nothing, since no client ever completes a handshake); and deferred surfaces — `sslCerts.createEphemeral`, `backupRuns`, `clone`, `failover`, `promoteReplica`, `import`/`export`, `demote`, `resetSslConfig`, `operations.cancel`, and the instance certificate custom methods (`instances:generateEphemeralCert`, ...) — fail loud with `501 UNIMPLEMENTED` rather than silently succeeding. The `v1beta4` path shape is recognized by the shared GCP identity extractor (`/v{N}beta{M}/projects/{project}`).

### Compute Engine: metadata only, no VM/disk/network data plane

Compute Engine (`compute.googleapis.com/compute/v1`) is implemented as metadata CRUD over the shared `ResourceStore`, mirroring the Cloud DNS/Memorystore/Cloud SQL providers and the AWS EC2 provider. Records are keyed by the project (AccountID) and the request scope — the zone for zonal resources, the region for regional resources, and `store.GlobalRegion` for global resources — so instances and disks with the same name in different zones never collide. The emulator never boots a VM or attaches a real disk: an instance is born in `status: RUNNING` with synthesized ids, `selfLink`s, `creationTimestamp`s, a cosmetic `nic0` interface that nothing listens on, and a stable `cpuPlatform`; `start`/`stop`/`reset` only flip the stored status (`RUNNING`/`TERMINATED`). There is no data plane and no AuthN/AuthZ.

Supported surface: zonal `instances.{insert,get,list,delete,start,stop,reset}` plus `instances.aggregatedList`; zonal `disks.{insert,get,list,delete}`; global `networks.{insert,get,list,delete}` and `firewalls.{insert,get,list,delete}`; regional `subnetworks.{insert,get,list,delete}`; the synthesized project resource (`projects.get`, any id resolves, carrying the project's `defaultServiceAccount`); the derived public-image catalog (`images.get` for a concrete build and `images.getFromFamily` for a family, in the projects Google publishes images from); synthesized `machineTypes.get/list` (zonal), `zones.get/list`, and `regions.get/list`; and zonal/regional/global `operations.get/list`. Every mutation returns Compute Engine's own `Operation` envelope (`kind: "compute#operation"`, with `operationType`, `targetId`, `targetLink`, `selfLink`, `insertTime`, and `progress: 100`) inline with `status: "DONE"` — **not** a `google.longrunning.Operation` — and the same operation is persisted at its scope so `operations.get`/`operations.list` read it back. List responses use the `compute#*List` envelopes, and pagination honors `maxResults`/`pageToken`.

Disks resolve an `image` reference exactly as real Compute does: `disks.insert` accepts the documented `projects/{p}/global/images/{image}`, `projects/{p}/global/images/family/{family}`, `global/images/{image}`, `global/images/family/{family}` and absolute self-link spellings, resolves a family to the catalog's concrete build, and records the image's absolute `selfLink` in the disk's `sourceImage` (plus `sourceImageId`), so a `google_compute_disk` (and a `google_compute_instance` boot disk) with a documented `image` applies, re-plans with **No changes**, and destroys. A reference that names no image is a `404`, and a malformed (non-API) spelling is a `400`.

Known debt for Compute Engine: the data-plane fields are accepted and preserved but have no effect (attached disks are stored verbatim, no boot disk is provisioned, `metadata`/`tags`/`labels` are cosmetic); a disk's record keeps the fields its documented surface uses — `name`, `sizeGb` (default 10), `physicalBlockSizeBytes` (default 4096, the server default real Compute reports), `type`, `zone`, `description`, `labels`, the resolved `sourceImage`/`sourceImageId` — and echoes every persisted caller input on read (`guest_os_features`, `licenses`, `provisioned_iops`/`provisioned_throughput`, `access_mode`, `resource_policies`, `storage_pool`, `architecture`, `replica_zones`, `enable_confidential_compute`, `async_primary_disk`, `source_disk`/`source_snapshot`/`source_instant_snapshot`/`source_storage_object`), each only when the request carried it because only `physicalBlockSizeBytes` documents a server default; `params` (Discovery: input only, not persisted) and the encryption-key blocks (real Compute returns no key material) are not echoed; `id`/`targetId` are stable numeric strings derived from the resource name (the real API assigns server-side integers); the default network is only a synthesized name, not a seeded resource; a network's record reports the two fields Discovery documents a server default for — `mtu` (`1460`) and `networkFirewallPolicyEnforcementOrder` (`AFTER_CLASSIC_FIREWALL`) — and echoes a caller-supplied value for either (both are validated against the documented range/enum on create and on patch); `networks.patch` is served as the mutation path the provider's update uses: a merge patch applies `mtu` and the firewall enforcement order in place and returns the `DONE` operation the client polls, so recreating-after-apply a network whose `mtu` or order changed converges instead of failing with a `501`; a patch that carries `routingConfig`/BGP or the ULA IPv6 pair is accepted but not persisted, and `networkProfile`/`internalIpv6Range` stay outside the record, the same read-shape boundary the create path has (raw-reader fidelity only, since the provider skips an absent `routingConfig` and keeps the configured value in state — TF2-17-2). `networks.update` is not a published method in the current `compute/v1` Discovery, so the `PUT` spelling answers `501` rather than inventing a second mutation path (TF2-17-1); the project resource is synthesized on read (for a project id the number is the deterministic `resource.ProjectNumber`; a project addressed by number is taken at face value, because the synthesized number is not invertible), and its `defaultServiceAccount` names the `{number}-compute@developer.gserviceaccount.com` account IAM does not render yet (TF2-1-1), so `data.google_compute_default_service_account` still stops at its IAM verification read. The image catalog is derived, never stored: a concrete public image is served for a name that carries a real build label (`-vYYYYMMDD`, or Cloud COS's milestone/build/patch/revision suffix) in a project Google publishes public images from, a family is served for any family name in one of those projects, and the family's reported build (and a concrete image's `family`) is synthesized — the emulator has no image registry and no image bytes, so `images.insert`/`list`/`delete`/`patch`/`deprecate`/`setLabels` and the image IAM mixin stay unserved. Everything outside the supported surface — addresses, snapshots, instance templates and groups, routers, backend services, the image write methods, `instances.setMetadata`/`attachDisk` and the other custom methods, `operations.wait`, and `aggregatedList` for resource types other than instances — resolves to `501 UNIMPLEMENTED` rather than a `404`. The `compute/v1` path shape is recognized by the shared GCP service detector by its `/compute/v1/` prefix, and the client `BasePath` must include that prefix.

### Cloud Resource Manager: a minimal project registry, not a resource hierarchy

Resource Manager serves the legacy v1 REST project API and the v3 gRPC `google.cloud.resourcemanager.v3.Projects` surface over one core. On top of the emulator's original synthesize-on-read behaviour — any project id resolves as `ACTIVE` with a deterministic project number, so existing clients and tests that address arbitrary projects keep working — it keeps a lightweight **registry** of explicitly created projects: `CreateProject` (validated id grammar, `409 ALREADY_EXISTS` on duplicate), `GetProject`, `ListProjects` (v1 `projects.list`: created projects unioned with the configured default project and `JAISCLOUD_EXTRA_ACCOUNTS`, paginated; the v3 RPC is parent-scoped — see below), `DeleteProject` (marks `DELETE_REQUESTED`; idempotent on a second delete), and `UndeleteProject`, each returning a `google.longrunning.Operation` (done inline in the default `sync` LRO mode). The registry is persisted in the shared `ResourceStore`, so it round-trips through memory, `--dsn` Postgres, snapshots, and `/_jaiscloud/reset`, and the console's project picker lists created projects alongside the configured accounts.

**Observed projects** answer "which project did the workload actually use?". Because an unknown id is synthesized as `ACTIVE`, a client pointed at `projects/acme-e2e` writes real resources without anything registering the project; the picker's configured ∪ created view would never show it. The emulator therefore records a `gcp_observed_project` entry (project, first/last seen, request count, up to 16 service ids) the first time a request addresses a project that is neither configured nor registered, with `lastSeen`/`requests` refreshed at most every 30 s. The set is capped at 200 by last activity, is excluded from the configured/registered groups so nothing appears twice, and is cleared by `/_jaiscloud/reset`. It is a discovery aid, not a registry: the wire semantics are unchanged, nothing is auto-registered, and a project's resources are never re-keyed when it is registered. Read it from the console (`GET /api/ui/v1/gcp/projects`, session-gated, rows tagged `configured`/`registered`/`observed`), from the admin plane (`GET /_jaiscloud/projects`, the same snapshot), or with `jaiscloud-gcp projects [--observed|--registered|--all] [--since 10m] [--json] [--host …]`. The observed set is **per emulator store**: several emulator instances pointed at one `--dsn` share it, while a workload pointed at a different emulator (and therefore a different store) stays invisible to this one.

**Project administration** is implemented over the same registry (v3 gRPC `SearchProjects`/`UpdateProject`/`MoveProject`, plus the legacy v1 REST `projects.update`): `UpdateProject` applies a field-masked metadata edit (`display_name`/`labels`; an empty mask applies the populated fields, and the masked `labels` map is replaced wholesale), `MoveProject` stores a new parent reference (`organizations/{id}` or `folders/{id}`; a non-`ACTIVE` project is `FAILED_PRECONDITION` and moving to the current parent is a no-op), and `SearchProjects` evaluates the v3 query grammar over the created ∪ configured set. A project's etag rotates on every successful update/move, and a request that supplies a stale etag is rejected `409 ABORTED`.

Deliberately **not** modelled: the org/folder **hierarchy** itself (only each project's parent *reference* is stored and reparentable), billing or quota, real project-number allocation (the number stays a deterministic hash of the id), the 30-day deletion window (a deleted project is restorable indefinitely), and IAM enforcement (project policies are stored metadata; the caller is always owner). The v1 `projects.list` `filter` and the v3 `SearchProjects` query share one case-insensitive OR-ed clause grammar over `name`/`displayName`, `id`/`projectId`, `labels` and `labels.<key>`, `lifecycleState`/`state`, and `parent`/`parent.type`/`parent.id` (trailing `*` is a prefix match, a bare `labels:<value>` matches a label key *or* value, and a by-parent query carrying both `parent.type` and `parent.id` ANDs the two); any other field or a malformed expression is `400` rather than a silently unfiltered page. v3 `ListProjects` requires its `parent` (`organizations/{org_id}` or `folders/{folder_id}`; missing or malformed is `400`), returns only the projects whose stored parent reference is exactly that parent (a project with no recorded parent is under none, and descendants of a child folder are not listed since no hierarchy is modelled), and orders by ascending `display_name` (project id as the tie-break) across pages. The unscoped read is v3 `SearchProjects` and the v1 `projects.list`.

## Demo spine verification baseline (SPK6)

The crypto-medallion demo follows one data product through provision → ingest →
process → serve → observe → automate against a single `jaiscloud-gcp` instance on
k3d. Every link is gated individually, but no single run used the demo's combined
config. `make test-e2e-demo-spine-k3d` (`scripts/demo-spine-verify.sh`) is that
run: it configures the deployment **once** with the combined config and runs the
composed gates against that one instance, recording the acceptance baseline the
recording is built on.

Combined config applied (one instance):

- `JAISCLOUD_SPARK_EXECUTOR_MODE=k8s` — real client-mode Spark pods;
- `JAISCLOUD_KAFKA_BROKER_MODE=k8s` — real Redpanda broker;
- `JAISCLOUD_CLOUDRUN_EXECUTOR_MODE=k8s` with `JAISCLOUD_CLOUDRUN_URL_SUFFIX=run.localhost`
  and `JAISCLOUD_CLOUDRUN_URL_PORT=18080` — browser-reachable revisions (SPK4);
- `JAISCLOUD_GCP_THROTTLE` unset — throttle off;
- `JAISCLOUD_DATAPROC_HMS_ENDPOINT` — the pod-reachable Hive Metastore (SPK1);
- LRO at the emulator default (synchronous). The demo's async-LRO
  pending→running→done beat is a "use on cue" pacing control (design §9), not a
  steady setting. Since SPK9 the Run/Eventarc k3s gate harnesses poll
  `operations.get`, so the cue can be folded in without failing them: set
  `SPINE_LRO_ASYNC=1`. It is also exercised separately by
  `make test-lro-async-gcp`.

The harness settles between suites so the previous suite's Spark/Kafka
driver+executor+broker pods drain before the next suite needs the same ~6 GiB k3d
node (a heavy suite started into a still-draining one leaves the next Spark
driver unschedulable). Suites run in order:

| Stage | Suite | Baseline evidence |
|---|---|---|
| Process | Iceberg batch on HMS (SPK1) | write job DONE, 3 rows, ≥1 snapshot; real `metadata/*.json` + `data/*.parquet` under the table `LOCATION` |
| Process | Iceberg Structured Streaming sink (SPK2) | wave 1 → snapshots=1/data=3, wave 2 → snapshots=2/data=6 while RUNNING; cancel + driver reap; read-back 9 rows |
| Process | Lakehouse medallion | real `pysparkJob` + `sparkSqlJob`; 100 input rows → 1 published object, orders reproduce the ingested distribution |
| Serve | Cloud Run browser reachability (SPK4) | synthesized `*.run.localhost` authority loads the service page with no `Host` override |
| Serve | Eventarc delivery | GCS-sourced trigger → Cloud Run / HTTP sink delivers the CloudEvent |
| Automate | Scheduler → Dataproc hop (SPK3) | `httpTarget` tick → in-cluster submitter → `dataproc.jobs.submit` reaches DONE, with the real Cloud Scheduler headers |
| Observe | Monitoring metric → alert incident (SPK5) | `CreateTimeSeries` crosses a `condition_threshold` policy → incident fires → notification pulled from the topic subscription |

The verification run found and fixed two real defects: a Dataproc Postgres
`UpdateJobAtomic` surfaced a benign SERIALIZABLE conflict (SQLSTATE 40001) as an
HTTP 500 under the real Spark job-state reconciler (now retried, via the shared
`storeutil.RetrySerializable`), and recreating a Dataproc cluster / Kafka broker
whose derived namespace was still `Terminating` failed all subsequent creates in
it (the shared namespace create now waits for the old namespace to disappear).
The Scheduler hop gate also gained a Service-endpoint readiness wait, because a
Ready submitter pod does not guarantee kube-proxy has programmed the ClusterIP and
a no-`retryConfig` job delivers exactly once.

The Dataproc-on-GKE lifecycle behind that hop — a zonal GKE cluster, the virtual
cluster, cross-project buckets and the downscoped credential — has its own
customer-shaped demo and gate: [`demo/dpgke-lifecycle/`](demo/dpgke-lifecycle/README.md),
`make test-e2e-dpgke-demo-k3d`.
